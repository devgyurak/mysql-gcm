# MySQL GCM 암복호화 함수 (component) — 설계와 절차

> **언어.** [English](design.md) · 한국어
>
> 이 문서는 [`design.md`](design.md) 의 한국어 번역입니다. **영어판이 정본**이고, 두 문서가 다르면
> 영어판이 맞습니다 (`.agents/rules/docs.md`). 설계를 바꿀 때는 두 문서를 같은 PR 에서 함께 고칩니다.

> ## 개정 A17 (2026-10-14) — 부분 일치를 위한 키드 n-gram 토큰 인덱스: 사전 등록된 누출 실험
>
> **상태: 기각 (2026-10-14) — 실험을 마쳤고 이 인덱스는 채택하지 않는다. `src/`, `spec/` 또는
> 벡터의 어떤 파일도 바뀌지 않았고, 이슈 #38 은 구현 PR 없이 닫힌다.** 아래 프로토콜은 실험이
> 돌기 **전에 사전 등록**되어, 결과를 본 뒤에 기준을 옮길 수 없게 했다. 결과와 검토는 끝의
> **Outcome** 블록에 있다. 그 검토는 **사람의 암호 감사가 아니라 범위를 한정한 설계 검토**다
> (제약 13). 실험은 이 개정이 기록하는 A4 확장("Python 범위") 아래 Python 만 썼다.
>
> ### 왜 결과보다 먼저 등록하는가
>
> 프로젝트 규칙은 코드보다 설계를 먼저 고치는 것이다 (`docs/design.md` §0,
> `.agents/rules/architecture.md` §2). 실험에서 같은 규칙은 *기준*이 *결과*보다 먼저 온다는 뜻이다.
> 그러지 않으면 결과가 기준을 정한다. 그래서 "채택 기준"의 수치는 시작값이고, PR 1 리뷰에서 확정한 뒤
> **PR 1 이 머지되면 동결된다**: 그 뒤에는 이유를 적은 개정으로만 바뀌고, 결과가 불편하다고 바뀌지
> 않는다. 기준을 통과하지 못한 결과는 "declined" 결과이며, 기각은 이슈 입장에서 성공적인 결과다.
>
> ### 문제, 그리고 동기 쿼리가 최악의 사례인 이유
>
> 제약 5: 함수는 옵티마이저에게 불투명하므로 `WHERE gcm_decrypt(col, @k) LIKE '%김%'` 는 후보 행을
> 전부 스캔·복호화한다. 300k 행 실측: 직렬 p95 235–255 ms, 8세션 ~1 s, 32세션 ~4 s (`docs/perf.md`).
> 이슈 #38 은 2단계 검색을 제안한다 — 사이드 테이블의 키드 n-gram 토큰과 일반 인덱스가 후보를 먼저
> 줄이고, 실제 복호화가 최종 필터로 남으므로 토큰 충돌은 비용만 늘리고 잘못된 행을 돌려주지 않는다.
>
> **동기 쿼리는 인덱스의 최악 사례다.** `'%김%'` 는 실제 한국 이름 컬럼의 약 5분의 1과 일치한다
> (성씨 김 하나가 인구의 ~21%). 이런 컬럼 위의 유니그램 인덱스는 가장 많이 누출하면서 가장 적게
> 돕는다: 토큰 `김` 은 행의 ~21% 를 고르는데, 이는 인덱스에 쓸 만한 선택도가 아니다. 채택되는
> 변형은 이슈를 낳은 그 쿼리 하나가 아니라 전체 질의 혼합으로 판정한다.
>
> ### 위협 모델 — 누가 무엇을 보는가
>
> 결정적 키드 n-gram 토큰은 같은 n-gram 에 대해 같은 토큰이므로, 테이블을 읽는 공격자는 (행, 토큰)
> 간선의 라벨된 그래프를 본다. 네 적대자를 범위에 둔다:
>
> - **S1 — 스냅샷.** 탈취한 백업·덤프·레플리카: 토큰 테이블, 암호문 컬럼(GCM 봉투가 이미 길이를
>   드러낸다), 암호화되지 않은 평문 컬럼, 공개 이름 통계. 기준 사례.
> - **S2 — S1 + 조건부 사전분포.** S1 에 더해 이름 사전분포를 조건부로 만드는 다른 평문 컬럼
>   (출생 연도, 성별). 채택 기준은 이 적대자로 판정한다. 실제 테이블에는 이런 컬럼이 있기 때문이다.
> - **S3 — S1 + 알려진/주입된 행 m개.** S1 에 더해 공격자가 평문을 알거나 고른 m개 행(공격자가 고른
>   이름으로 등록한 환자, 또는 유출 표본). m ∈ {1, 10, 100, N의 1%}.
> - **S4 — 로그 열람자.** 검색 키와 검색 패턴이 서버 로그에 들어가고(제약 2), 한글 바이그램 공간은
>   ~1.2×10⁸ 이라 검색 키를 가진 쪽은 모든 토큰을 열거할 수 있다. **시뮬레이션하지 않고 논증한다** —
>   결과가 구성상 전부이기 때문이다. S4 는 질문 6(컴포넌트냐 레시피냐)이 중요한 이유다: 검색 키를
>   서버에 두지 않는 구성은 로그 노출을 없앤다.
>
> **토큰 다중집합 밖의 누출, 잊지 않도록 열거:** 물리·삽입 순서(따라서 행의 첫 토큰. 이름에서는
> 성씨다), `ROW` binlog 와 undo 로그(변경 이력), `mysql.innodb_index_stats` 와 인덱스 페이지 채움
> (어떤 토큰이 뜨거운지), 버퍼풀 덤프, 그리고 `patient_id` 로의 조인.
>
> **의도적으로 범위 밖:** 능동 변조, 메모리 스크래핑, 볼륨/접근 패턴 기반 쿼리 복구. 실재하지만
> 이 실험이 재는 것이 아니다.
>
> ### 무엇을 모델링하고, 무엇을 하지 않는가
>
> PRF 가 무엇이든 공격자는 같은 (행, 토큰) 그래프를 본다. 그래서 시뮬레이션은 토큰 함수를 n-gram
> 공간의 **무작위 단사** — 전단사 재표지 — 로 모델링하고, `b` 비트로 절단한다. 이는 `b` 가 공간의
> 엔트로피보다 낮을 때 무작위 함수로 동작한다. **암호 연산을 하지 않고, 하네스는 키 재료를 갖지
> 않는다.** 이것이 A4 의 Python 범위 확장을 가능한 한 작게 유지하고, `tests/leakage/` 가 출하
> 컴포넌트가 맞춰야 할 두 번째 참조 토크나이저가 되는 것을 막는다.
>
> **그 모델의 한계:** 토큰 함수가 이상적이라고 가정한다. 어떤 구체적 PRF 의 안전성도 재지 않고, 잴
> 수 없다 — 그것은 구성이 선택되는 곳에서 하는 별개의 논증이다. 이 실험은 **이상적 토크나이저가
> 주어졌을 때 토큰 구조에서 나오는 누출**을 재며, 그것이 채택 결정에 필요한 관점이다.
>
> ### 데이터
>
> 집계값만 커밋하고, 각각 출처·라이선스·조회일을 적는다. 라이선스는 데이터를 커밋하기 전에 확인한다.
>
> - 한국 성씨: 통계청 2015 인구주택총조사 (KOSIS).
> - 출생연도·성별 한국 이름: 대법원 출생신고 통계.
> - 라틴 성씨: US Census 2010 성씨 목록 (퍼블릭 도메인).
> - 라틴 이름: US Social Security Administration 아기 이름 (퍼블릭 도메인).
>
> N ∈ {5k, 50k, 300k, 1M}, 시드 ≥ 20, 그리고 공격자의 지식은 의도적으로 불완전하다: 지역 편중,
> 코호트 불일치, top-K 절단, 디리클레 잡음. 모든 복구율은 생성기와 공격자 사전분포 사이의
> 총변동거리와 함께 보고해, *완전한* 사전분포에서의 복구율을 현실적 사전분포에서의 복구율로
> 착각하지 않게 한다.
>
> ### 공격 (인용은 A17 에 적기 전에 원문과 대조한다)
>
> 1. **빈도 순위 / 최대우도 매칭** — 할당 문제로.
> 2. **동시출현 그래프 매칭** — n-gram 고유성 제약 아래(바이그램은 자기 유니그램과 항상 공존하고,
>    행에서 가장 빈번한 토큰이 성씨다).
> 3. **알려진 행 시딩** — m ∈ {1, 10, 100, 1%}.
> 4. **행 복원:** 토큰 다중집합 → 이름, 바이그램을 경로로 정렬.
>
> **시도하지 않음:** 시뮬레이티드 어닐링, 쿼리 복구 계열, 학습 기반 공격. 각 공격 구현은 정답을 심은
> 소형 데이터의 **known-answer 테스트**로 검증한다: 그곳에서는 복구율 100%를, 토큰이 없는 대조군에서는
> B0 수준으로 떨어져야 한다.
>
> ### 지표와 기준선
>
> - **누출:** 토큰 복구율(고유 및 출현 가중), 행별 성씨 정답률, 전체 이름 top-1·top-5, 그리고 공격
>   무관 구조 지표(동일 토큰 집합을 공유하는 행 분포, 유일 행 비율).
> - **B0 — 길이와 사전분포만.** 성씨 바닥(~21%).
> - **B1 — 전체 이름 `gcm_encrypt_det`** (값 전체의 동등성만).
> - **B1′ — 성·이름 분리 `gcm_encrypt_det`.**
>
> 모든 결과는 B0·B1 대비 증분으로 보고하고, 단독으로 보고하지 않는다. "공격이 실패했다"는 안전의
> 증거가 아니다: 공격 무관 지표와 완전 지식 상한을 공격 결과와 함께 보고한다.
>
> ### 변형 — 모든 누출 수치는 효용 수치 옆에 둔다
>
> 효용은 누출과 **함께** 보고한다: 토큰 질의가 만드는 후보 집합 배율, 인덱스가 스캔 없이 답하는
> 질의 비율, 저장 비용. 효용 없는 누출은 결과가 아니다.
>
> - **V0** 유니그램 + 바이그램 + 트라이그램.
> - **V1** 바이그램만 (2자 미만 문자열은 스캔 폴백).
> - **V2** 트라이그램만.
> - **V3** b ∈ {8, 12, 16} 비트 절단.
> - **V4** 동음(homophonic) 토큰.
> - **V5** 더미 패딩.
> - **V6** 행별 솔트 / 블룸(이 인덱스에는 구성상 불가 — 기록만, 시뮬레이션하지 않음).
> - **V7** 토큰 없음(B1′ + 스캔) — "기각" 비교 대상.
>
> 실제 워크로드가 없으므로 질의 모델을 세 가지 혼합으로 명시한다: 전체 이름, 이름만, 성만, 그리고 한
> 음절.
>
> ### 정규화 — 인덱스가 깨뜨리면 안 되는 불변식
>
> **지정된 최종 필터는 인덱스가 제시했어야 할 행을 절대 놓치면 안 된다.** 토큰을 최종 `LIKE` 가 쓰지
> 않는 정규화 형태 위에서 계산하면, 인덱스는 복호화가 맞췄을 행을 조용히 떨어뜨린다 — 실패는 느린
> 질의가 아니라 누락된 결과다. 세 후보:
>
> - **N1 — 바이너리 고정:** `COLLATE utf8mb4_0900_bin LIKE`, 대소문자·악센트 무시 포기.
> - **N2 — MySQL 이 정규화하게** `WEIGHT_STRING` (가설, 검증 필요).
> - **N3 — 더 거친 키** (대소문자 접기, 악센트 제거)와 문서화된 범위 축소.
>
> PR 6 은 이것을 실서버 8.0/8.4/9.x 에서 **평문 SQL 만으로** 검증한다 — 컴포넌트 함수도, C++ 도 쓰지
> 않는다 — 선언한 레퍼토리(한글 음절·자모 변종, Latin-1 과 확장, 전각)와 무작위 다문자 쌍 위에서:
> `h LIKE '%q%'` 가 성립하는데 `tokens(q) ⊄ tokens(h)` 인 행이 **0건**이어야 한다. 0이 아니면 그대로
> 기록하고 환경 탓으로 돌리지 않는다. 실측 비교 콜레이션은 `utf8mb4_0900_ai_ci`
> (`tests/integration/20_korean_like.expected`)이며, §5.3 이 예시로 드는 `utf8mb4_general_ci` 가
> **아니다**. 이 개정의 Outcome PR 이 그 표현을 라벨이 아니라 버전별 진실로 고친다.
>
> ### 후보 구성 (질문 6: 컴포넌트냐 레시피냐?)
>
> - **C0 — 기각** (V7 문서화). 기준 결과.
> - **C1 — 애플리케이션 레시피.** 검색 키가 서버에 닿지 않는다; 비용은 언어별 분절과 정규화 표류이고,
>   A4 와 긴장한다.
> - **C2 — 새 함수 없음.** `SUBSTRING(gcm_encrypt_det(@g, @search_key), 2, 12)`: 결정적 논스가
>   96비트 PRF 이지만, 봉투 레이아웃이 API 로 굳고 결정적 라벨을 재사용하므로 분리가 키 독립성에만
>   의존한다.
> - **C3 — 스칼라 함수** `gcm_search_token(bytes, key)` 16바이트, 전용 라벨, `_kr` 형태로 키를 로그에서
>   뺀다.
> - **C4 — 이슈의 JSON 함수** (비용 최대).
>
> **선택된 구성을 SQL 이나 애플리케이션으로 표현할 수 없을 때만 컴포넌트 함수를 고른다.** 기본값은
> 출하 표면을 늘리지 않는 것이다.
>
> ### 채택 기준 (등록값 — 실험 전 프로토콜 커밋에서 동결)
>
> **S2**(조건부 사전분포를 가진 스냅샷 적대자), 불완전 보조 지식, N = 300k, 시드 ≥ 20 에서 판정한다.
> 실험은 S2 의 하한인 **S1** 을 구현했다; Outcome 참고.
>
> **누출 상한** — B1 대비:
>
> - 출현 가중 **토큰** 복구율 ≤ B1 토큰 복구율 + 10 pp;
> - **성씨** 정답률 ≤ B1 성씨 정답률 + 10 pp;
> - **전체 이름 top-1** ≤ B1 top-1 + 5 pp, **top-5** ≤ B1 top-5 + 5 pp;
> - 유일 행 비율 ≤ B1′ 의 1.5 배.
>
> **효용 하한** — 세 가지 혼합 질의 모델, 재현율 100% 에서:
>
> - **1세션과 32세션** 모두에서 p95 ≤ 스캔 p95 의 0.5 배 (≥ 2배);
> - 인덱스가 스캔 없이 답하는 질의 비율은 보고만 하고 임계값을 두지 않는다.
>
> 리뷰어는 PR 1 이 머지되기 전에 이 수치를 바꿀 수 있다; 머지 후에는 아무도 바꾸지 않는다.
>
> ### Python 범위 — A4 확장
>
> A4 는 Python 을 벡터 생성·검증, SQL E2E·load 러너, 커밋된 측정값으로 문서 차트를 그리는 일로
> 한정한다. A17 은 **하나의 좁은 허용을 더한다:**
>
> > 합성 데이터 위의 누출 시뮬레이션. 암호 연산을 하지 않고, 아무 데도 배포되지 않는다.
>

>   B1 + 10 pp 다. 한국어 V0 는 출현 가중 **20.7%(공격 1) / 17.3%(공격 2)** 를 복구하고, 더 강한

> ## 개정 A16 (2026-10-13) — 에러를 내는 행은 여섯 함수 모두에서 모든 비밀을 버린다
>
> **상태: 구현되어 머지됨 (이슈 #43; PR #53 과 #54, 2026-10-13, 아래에 기록된 검토 뒤 저장소 owner 가
> 머지).** 규칙은 `src/udf_glue.cc` 의 `give_up_secrets` 이고 여섯 함수의 모든 행 콜백이 부르며,
> 거부는 그 옆의 `refuse_if_spent` 다. 고정한 것: `tests/adapter/udf_kr_test.cc`(wipe, 거부, 그리고
> 두 번째 검토 전까지 핀되지 않았던 두 경로)와 `tests/integration/nested`(케이스 20~26, major 별).
> 측정: 머지에서 `scripts/bench.sh --gate`, 그리고 #54 에 기록된 ASan/UBSan adapter 실행. 서버 원인은
> `docs/upstream-udf-handler-leak.md` 에 있다. **제안 상태이던 시절의 이 개정판은 개정이 *말하는*
> 범위를 넓혔다: #51–#55 스택 전체의 검토가, 같은 서버 결함이 아무것도 올리지 **않은** 인스턴스도
> 버린다는 것을 측정했다. 그래서 보장은 에러를 낸 그 행으로 한정되고, 한계는 암시되는 대신 적힌다.**
> A13 이 `_kr` 함수 세 개에 이 규칙을 주었다. 이 개정은 그것을 키 인자 함수 세 개에도 주고, 비용이 0 인 이유를
> 적는다.
>
> A13 의 "키 복사본"은 에러를 내는 `_kr` 행에 대해 이미 이것을 요구한다: 읽어 온 키, A11 컨텍스트,
> A11 nonce 키, 결과 버퍼를 `deinit` 이 아니라 그 자리에서 버린다. 거기서 멈춘 것은 그것이 가장 필요했던
> 함수가 문장 텍스트에 없는 키를 들고 있는 함수였기 때문이다. **이유는 그 세 함수에 국한되지 않는다.**
> A13 이 그것을 보여 주는 형태를 기록했고, #43 을 위해 추가한 스윕이 그것을 고정한다 —
> `tests/integration/nested`, 바로 앞 PR 에서 (A13 의 "커밋된 케이스로 고정하지 않는다" 는 문장도 거기서
> 고친다): loadable function 이 다른 함수의 인자로 평가되는 중에 에러를 내면 — *안쪽* 호출이 prepared
> statement 매개변수를 받는 것이 A13 이 드는 유일한 조건이다 — 그 함수의 `deinit` 이 호출되지 않는다.
> 문장이 끝날 때도, `DEALLOCATE PREPARE` 때도, 세션이 끝날 때도 아니다. 그 뒤에는 서버를 재시작할
> 때까지 `UNINSTALL COMPONENT` 가 거부된다. 그 `UDF_INIT` 이 들고 있던 것은 서버가 살아 있는 동안
> 지워지지 않은 채 메모리에 남았을 것이다 — 아래 규칙이 그것을, 에러를 낸 인스턴스에 대해, 막는다.
>
> **결정.** 여섯 암호 함수 모두의 모든 행 콜백 — `gcm_encrypt`, `gcm_encrypt_det`, `gcm_decrypt`, 그리고
> `_kr` 세 형태 — 은 서버에 에러를 반환하기 전에 다음을 버린다:
>
> - keyring 에서 읽어 온 키 (`_kr` 함수만, A13);
> - A11 상태: `gcm_decrypt` 뒤의 키 스케줄을 담은 스케줄된 `EVP_CIPHER_CTX`, 그리고 `gcm_encrypt_det`
>   뒤의 캐시된 nonce 키와 그 키 사본 (`gcm_encrypt` 는 둘 다 갖지 않는다);
> - 결과 버퍼. 그 순간 그 안에는 이전 행의 출력이 남아 있을 수 있다 — 복호화 두 함수는 평문, 암호화 네
>   함수는 봉투.
>
> 그 뒤 인스턴스는 **spent** 이다: 그 인스턴스에 대한 추가 호출은 이미 해제된 세션을 쓰는 대신 에러를
> 낸다. (NULL 인자는 여전히 SQL NULL 이다 — NULL 검사가 먼저이고 어떤 세션도 보지 않는다,
> `spec/envelope.md` §4 규칙 3.) 이 래치가 삭제를 관찰 가능하게 만든다 — 그런 호출은 테스트만이 할 수
> 있기 때문이며, 그 이유는 고정된 것이 아니라 소스에서 읽은 것이다(아래 문단).
>
> **비용이 0 인 이유.** A11 의 불변 목록은 사전 검사 실패가 스케줄을 그대로 두게 한다. 근거는 "한 행의
> 잘못된 키 길이는 그 행의 SQL 오류이지, 유효한 키 스케줄을 버릴 이유가 아니다" 라는 것이다. 잘못된
> 키 길이가 그 행의 SQL 오류라는 바로 그 점이 버리는 데 드는 비용이 0 인 이유다: 그 행의 에러로 실행이
> 끝난다. **테스트로 고정된 것이 아니라 8.0.43·8.4.11·9.4.0 소스에서 읽었다**:
> `udf_handler::get_arguments` 는 핸들러의 에러 플래그를 보고 일찍 돌아가므로, 에러를 보고한 뒤에 그 행
> 콜백이 다시 들어오지 않고, 삭제는 그 문장이 끝나는 동안 실행된다. 성공 경로는 바뀌지 않는다 — 성공하는
> 행은 A11 이 말한 대로 다음 행을 위해 컨텍스트와 nonce 키를 그대로 둔다. 세 major 가 중첩 형태에서 같게
> 동작한다는 데 기대지 않는다: 그렇지 않다(A13 "구현 기록", 케이스 `20`). 그 차이가 무관해지는 것은 **에러를
> 낸** 인스턴스가 메모리에 남기는 것에 대해서이고, 에러 없이 서버가 버린 인스턴스가 들고 있는 것에 대해서가 아니다.
>
> **의도적으로 다루지 않는 것.**
>
> - **`gcm.strict=OFF` 가 NULL 로 바꾸는 `bad_tag` 는 삭제하지 않는다.** 서버가 보기에 그 행은 성공했고
>   문장은 계속되므로 세션은 여전히 필요하다. 거기에는 A11 의 규칙이 이미 적용된다: 코어가 실패 시
>   사본·컨텍스트·nonce 키를 버리고, 다음 행이 여전히 복호화해야 하므로 `_kr` 함수만 읽어 온 키를
>   유지한다(A13). 결과 버퍼도 그대로 둔다: 문장이 끝나지 않았고, 문장을 끝내는 쪽이 삭제한다 — 성공이면
>   `deinit`, 에러 행이면 A16. 현재 행의 출력 너머로 버퍼에 남을 수 있는 것은 그 문장의 이전 행 출력이지,
>   문장의 끝이 남기는 비밀이 아니다.
> - **`deinit` 이 여전히 정상 종료 경로**이고 여전히 전부 소거한다(A11). A16 은 에러 경로에서만 `deinit`
>   에 대한 의존을 없앤다.
> - **에러를 낸 행, 그리고 오직 그 행.** 이 규칙은 행 콜백에서 발동하므로 에러를 보고하는 인스턴스만
>   덮을 수 있다. 같은 서버 결함은 아무것도 올리지 *않은* 인스턴스도 버린다 — 에러를 낸 함수의 형제,
>   성공적으로 봉인한 키 id 인스턴스, 실패한 재-prepare 가 버리는 모든 함수 — 그리고 컴포넌트는 그런
>   인스턴스에 대한 제어를 다시 얻지 못하므로 들고 있던 것, 즉 읽어 온 keyring 키까지 그대로 남는다.
>   어떤 행 콜백도 그것을 막을 수 없다; A11 과 A13 이 존재하는 이유인 행 간 재사용을 대가로 줄일 수
>   있는지는 열린 질문이고, 이 개정은 줄 수 없는 보장을 암시하는 대신 그 한계를 적는다.
>   `tests/integration/nested` 의 케이스 `23`~`25` 가 그 세 형태를 고정하고, `26` 은 `20` 의 `const_item`
>   변형 — constness 가 발동 조건이 아님을 보이는 대조군 — 이다.
> - **서버 결함을 고치지는 않는다.** 새어 나간 인스턴스는 여전히 새어 나간 것이고, 재시작까지
>   `UNINSTALL COMPONENT` 는 여전히 거부된다. A16 이 보장하는 것은 **에러를 낸 행의** 새어 나간
>   인스턴스별 상태에 키 재료도, 평문도, 쓸 수 있는 컨텍스트도 남지 않는다는 것이다. 서버 자신의 인자
>   버퍼는 컴포넌트의 손이 닿지 않으며, A11 이 이미 그렇게 적고 있다. 결함은 이슈 #43 이고
>   `tests/integration/nested` 가 고정하며 운영 제약 18 이 요약한다; 고치는 것은 서버의 몫이다.
> - **`init` 실패는 여기 포함되지 않는다.** `init` 이 할당한 것은 A9 의 롤백이 이미 해제한다; A16 은 행
>   콜백에 대한 것이다.
>
> **A11 이 잃는 것.** A11 의 불변 목록은 사전 검사가 그것을 "그대로 둔다 … `bad_key_len` 사전 검사에서는
> 건드리지 않는다" 고 적는다. 그 문장은 위에서 대체된다: 사전 검사는 호출이 도는 동안 여전히 건드리지
> 않고, 그 호출이 에러를 내며, 그것이 버린다. A11 의 나머지는 바뀌지 않는다 — 바이트 레이아웃도, 측정도,
> 위협 모형도.
>
> **검토 기록.** 독립적인 `crypto-reviewer` 검토(2026-10-13, 이 PR)가 여섯 행 콜백, `udf_glue`, `gcm`,
> `nonce`, `key_source`, `spec/envelope.md`, `crypto-safety.md` 를 이 초안에 대해 읽었다. 컴포넌트가
> 가진 상태에 대해 열거한 비밀 집합이 완전하다고 보았고, "비용이 0" 이라는 논증도 타당하다고 보았다 —
> 저장소의 어떤 형태도 에러 뒤에 한 `UDF_INIT` 의 행 콜백에 다시 들어가지 않는다. 제기한 네 가지는 위에서

> 동일성은 소스에서 읽은 것이며 이제 그렇게 표시했고, 중첩 형태에서의 major 차이는 덮지 않고 이름을

> ## 개정 A15 (2026-10-13) — 봉투 안의 키 버전: 키 id 함수의 회전과 dual-read
>
> **상태: 제안됨 (이슈 #34 에서 개정 A13 이 미룬 부분). 이 개정으로 구현되는 것은 없다. 봉투를 바꾸므로,
> `crypto-reviewer` 검토와 사람 검토자 두 명을 거치기 전에는 이것을 근거로 아무것도 구현해서는 안
> 된다.** 버전 바이트 하나와 헤더를 더한다. **인증되는 대상과 결정적 nonce 유도는 바꾸지 않는다** —
> 앞선 초안들은 바꿨으며, 아래 "헤더를 인증하지 않는 이유" 에 그 초안들이 무엇을 제안했는지, 첫 초안이
> 왜 안전하지 않았는지, 왜 더 작은 설계를 (한 검토자의 권고에 따라) 제안하는지 적는다. 이 개정의 어떤
> 초안도 사람의 암호 검토를 받지 않았다.
>
> **이 개정은 A13 이 그런 개정에 필요하다고 한 세 가지 중 하나를 버릴 것을 제안한다.** A13 의 "의도적으로 범위 밖" 은 "인증된
> id, 저장된 값이 가리킬 수 있는 id 의 한정, 행 단위 조회에 대한 답" 을 들었다. 한정과 행 단위 조회는
> 아래에서 답한다(id 는 문장에서 오고, `UDF_INIT` 당 키는 많아야 넷). 인증된 id 는 제공하지 **않는다**:
> 헤더는 인증되지 않으며, 그 이유와 거기서 따라 나오는 것은 "헤더를 인증하지 않는 이유" 에 있다. 이
> 개정의 모든 보안 진술은 작성자와 자동 검토자의 추론이며, 어느 것도 독립적인 암호 검토를 받지 않았다.
>
> A13 은 키를 id 로 이름 붙인 keyring 항목으로 만들었다. 회전은 있던 자리에 그대로 두었다: 컬럼을 새
> 키로 옮기려는 애플리케이션은 어떤 키가 봉인했는지 행마다 알아야 하고, A13 은 행마다 달라지는 키 id 를
> 거부하므로 절반만 회전된 컬럼은 읽는 것조차 키마다 문장 하나가 필요하다. 이 개정은 행이 자신을 봉인한
> 키의 버전을 스스로 말하게 한다.
>
> ```
> gcm_encrypt_krv(plaintext, key_id, key_version [, aad])      -> BLOB
> gcm_encrypt_det_krv(plaintext, key_id, key_version [, aad])  -> BLOB
> gcm_decrypt_krv(ciphertext, key_id [, aad])                  -> VARCHAR (utf8mb4)
> gcm_envelope_key_version(ciphertext)                         -> BIGINT, 봉투에 버전이 없으면 NULL
> ```
>
> ### 봉투
>
> ```
> 0x10 || suite(1) || key_version(4, big-endian) || nonce(12) || ciphertext || tag(16)
> ```
>
> - **새 버전 바이트 하나, `0x10`, "확장 헤더".** `0x02`–`0x07` 이 한 바이트로 말하던 것 — 어떤 cipher,
>   어떤 nonce 모드 — 이 `suite` 바이트로 옮겨 가며, `suite` 는 **같은 여섯 값을 같은 의미로** 쓴다
>   (`0x02` AES-256 랜덤 … `0x07` AES-192 결정적). 맞춰 둘 두 번째 표가 없고, 나중에 수트를 더할 때(이슈
>   #37)는 조합마다 버전 바이트 한 쌍을 새로 할당하는 대신 `0x10` 아래 `suite` 값 하나를 더한다. #37 에
>   대한 제안은 새 수트를 확장 헤더 아래에만 두자는 것이다.
> - **`key_version`** 은 1 부터 4294967295 까지의 부호 없는 32비트 수이며 상위 바이트가 먼저 온다. 0 은
>   버전이 아니다. (`spec/envelope.md` §2 는 다중 바이트 필드에 endianness 가 없다고 한다. 이것이 있는 첫
>   필드이므로 명세가 그렇게 말해야 한다.)
> - 오버헤드는 29바이트가 아니라 34바이트이고, 34 는 잘 형성된 `0x10` 봉투의 최소 길이다.
> - `0x02`–`0x07` 과 `0x01` 은 건드리지 않으며 계속 읽힌다. 이 개정 이전의 빌드는 `0x10` 을 예약된
>   버전으로 거부한다(`spec/envelope.md` §2.6). 명세가 늘 약속해 온 실패다: **0.1.0 은 이 봉투를 읽지
>   못한다.** 그러므로 옛 컴포넌트가 아직 읽어야 할 수 있는 동안에는 컬럼을 `_krv` 로 써서는 안 된다.
>   (헤더가 인증되지 않으므로 헤더 여섯 바이트를 `suite` 바이트 하나로 바꾸면 옛 빌드가 여는 봉투가
>   된다. 그것은 이 값을 읽는 지원되는 방법이 아니며 계속 동작한다는 약속도 없다.)
> - **`0x10` 은 `gcm_decrypt_krv` 만 읽는다.** `gcm_decrypt` 와 `gcm_decrypt_kr` 은 새 빌드에서도
>   `bad_envelope` 로 거부한다: 그것을 여는 키는 헤더가 가리키는데, 그 함수들은 키 하나 또는 항목 하나를
>   받기 때문이다.
> - `suite` 바이트는 오늘의 버전 바이트처럼 키 길이와 일치해야 한다. 불일치는 `bad_key_len` 이다. 알 수
>   없는 `suite`(`0x01` 포함)나 0 인 `key_version` 은 `bad_envelope` 다.
>
> ### 결정
>
> - **`key_id` 의 버전 N 의 키는 keyring 항목 `key_id` + `.v` + N 이다**(`patient_name.v2`). 호출 계정의
>   것이고, 나머지는 모두 A13 의 규칙이다: 타입 `AES`, 16·24·32바이트, 길이가 수트를 고르고,
>   `gcm.min_key_bytes` 는 암호화에만. N 은 부호도 앞자리 0 도 없는 ASCII 십진수로 쓴다. 이 규약은
>   컴포넌트의 것이며, `SELECT keyring_key_generate('patient_name.v2', 'AES', 32)` 가 버전 하나를 만든다.
> - **`_krv` 의 `key_id` 자체는 `\.v[0-9]+$` 에 맞아서는 안 된다** — `utf8mb4` 바이트 기준, 대소문자
>   구분, 숫자가 무엇이든(`a.v0` 과 `a.v01` 도 거부) — 그리고 1–243바이트다(`.v` 와 최대 열 자리 숫자를
>   더하면 항목 id 가 A13 의 255 가 된다). 이 규칙이 없으면 `_krv(…, 'a.v1')` 의 버전 없는 대체 항목이
>   바로 `a` 의 버전 1 인 항목이 된다: 한 id 의 일반 키가 다른 id 의 버전이 되는 것이다. 그렇게 끝나거나
>   243바이트를 넘는 A13 id 는 `_krv` 와 함께 쓸 수 없다. **항목은 여전히 평범한 keyring 항목이다**:
>   A13 함수들은 `'patient_name.v2'` 로 같은 키에 닿는다 — `gcm_decrypt_kr` 은 그 키로 열고
>   `gcm_encrypt_kr` 은 그 키로 평범한 `0x02`–`0x07` 봉투를 봉인한다. 컴포넌트는 그것을 막지 않으며, 그것은 nonce 재사용이 아니다: 두 계열은
>   똑같이 유도하고 똑같이 인증하므로 같은 키·평문·AAD 는 양쪽에서 같은 nonce·ciphertext·tag 를 낸다.
>   따라서 그런 항목에 대해서는 "키 하나에 AAD 규약 하나"(제약 7)가 두 계열에 걸쳐 적용된다.
> - **암호화는 버전을 지정한다.** "현재 버전" 은 없다: 컴포넌트는 가장 높은 것을 찾으려고 keyring 을
>   열거하지 않으며, 무엇이 현재인지 말하는 설정은 A1 이 철회한 `gcm.key_id` 가 될 것이다. 쓰는 쪽이 어느
>   버전을 쓸지는 애플리케이션의 설정이다. `key_version` 은 이 함수들의 다른 인자처럼 문자열로 받아(`utf8mb4` 로 요청하고 바이트로
>   비교하므로 전각 숫자는 숫자가 아니다) 엄격하게 파싱한다: ASCII 숫자만,
>   부호·공백·앞자리 0 없음, 열 자리 이하, 값은 1 부터 4294967295. 문자열 `'02'`, `' 2'`, `'2.5'`, `'0'`,
>   `'4294967296'` 은 에러이고 NULL 은 NULL 을 준다. 이 규칙은 함수가 받는 문자열에 대한 것이며, 문자열이
>   아닌 인자에 대해 그것이 무엇일지는 서버가 정한다. A13 함수로 8.0.46, 8.4.11, 9.4.0 에서 손으로
>   관찰한 바: 리터럴 `2`, `02`, `2e0`, `0x32` 는 모두 `'2'` 로, `TRUE` 는 `'1'` 로, `2.0` 은 `'2.0'` 으로,
>   `-2` 는 `'-2'` 로 들어온다. 따라서 `TRUE` 는 버전 1 로, `0x32` 는 버전 2 로 받아들여진다 — 해는
>   없지만 알아 둘 일이다. 버전은 평범한 정수나 숫자 문자열로 넘길 것. id 처럼 한
>   `UDF_INIT` 의 모든 행에서 같아야 한다: 암호화 호출 지점 하나는 키 하나를 쓴다.
> - **복호화는 봉투에서 읽는다.** `gcm_decrypt_krv(ciphertext, key_id)` 는 `suite` 와 `key_version` 을
>   행에서 읽는다. 따라서 컬럼에 쓸 수 있는 쪽이 버전을 고른다 — 다만 문장이 지정한 `key_id` 의 버전들
>   가운데서만, 호출 계정 아래에서만. 저장된 값은 다른 키 id 나 다른 계정의 키를 가리킬 수 없다.
> - **A13 의 봉투도 읽지만 legacy 봉투는 읽지 않는다.** 버전이 없는 `0x02`–`0x07` 에 대해
>   `gcm_decrypt_krv` 는 항목 `key_id` 자체 — A13 의 키 — 를 쓴다. 그래서 `gcm_encrypt_kr` 로 쓴 컬럼은
>   `gcm_decrypt_krv` 로 그대로 읽히고, 행 단위로 버전 있는 봉투로 회전할 수 있다. **`0x01` 은
>   `bad_envelope` 로 거부한다**: 인증되지 않는 CBC 이고, 새 함수에는 그것을 유지해 줄 기존 사용처가 없다.
>   받아들이면 컬럼에 쓸 수 있는 쪽이 인증된 값을 인증되지 않은 값으로 바꿔 놓을 수 있다 — 패딩 검사를
>   운으로 통과하는 것(약 256번에 한 번)만이 아니다. CBC 에서는 IV 가 저장된 값의 일부이므로, 같은 키
>   바이트 아래의 CBC 행이 있으면 그 IV 에 어떤 차이를 XOR 할 때 첫 평문 블록에 같은 차이가 확실하게
>   XOR 된다 — 그 블록을 알고 있으면 원하는 값으로. 평문이 열여섯 바이트 이상이면 패딩은 건드려지지
>   않고, 그보다 짧으면 패딩이 그 블록 안에 있어 차이가 패딩을 피할 때만 살아남는다.
>   기존 함수들이 마이그레이션을 위해 안고 있는 다운그레이드이며(A3) 이 함수는 안을 필요가 없다. CBC 컬럼은 먼저 `gcm_decrypt_kr` 로 마이그레이션한다.
> - **keyring 에 남아 있는 모든 키는 계속 받아들여진다.** 읽는 쪽은 항목이 존재하는 어떤 버전이든, 그리고
>   버전 없는 항목 `key_id` 가 있으면 그것도 연다. 따라서 침해 뒤의 회전은 옛 항목을 지우기 전까지 아무것도 보호하지 못하고,
>   그때까지 컬럼에 쓸 수 있는 쪽은 옛 봉투를 되돌려 놓을 수 있다. 이 개정에는 "최소 버전" 인자가 없다.
>   필요한지는 열린 질문이다.
> - **`UDF_INIT` 당 키는 많아야 넷.** A13 은 `UDF_INIT` 당 keyring 읽기 한 번을 허용한다. 절반만 회전된
>   컬럼에 대한 문장은 키가 둘 이상 필요하므로 이것을 작은 표로 넓힌다: 서로 다른 키 넷까지(버전들,
>   그리고 행이 필요로 하면 버전 없는 항목 — 넷 중 하나로 센다). 각각 그것이 필요한 첫 행에서 한 번
>   읽고, A13 이 하나를 보관하듯 보관한다. 수명 규칙은 A13 의 것을 그 전부에 적용한다: 에러를 내는 행은
>   보관한 키 전부를 A11 상태·결과 버퍼와 함께 지우고, `deinit` 도 그렇게 한다. `gcm.strict=OFF` 가
>   NULL 로 바꾸는 `bad_tag` 는 전부를 유지하되, 스케줄된 컨텍스트는 A11 이 cipher 실패 뒤에 요구하는
>   대로 초기화한다. 스케줄된 복호화 컨텍스트(A11)는 여전히 **하나** 다: 앞
>   행과 키가 다른 행은 보관한 키로 다시 스케줄한다 — keyring 읽기는 아니지만, 버전이 번갈아 나오는
>   컬럼에서는 A11 이 없앤 행당 준비 비용이 되돌아온다. A14 의 합치기는 한 번의 락 아래 이름 넷까지가
>   된다. **다섯 번째가 필요한 행은 에러다.** 내보내기가 아니다:
>   내보내면 컬럼에 쓸 수 있는 쪽이 버전을 번갈아 넣어 모든 행이 keyring 읽기를 치르게 할 수 있다. 둘이
>   회전의 정상 상태이고, 넷은 다음 회전과 겹치는 경우의 여유다. 쓸 수 있는 항목을 가리키지 않는 버전은
>   A13 의 *쓸 수 있는 키 없음* 이고 에러는 그 `UDF_INIT` 에서 최종이므로, 지어낸 버전은 읽기 한 번과
>   실패한 문장 하나를 치른다. **그것은 읽기를 깨는 방법이기도 하다**: 항목이 없는 버전을 가진 행
>   하나를 심으면 그것을 스캔하는 모든 문장이 실패하며, `gcm.strict` 가 OFF 여도 마찬가지다 — 오늘의
>   잘못된 봉투와 같은 부류이고 strict 는 그것도 누그러뜨리지 않는다. (그 행의 NULL 이 아니라 에러인
>   이유는 A13 과 같다: 얻을 수 없는 키는 설정 오류이고 `gcm.strict` 의 의미는 하나다.) "다섯 번째 키"
>   에러는 모두 존재하는 버전 다섯 개가 필요하므로, 그만큼의 항목이 아직 keyring 에 남아 있는 곳에서만
>   생긴다. 그 행을
>   찾을 수 있도록 이 두 에러는 **`key_version` 을 메시지에 넣는다**: 그것은 저장된 값에서 읽은 헤더
>   필드이지 keyring 의 사실이 아니다 — `spec/envelope.md` §4 규칙 4 는 메시지에 길이와 버전 바이트를
>   이미 허용하며, 다만 오늘의 메시지는 길이만 담는다. 찾는 방법은
>   `WHERE gcm_envelope_key_version(col) NOT IN (…)` 이다. 정당하게 다섯 버전을 가진 컬럼은 일부를 다시
>   봉인하기 전에는 한 문장으로 스캔할 수 없다.
> - **`gcm_envelope_key_version(ciphertext)`** 는 복호화가 쓰는 것과 같은 코드로 헤더 여섯 바이트를
>   파싱하며 키가 필요 없다: 잘 형성된 확장 헤더 봉투면 그 버전, 잘 형성된 `0x01`–`0x07` 봉투면 NULL, 그
>   밖의 것(최소 길이 미달, 알 수 없는 버전 바이트나 `suite`, 0 인 `key_version`)은 에러다. 결과는
>   loadable function 의 정수 타입인 부호 있는 64비트 `BIGINT` 이며 모든 버전을 담는다. **인증되지
>   않는다.** 어떤 행이 어떤 버전을 *주장하는지* 알려 줄 뿐이며, 재봉인 작업에 필요한 것은 그것이다. 어떤
>   행도 더는 어떤 키에 의존하지 않는다는 것은 증명하지 못한다. 옛 항목을 지우기 전에는 모든 행을 살펴보는
>   것으로는 부족하고 열어 봐야 한다 — tag 검사 — 다시 쓰인 헤더는 행을 이 함수로부터 숨길 수 있기
>   때문이다. **그것도 `gcm.strict = ON` 에서, 또는 NULL 결과를 세면서 열어야 한다**: strict 가 OFF 면
>   헤더가 다른 버전으로 고쳐진 행은 tag 실패가 조용히 NULL 이 되고, 스캔은 에러 없이 끝나며, 운영자는
>   바로 그 행에 필요한 항목을 지우게 된다.
> - **사용량 카운트(A14)는 버전별이며, 이름을 더 빨리 쓴다.** A14 는 이름을 (계정, `key_id`) 로
>   정의한다. 이 함수들에서는 (계정, **항목 id**) 이므로 `patient_name.v2` 는
>   `gcm_key_usage('patient_name.v2')` 로 읽고, 버전마다 행이 따로 생긴다 — 새 버전이 새 이름이니, 각 버전이 새로 생성한 키라면 A14 가 닿을 수
>   있던 것보다 "키별" 에 가깝다. A14 는 계정당 이름을 64개로 제한하고 내보내지 않으므로, 긴 회전
>   이력은 그 상한에 포함되어 세어진다.
> - 그 밖은 모두 A13 의 것이다: 계정 경계, definer 루틴, NULL, 실패 의미, 에러가 인스턴스의 모든 비밀을
>   내놓는 것, id·계정·항목을 메시지에 넣지 않는 것. `_krv` 위의 definer 루틴은 A13 의 오라클에 하나를
>   더한다: 호출자가 어떤 버전이 존재하는지 알게 된다.
>
> ### 헤더를 인증하지 않는 이유
>
> **결정: 헤더 여섯 바이트는 associated data 에 들어가지 않고, 결정적 nonce 는 지금과 똑같이
> 유도한다** — 라벨 하나, `HMAC-SHA256(nonce_key, plaintext)[:12]`, associated data 는 호출자의 AAD
> 뿐이며, `spec/envelope.md` §3 의 "AAD 는 nonce 의 입력이 아니다" 도 그대로다. 헤더는 `0x02`–`0x07` 의
> 버전 바이트가 이미 그렇듯 인증되지 않는다. 헤더 뒤의 `0x10` 봉투 바이트는 같은 키·평문·AAD 가 만드는
> `0x02`–`0x07` 봉투의 바이트와 같다.
>
> - **그래서 정확히 무엇이 열려 있는가.** 컬럼에 쓸 수 있는 쪽은 헤더를 고치거나 `0x10` 봉투를
>   `0x02`–`0x07` 봉투로 다시 싸고 되돌릴 수 있다. **평문은 위조되지도 드러나지도 않는다**(작성자와 자동 검토자의 추론이며 독립
>   검토를 받지 않았다). 고친 헤더가
>   가리키는 항목이 *다른* 키 바이트를 갖고 있으면 여느 틀린 키처럼 tag 가 실패하고, *같은* 키 바이트를
>   갖고 있으면 — 한 키를 두 버전 아래, 또는 `id` 와 `id.v1` 로 저장한 경우 — 값은 원래 담고 있던
>   평문으로 열린다. 헤더를 고쳐서 할 수 있는 것:
>   1. `gcm_envelope_key_version` 에 **버전을 잘못 보고하게 한다.** 이 함수는 어떤 설계에서도 인증되지
>      않으며, 위의 규칙 — 항목을 지우기 전에 모든 행을 열어 볼 것 — 은 그것이 속을 수 있다고 전제한다.
>   2. `suite` 의 **랜덤/결정적 표시를 뒤집는다.** 복호화는 그 표시를 무시한다. 오늘 `0x02` 와 `0x03` 의
>      차이를 무시하는 것과 똑같다.
>   3. **한 값에 모두 열리는 저장 형태를 여러 개 준다** — 같은 바이트의 다른 버전, 반대 표시, 버전 없는
>      형태. 그래서 `UNIQUE` 인덱스와 ciphertext 동등성은 컬럼에 쓸 수 없는 쪽에 대해서만 성립한다:
>      결정적 행을 복사해 헤더를 고친 것은 인덱스가 보지 못하는 중복이고 조회가 찾지 못하는 행이다.
>      이것은 `0x02`/`0x03` 에서도 이미 그렇고, 헤더는 그 방법을 늘린다.
>   4. **문장을 실패시킨다**: 다른 키 길이의 `suite` 는 `gcm.strict` 와 무관하게 `bad_key_len` 이다.
>
>   그리고 결과를 볼 수 있는 쓰는 쪽은 시도해 봄으로써 두 항목이 같은 키 바이트를 갖는지(값이 열리거나
>   tag 가 실패한다)와 각 버전의 키 길이를 알게 된다 — 위에서 서술한 오라클에 더해지는 것이다.
> - **재생(replay)을 막는 것은 오늘처럼 호출자의 AAD 다.** 봉투는 같은 키 바이트로 봉인된 다른 행이나
>   다른 컬럼에 복사할 수 있고 거기서 열린다. 값을 그 행이나 컬럼에 묶는 것이 호출자 AAD 의 용도다 —
>   랜덤 모드에서. 제약 7 은 결정적 값에 행마다 다른 AAD 를 금지한다. 이 개정은 그것을 바꾸지 않는다.
> - **새로운 (키, nonce) 재사용은 생기지 않는다**(역시 같은 추론이며 독립 검토를 받지 않았다). 여기서
>   "키" 는 키 *바이트* 를 뜻한다. 같은 바이트
>   아래 같은 평문은 같은 nonce 를 내고, AAD 가 같으면 같은 ciphertext 와 tag 를 낸다: 몇 개의 헤더 아래
>   저장되든 하나의 메시지다. 평문이 다르면 nonce 가 다르다 — `spec/envelope.md` §3 이 이미 받아들인
>   96비트 절단의 범위 안에서. 호출자의 의무는 기존 것이며, 그 범위는 분명히 말해야 한다: **제약 7 과
>   사용 예산은 같은 키 바이트를 가진 모든 버전·id·계열에 걸친다.** A13 키를 `id.v1` 로 다시 저장하고
>   그와 함께 새 AAD 규약을 쓰면 제약 7 을 어긴다. 각 버전은 독립적으로 생성한 키여야 하며(SHOULD),
>   그러면 위의 같은 바이트 경우가 모두 사라진다.
> - **앞선 초안들이 한 것.** 첫 초안은 헤더를 associated data 에 넣고 nonce 는 그대로 두었다. 그것은
>   안전하지 않다: 같은 키 바이트가 두 버전 아래 있으면 같은 평문이 같은 키와 nonce 에 *다른*
>   associated data 로 봉인되어 §3 이 금지하는 쌍이 되며, `crypto-reviewer` 가 차단했다. 둘째 초안은
>   헤더를 두 번째 유도 라벨 아래 nonce 에도 해시해 넣었다. 그러면 그 재사용이 사라진다. 그 초안은
>   HMAC-SHA256 이 PRF 라는 가정 아래 자동 `crypto-reviewer` 를 지적 사항과 함께 통과했을 뿐, 사람이나
>   독립적인 검토는 받지 않았다. 그것을 제안하지 않는 이유는 한 검토자가 든 세 가지다.
>   - 그것이 막는 것은 두 항목이 같은 키 바이트를 가진 곳에서만 존재하고, 거기서도 위에 나열한 편집을
>     막을 뿐이며 그 어느 것도 평문을 위조하거나 드러내지 않는다.
>   - associated data 를 바꾸고, 두 번째 라벨을 더하고, 모든 수트에 새 벡터가 필요하고, A12 의 수트 간
>     연결을 바꾸며, 그 자체의 혼동(호출자 AAD 가 헤더 바이트로 시작하는 A13 봉투)을 남긴다 — 독립적인
>     암호 검토를 받지 못한 부분에서 표면이 더 넓어진다.
>   - 어느 형태든 나중에 버전 바이트를 하나 더해 추가할 수 있다. 그러므로 선택은 독립 검토 이전에 어느
>     쪽에 먼저 묶일 것인가이며, cipher 코드를 그대로 두는 쪽을 고른다.
> - **독립 검토가 헤더 바인딩을 요구하면** 버전 바이트를 하나 더 — `0x11`, "확장 헤더, 인증됨" — 더해
>   추가한다. 헤더를 associated data 에 넣고 *동시에* 두 번째 라벨 아래 결정적 nonce 에 해시해 넣는
>   형태다. 한쪽만 하는 것이 안전하지 않았던 첫 초안이다. `0x10` 봉투는 계속 읽히며, 다시 봉인하기
>   전까지는 위에 나열한 방식으로 계속 편집 가능하다.
> - 결정적 값은 저장된 바이트로는 한 키, 한 수트, **한 버전**, 한 봉투 계열 안에서만 다른 값과 같다.
>   헤더가 저장된 값의 일부이기 때문이다. 헤더 뒤의 바이트는 키 바이트·평문·AAD 가 같으면 언제나 같다 — 그래서
>   같은 평문은 키 바이트를 공유하거나 키가 서로의 0 확장인 버전과 계열을 넘어 여전히 연결 가능하다.
>   유도가 바뀌지 않으므로 A12 의 관찰이 그대로 넘어온다: 키와 그 0 확장은 nonce 키 하나를 유도하며,
>   수트 간에서처럼 버전·id·계열 간에서도 그렇다. "16바이트 키를 32로 채워 버전 2 라고 부르기" 는 A12 와
>   제약 11 이 금지하는, 한 키를 다른 길이로 바꿔 쓰는 것이다.
>
> ### 그러면 회전은 이렇게 된다
>
> ```sql
> -- 0. 컬럼을 읽는 모든 쪽이 이미 gcm_decrypt_krv 를 호출한다 (A13 행도 읽는다)
> SELECT keyring_key_generate('patient_name.v2', 'AES', 32);            -- 1. 새 버전
> -- 1b. 2단계 전에, 컬럼을 읽는 모든 서버의 keyring 에 같은 id 와 계정으로 '같은' 키 바이트가 있어야
> --     한다 (제약 14). 서버마다 다시 생성하면 한 이름 아래 다른 바이트가 된다.
> -- 2. 쓰는 쪽이 버전 2 로 바꾼다. 읽는 쪽은 둘 다 처리한다:
> SELECT id FROM patients WHERE gcm_decrypt_krv(name_enc, 'patient_name') LIKE '%길%';
> -- 3. 나머지를 배치로 다시 봉인한다. 반드시 gcm.strict = ON 에서. 먼저 이 블록 아래의 경고를 모두
> --    읽을 것: 중첩 호출은 8.0/8.4 에서 검증된 형태가 아니고(A7), strict OFF 는 행을 잃는다.
> UPDATE patients
>    SET name_enc = gcm_encrypt_krv(gcm_decrypt_krv(name_enc, 'patient_name'), 'patient_name', 2)
>  WHERE name_enc IS NOT NULL
>    AND (gcm_envelope_key_version(name_enc) IS NULL OR gcm_envelope_key_version(name_enc) < 2)
>    AND gcm_decrypt_krv(name_enc, 'patient_name') IS NOT NULL    -- NULL 을 되쓰지 않는다
>  LIMIT 1000;
> ```
>
> **3단계는 `gcm.strict = OFF` 에서, 그 마지막 조건 없이 실행하면 데이터를 파괴한다** — 그리고 strict 와
> 별개로, 중첩 호출이 A7 이 망가뜨리는 형태 중 하나로 드러나면 역시 그렇다(아래). tag 가 실패하는 행 — 손상됐거나,
> 헤더가 다른 키 바이트를 가진 버전으로 고쳐진 행 — 은 NULL 로 복호화되고, NULL 을 봉인하면 NULL 이며,
> `UPDATE` 는 원래 버전으로는 여전히 열 수 있었을 ciphertext 위에 NULL 을 쓴다. 그러면
> `name_enc IS NOT NULL` 이 그 행을 이후 모든 배치에서 숨긴다. 기본값인 `gcm.strict = ON` 에서는 같은
> 행이 에러가 되어 배치가 멈추며, 재봉인이 원하는 동작이 그것이다. **재봉인은 `gcm.strict = ON` 에서만
> 할 것.** 그러나 그 설정은 MySQL 9.0 이전에는 GLOBAL 전용이고(A5) 문장마다 읽으므로, 확인하고 나서
> 실행하는 것은 그 설정을 바꾸는 쪽과의 경쟁이다 — 그리고 그것을 바꾸기 가장 쉬운 순간이 바로 배치가
> 실패하는 행에서 멈췄을 때다. 에러는 어느 행인지 말해 주지 않으므로 누군가 strict 를 끄고 `… IS NULL` 로
> 찾으려 한다. 그래서 마지막 조건을 둔다. **그 조건이 하는 일은 NULL 이 쓰이지 않게 하는 것이지 작업을
> 완결시키는 것이 아니다**: strict 가 ON 이면 tag 가 실패하는 행은 여전히 에러이고 배치가 멈춘다. OFF 면
> 그 행은 건너뛰어지고 이후 모든 배치에서도 다시 건너뛰어져, 옛 버전인 채로 남는다. 항목이 없는 버전을
> 가리키는 행은 어느 설정에서든 에러다. 회전이 끝났다고 하기 전에 **작업이 남긴 행을 셀 것**, 그리고
> **실패하는 행을 찾으려고 strict 를 끄기 전에 작업을 멈출 것.** MySQL 9.0 이상에서는 경쟁 자체를 없앨 수
> 있다: 작업을 실행하는 세션에서 `SET SESSION gcm.strict = ON`.
>
> 그 조건에는 비용이 있다: 문장에 `gcm_decrypt_krv` 인스턴스가 둘이 되므로 행마다 복호화가 두 번
> 일어나고, keyring 은 인스턴스마다 한 번 읽히며, tag 실패는 A14 에서 `WHERE` 쪽 인스턴스가 센다.
>
> **이 문장은 스케치이지, 아직 존재하지 않는 이 함수들에 대해 검증된 방법이 아니다.** 그 형태에 대해
> 알려진 것은 두 가지다.
>
> - 한 loadable function 의 결과를 다른 함수의 평문 인자로 넘긴다. 개정 A7 은 MySQL 8.0 과 8.4 가
>   loadable function 에 일부 *계산된* 문자열 인자를 낡은 모습으로 넘긴다는 것을 발견했다. 이 형태에
>   대해서는, 이미 존재하는 A13 함수로 — `gcm_encrypt_kr(gcm_decrypt_kr(c, id), id)` 를
>   `INSERT … SELECT` 와 `UPDATE` 에서, 두 행 순서 모두로, 빈 문자열을 포함해 길이가 크게 다른 여덟
>   행에 대해 — 8.0.46, 8.4.11, 9.4.0(고정된 이미지의 서버. 8.0 이미지는 8.0.46 을 실행하고 컴포넌트는 8.0.43
>   트리로 빌드한다)에서 모든 행이 온전히 돌아왔다. 세 서버에서 손으로 실행한 관찰 한
>   번이고 커밋된 테스트가 뒷받침하지 않으며, 모든 형태에 대한 보장이 아니다. 이 형태에서 `utf8mb4`
>   결과를 거쳐 `utf8mb4` 인자로 넘어가는 이진(UTF-8 이 아닌) 평문은 시도하지 않았다. 구현은 `91_server_udf_arg_defect` 가 A7 을 고정하듯 major 별로
>   고정해야 하며, 그때까지 보수적인 형태는 제약 10 의 것이다: 실제 테이블로 복호화하고 거기서 봉인한다.
> - 컬럼에 legacy `0x01` 행이 없다고 가정한다: 찾기 함수는 그런 행에 NULL 을 답하고, 문장은 그것을
>   고르며, `gcm_decrypt_krv` 는 거부한다. 그런 행은 먼저 `gcm_decrypt_kr` 로 마이그레이션한다.
>
> 점(`.`)이 든 키 id 는 같은 세 서버의 `component_keyring_file` 에서 시도했고(`it_dot.v2` 를 생성하고
> A13 함수로 봉인하고 열었다) 다른 id 와 똑같이 동작했다 — 역시 손으로 한 것이고 커밋된 테스트는 없다.
>
> 컴포넌트는 이 단계들 가운데 어느 것도 스스로 하지 않는다. 회전하지 않고, 일정을 잡지 않고, 키가
> 오래됐다고 판단하지 않는다. A8 의 "회전은 운영자가 계획한다" 는 그대로다. 달라지는 것은 그 계획에 더는
> 두 번째 컬럼이나 키마다의 문장이 필요 없다는 점이다.
>
> ### 해결하지 못하는 것
>
> - **결정적 컬럼.** 동등성은 한 키 버전 안에서만 성립한다. 회전 중에 `UNIQUE` 인덱스는 한 값의 두
>   버전을 중복으로 보지 못하고, ciphertext 조인은 다른 버전의 행을 놓친다. 결정적 컬럼은 A8 이 이미
>   말하듯 하나의 마이그레이션으로 회전해야 한다. 봉투의 버전은 그 진행을 보이게 할 뿐이다.
> - **옛 키.** 어떤 행이나 백업이 아직 그 버전을 담고 있는 동안에는 keyring 에서 지울 수 없다.
>   `gcm_envelope_key_version` 은 어떤 행이 그렇게 주장하는지 말해 주고, 증명은 열어 보는 것만이 하며
>   (`gcm.strict = ON` 에서, 또는 NULL 을 세면서), 백업은 운영자가 알아야 한다. 컬럼을 읽는 모든 서버는 만날 수 있는 모든 버전을 자신의 keyring 에
>   갖고 있어야 한다(제약 14).
> - **제약 2.** 평문과 `LIKE` 패턴은 여전히 문장에 있다.
> - **중첩 호출 결함(#43)** 은 다른 함수와 마찬가지로 이 함수들에도 적용되며, 위의 재봉인 문장은 함수를
>   함수 안에 중첩한다 — 리터럴로, #43 이 관찰된 형태가 아니다. #43 은 *안쪽* 호출이 prepared statement 의
>   매개변수를 받는 경우이며, 구현된 `_kr` 함수들이 그 답을 보여 준다:
>   `tests/integration/nested/17_kr_reseal_chain` 는 모든 키 id 를 바인딩한
>   `gcm_decrypt_kr(gcm_encrypt_kr(gcm_decrypt_kr(c, ?), ?), ?)` 를 준비하고, 8.0·8.4·9 에서 왕복하며 그
>   뒤 컴포넌트가 정상적으로 언인스톨된다 — 가장 안쪽 호출의 컬럼 인자가 서버가 그것을 미리 평가하지
>   못하게 한다. 아직 시도하지 않은 것은 `key_version` 을 바인딩한 `gcm_decrypt_krv` 와
>   `gcm_envelope_key_version` 이다: 아직 존재하지 않으며, 그것을 구현하는 PR 이 A7 의 발견을 고정하듯
>   그 형태를 major 별로 고정해야 한다.
>
> ### 검토를 위한 열린 질문
>
> 1. ~~헤더를 인증하고 nonce 에 해시해 넣을 것인가, 둘 다 하지 않을 것인가?~~ **한 검토자의 권고에 따라
>    제안: 둘 다 하지 않는다** — "헤더를 인증하지 않는 이유" 참조. 열려 있는 것은, 독립적인 암호 검토가 이루어질 때
>    그것이 인증된 형태를 `0x11` 로 추가하기를 원하느냐다.
> 2. **`UDF_INIT` 당 키 넷** — 그 수, 그리고 내보내기가 아니라 에러라는 것.
> 3. **`key_version` 네 바이트.** 실제 회전 이력에는 둘이면 충분하고 행마다 두 바이트를 아낀다. 넷은
>    한계를 따져 볼 필요가 없게 해 준다.
> 4. **`.v` 이름 규약.** 끝에 `.v<숫자>` 가 들어간 `key_id` 값은 컴포넌트에는 모호하지 않아도 사람이
>    읽기에는 모호하다.
> 5. **버전 없는 대체가 `gcm_decrypt_krv` 에 속하는지**, 아니면 별도의 명시적 마이그레이션 단계여야
>    하는지. 그리고 옛 키가 항목이 지워지기 전에 받아들여지지 않게 하도록 **읽는 쪽에 최소 버전 인자가
>    필요한지.**
> 6. **이슈 #37**: 새 수트를 확장 헤더 전용으로 할지.
> 7. **`gcm_decrypt_krv` 가 이미 들고 있는 키와 바이트가 같은 두 번째 키를 거부해야 하는지**(많아야 넷
>    사이의 상수 시간 비교). 한 문장 안의 같은 바이트 경우를 모두 없애지만, "버전 1 은 이미 갖고 있던
>    키" 라는 지름길을 시끄럽게 실패시킨다.
>

> ## 개정 A14 (2026-10-12) — 키 id 함수의 키별 사용량 카운트
>
> **상태: 구현되어 머지됨 (이슈 #35; PR #44, #45, #46, 2026-10-13, 해당 PR 들에 기록된 검토 뒤 저장소
> owner 가 머지).** 표는 `src/usage`, 함수는 `src/udf_usage.cc`, 세기와 합치기는 `src/udf_kr.cc` 와
> `src/udf_glue.cc` 에 있다. 고정한 것: 표는
> `tests/unit`(18 케이스, 스레드 포함), 배선은 `tests/adapter/udf_usage_test.cc`, 8.0·8.4·9.4 의
> `tests/integration/63_kr_usage`, 8.4 의 `mysql-test/suite/gcm/t/gcm_kr_usage`, 그리고 keyring 이 없는
> 서버에서도 함수가 답한다는 것. 고정한 것(추가): 이 인스턴스가 새어 나가며 잃는 카운트 — 이슈 #43 —
> 를 `tests/integration/nested/24_nonraising_kr_inner` 가 만든다: 새어 나간 인스턴스의 봉인은 답에
> 없고, 그 인스턴스 자신의 수치는 결코 합쳐지지 않는다.
>
> 개정 A8 과 운영 제약 11·13 은 모든 배포에 키별 사용 예산을 정하라고 하면서 "컴포넌트는 사용량을 세지
> 않는다" 고 한다. 그래서 운영자에게는 예산과 비교할 숫자가 없다. 개정 A13 이 키에 컴포넌트가 공개해도
> 되는 이름을 주었다. 이 개정은 그 이름 아래 카운트를, 그리고 그것을 읽는 함수 하나를 더한다.
>
> ```
> gcm_key_usage(key_id)  -> VARCHAR (utf8mb4), JSON 객체의 텍스트
>   {"random_seals":N,"det_seals":N,"bytes_sealed":N,"tag_failures":N,"since":T,"complete":true}
> ```
>
> **이 숫자가 무엇인가. 보이는 것보다 작다.** 한 행은 *이 서버가 세기 시작한 뒤 키 id 함수로 이 이름
> 아래 수행한 호출* 이다. A8 이 요구하는 예산의 **입력 하나** 이지 예산이 아니며, 문서는 이 숫자가 나오는
> 모든 곳에서 그렇게 말한다. `random_seals` 는 그 바이트의 키 아래 뽑힌 nonce 수의 하한이다.
> `det_seals` 는 어떤 것의 한계도 아니다: **호출** 을 세므로, 반복 조회
> (`WHERE c = gcm_encrypt_det_kr(?, 'id')`)와 최적화 단계에서 접힌 평가는 새 메시지를 봉인하지 않으면서도
> 각각 1 을 더한다. (구현에서 측정: 상수 인자 조회는 8.0, 8.4, 9.4 에서 문장당 3 을 더한다.)
>
> - 예산은 키 **바이트** 에 대한 것이고 카운트는 **이름** 에 대한 것이다. 같은 바이트가 다른 id 나 다른
>   계정 아래 있으면 따로 세어진다. 항목을 지우고 다시 생성한 id 는 옛 이름 아래의 새 키이고, 카운트는
>   이어진다. 컴포넌트는 키 바이트에서 파생한 무언가를 보관하지 않고는 어느 경우도 구분할 수 없다.
>   A11 은 키의 해시를 캐시 키로 쓰는 것조차 기각했고, 이 개정도 키에서 파생한 값을 보관하지 않는다.
> - **키 인자 함수는 전혀 세지 않는다**: 셀 이름이 없다. 두 계열을 함께 쓰는 배포의 카운트는 합계가
>   아니며, `keyring_key_fetch` 는 애플리케이션이 keyring 키를 세지 않는 계열로 옮길 수 있게 한다.
> - 다른 서버는 다른 카운트다. ROW 복제의 replica 는 함수를 호출하지 않으므로 아무것도 세지 않는다.
>   봉투를 복사하거나 복원하는 것은 봉인이 아니다.
> - 서버가 재시작되거나 컴포넌트가 재설치되면 0 부터 다시 시작한다. 읽는 쪽은 **`since` 가
>   바뀌었거나 카운트가 마지막으로 읽은 값보다 작아진 것** 으로 초기화를 알아챈다. `since` 만으로는
>   안 된다: `since` 는 1초 해상도의 벽시계라서 같은 초 안의 재설치는 값을 그대로 두고, 뒤로 맞춰진
>   시계는 더 이른 값을 만들 수 있다. A8 이 운영자에게 두라고 한 원장이 비교할 이전 값을 갖고 있다.
> - 에러를 내지도 않고 de-initialise 되지도 않는 인스턴스가 들고 있던 카운트는 잃는다. 이슈 #43 은 서버가
>   한 형태에서 `deinit` 을 건너뛰는 것을 보여 준다(8.0·8.4·9 에서 측정 — `tests/integration/nested`).
>   에러 행에서의 합치기는 인스턴스 자신이 에러를 낸 경우를 덮고, 나머지를 덮는 것은 없다. 이 손실은
>   이제 고정돼 있다: `24_nonraising_kr_inner` 는 새어 나간 인스턴스의 봉인을 세지 않고, 그 수치는 답에
>   없다.
>
> ### 결정
>
> - **이름은 (호출 계정, 키 id)** — A13 의 네임스페이스인 `priv_user@priv_host` 와 id. `gcm_key_usage` 는
>   호출자 자신의 계정에 대해서만 답한다. A13 이 이미 가진 경계이고 새 권한이 필요 없다. 계정을 넘는
>   조회는 없다. 운영자는 각 계정으로 읽거나, A13 과 같이 id 를 하드코딩한 `SQL SECURITY DEFINER` 루틴으로
>   읽는다 — 그런 루틴은 호출자에게 definer 의 봉인량과 tag 실패를 보여 주며, 그것은 루틴을 쓰는 쪽이
>   결정할 일이다.
> - **keyring 을 읽지 않는다.** 함수는 컴포넌트 자신의 표에서 이름을 찾는다. id 가 키를 가리키는지
>   확인하지 않는다: 카운트가 없는 이름은 0 을 답한다. `key_id` 는 A13 과 같이 검증한다(`utf8mb4` 변환 뒤
>   1–255바이트, NUL 없음). NULL 인자는 NULL 을 준다.
> - **무엇을 세는가.** `random_seals` 와 `det_seals`: 성공한 `gcm_encrypt_kr`, `gcm_encrypt_det_kr`
>   호출. `bytes_sealed`: 그 호출들의 평문 바이트, 봉인된 그대로 — `utf8mb4` 변환 뒤, AAD 제외.
>   `tag_failures`: tag 불일치로 끝난 `gcm_decrypt_kr` 호출(`gcm.strict` ON·OFF 모두) — 위조 시도도 GCM
>   한계에 들어가며(NIST SP 800-38D), 여기서 공격을 보여 줄 수 있는 유일한 숫자다. 잘못된 키 id 로 값을
>   여는 것 같은 정직한 실수도 센다. 성공한 복호화와 실패한 봉인은 세지 않는다. 호출은 반환할 때 세어지며,
>   그 뒤 문장이 실패하거나 트랜잭션이 롤백돼도 마찬가지다. 카운트는 64비트이고 포화한다.
> - **이름이 행을 얻는 때.** `_kr` 함수가 0 이 아닌 카운트를 합칠 때뿐이며, 그것은 keyring 이 그 이름
>   아래 쓸 수 있는 키를 준 뒤에만 가능하다. `gcm_key_usage` 는 행을 만들지 않고, 키 출처 실패, 하한
>   거부, NULL 인자도 만들지 않는다. 그래서 키가 없는 이름에는 행을 만들 수 없다.
> - **`since`** 는 컴포넌트가 세기 시작한 시각(초기화)의 Unix 시간(초)이다. **`complete`** 는 **호출자 계정** 의
>   이름이 한 번이라도 들어가지 못했으면 false 다 — 아래 참조 — 그때는 그 계정의 어떤 사용이 어느 행에도
>   없다. 다른 계정에 대해서는 아무것도 말하지 않는다.
> - **`UDF_INIT` 당 합치기 한 번, 행마다는 없음.** `_kr` 함수는 자신의 `UDF_INIT` 상태에 평범한 정수로
>   세고, 인스턴스가 끝날 때 컴포넌트의 표로 합친다: `deinit` 에서, 그리고 에러를 내는 행에서. 서버가 에러
>   뒤에 `deinit` 을 호출하지 않는 것이 관찰됐기 때문이다(이슈 #43). 합치면 카운터를 0 으로 되돌리므로
>   에러 행 뒤에 정상 `deinit` 이 와도 두 번 세지 않고, 합칠 것이 없는 인스턴스는 락을 잡지 않는다.
>   합치기는 키를 읽을 때 기록한 계정과 id 를 쓰며 호출자를 새로 조회하지 않는다. 그래서 문장 자신의
>   카운트는 실행 중에 보이지 않고, 세어질 봉인과 같은 문장 안의 `gcm_key_usage` 호출은 이전 값을 본다.
>   **예외는 A13 의 것이다:** definer 저장 *함수* 를 통하면 서버가 행마다 `UDF_INIT` 을 만들므로, 그
>   형태는 이미 드는 keyring 읽기에 더해 행마다 표의 락을 한 번 잡는다.
> - **영속화도 임계값도 없다.** 이슈 #35 는 둘 다 제안했다. 컴포넌트가 영속화한 카운트는 복원으로
>   되돌아가며(A8 이 경고한다), 8.0 에서는 서버가 컴포넌트에 종료 알림을 주지 않는다. 영속화 없는 거부
>   임계값은 재시작으로 풀리므로 집행처럼 보이면서 집행이 아니다. 지속되는 원장과 알림은 이 함수를 읽는
>   운영자의 모니터링 시스템 몫이다 — A8 이 이미 원장을 두는 곳이다.
> - **새 서버 서비스 없음**, 봉투 변경 없음, 코어 변경 없음.
>
> ### 컴포넌트의 첫 공유 상태
>
> 지금까지 컴포넌트가 호출 사이에 들고 있던 것은 fetch 한 알고리즘과 시스템 변수 둘뿐이었다. 카운트 표는
> 공유되고 변경 가능하며 컴포넌트 init 부터 deinit 까지 산다. `architecture.md` §3 은 그런 상태에 명시된
> 수명과 동기화를 요구한다.
>
> - **내용:** 이름(계정과 키 id — 비밀이 아니며 이미 `performance_schema.keyring_keys` 에 보인다)과
>   정수. **키 바이트도, 거기서 파생한 것도 없다.**
> - **동기화:** 뮤텍스 하나. `UDF_INIT` 당 합칠 때 한 번, `gcm_key_usage` 호출당 읽을 때 한 번 잡는다.
>   암호화·복호화의 행 경로에서는 잡지 않는다.
> - **상한:** 계정당 이름 최대 64개, 전체 1024개. 들어가지 못한 이름 아래의 사용은 어디에도 귀속되지
>   않고, 그때부터 그 계정의 답에서 `complete` 가 false 가 된다. 계정당 상한은 한 계정이 다른 계정들의
>   집계를 끄지 못하게 한다: 자기 몫을 채운 계정은 자신의 이후 이름을 잃을 뿐 다른 누구의 답도 바꾸지
>   못한다. 표 전체는 계정 열여섯 개가 각자 64개씩 이름을 가지면 찬다 — 공모가 필요 없고, 그만큼 바쁜
>   계정이 있으면 된다. 그때부터 새 이름은 모두 잃는다: 행이 있는 계정은 이름을 잃을 때
>   `complete: false` 를 받고, 행이 하나도 없는 계정은 행 없는 어느 계정이든 사용을 잃은 순간부터
>   `false` 를 받는다. 표에 그것이 어느 계정인지 둘 곳이 없기 때문이다. 이 마지막 경우가 다른 계정의
>   사용이 답에 드러나는 유일한 길이다. 이름은 내보내지 않는다: 내보내면 카운트가 뒤로 간다.
> - **수명:** 어떤 함수도 등록되기 전에 init 에서 만들고, 모든 함수가 해제된 뒤 deinit 에서 해제한다.
>   서버가 끝내 de-initialise 하지 않는 인스턴스(이슈 #43)는 에러를 낸 행에서 이미 합쳤다.
> - **위치:** 서버 의존이 없는 모듈. 그래서 `tests/unit` 이 동시성까지 포함해 다룬다.
>
> ### 그대로인 것
>
> 컴포넌트는 여전히 예산을 갖지 않고, 키를 회전하지 않고, 반복된 nonce 를 탐지하지 않고, AAD 정책을
> 강제하지 않는다(제약 13). 서버·컬럼·애플리케이션에 걸친 키의 **모든** 사용을 합산하라는 A8 의 지시는
> 그대로다. 이 개정은 합산할 숫자 하나를 준다.
>
> **순서.** 키 id 함수(A13) 다음, 같은 마이너 릴리스에. 하위 호환: 함수 하나가 늘 뿐이다.

> ## 개정 A13 (2026-10-12) — 키 id 를 받아 keyring 에서 키를 읽는 함수
>
> **상태: 구현되어 머지됨 (이슈 #34; PR #39, #40, #42, #41, 2026-10-12, 해당 PR 들에 기록된 검토 뒤 저장소
> owner 가 머지).** 키 취급을 바꾸고, 개정 A11 이
> `UDF_INIT` 에 허용한 보관 범위를 넓힌다. 이 개정 끝의 "구현 기록" 에 구현이 고정한 것, 관찰만 한 것,
> 그리고 도중에 만난 서버 결함 하나(이슈 #43)를 적는다.
>
> 개정 A1 은 keyring 설계를 철회하면서 문을 열어 두었다: "keyring 방식은 향후 선택 기능
> (`gcm_encrypt_kr` 류)으로 재검토할 수 있다". 이 개정이 그 재검토다. 함수 세 개를 **추가**하고 기존 세
> 함수는 하나도 바꾸지 않는다. 키를 SQL 인자로 받는 방식이 여전히 기본이며 계속 지원된다.
>
> ```
> gcm_encrypt_kr(plaintext, key_id [, aad])       -> BLOB     랜덤 nonce
> gcm_encrypt_det_kr(plaintext, key_id [, aad])   -> BLOB     결정적
> gcm_decrypt_kr(ciphertext, key_id [, aad])      -> VARCHAR  charset 태깅 (utf8mb4)
> ```
>
> **무엇을 닫고 무엇을 닫지 못하는가.** 운영 제약 2 는 두 부분이다. 이 함수들을 쓰면 *키* 는 암호화·복호화
> 문장의 인자가 아니므로, 그 문장들이 키를 general log, slow log,
> `performance_schema.events_statements_*`, binlog 로 실어 나르지 않는다. `keyring_key_generate` 로 만든
> 키는 어떤 문장에도 나타나지 않는다. **기존 키를 들여올 때는 한 번 나타난다**:
> `keyring_key_store('id', 'AES', <key>)` 는 키가 들어 있는 문장이고, `keyring_key_fetch` 는 그 키를
> 소유한 계정의 어떤 세션에든 키를 돌려준다. *평문* 인자와 `LIKE '%김%'` 패턴은 여전히 문장에 있다.
> 제약 2 는 줄어들 뿐 사라지지 않는다.
>
> ### 결정
>
> - **봉투는 바뀌지 않는다.** 이 함수들은 `spec/envelope.md` 가 정의한 `0x02`–`0x07` 을 그대로 만들고,
>   `gcm_decrypt_kr` 은 `gcm_decrypt` 가 읽는 것을 모두 읽으며 — legacy `0x01` 봉투도 같은 코어 경로로,
>   A3 의 조건 그대로 — 벡터도 바뀌지 않는다. `gcm_encrypt(…, key)` 로 쓴 행은 keyring 이 `id` 아래 같은 키 바이트를
>   갖고 있으면 `gcm_decrypt_kr(…, id)` 로 읽히고, 반대도 성립한다. 이것이 마이그레이션 경로이며 서버
>   테스트로 고정한다.
> - **키 id 는 세 함수 모두에서 명시적 인자다.** 이슈 #34 는 복호화 때 id 를 봉투에서 읽자고 제안했다.
>   그것은 미룬다("의도적으로 범위 밖" 참조): 새 버전 바이트가 필요하고, 컬럼에 쓸 수 있는 쪽이 키를
>   고르게 되며, keyring 조회가 행 단위가 된다.
> - **키는 `keyring_reader_with_status` 로 읽고**, keyring `auth_id` 는 호출자의
>   `priv_user@priv_host` 로 한다. 서버의 범용 keyring 함수(`keyring_udf`)가 쓰는 네임스페이스와 같으므로
>   `SELECT keyring_key_generate('id', 'AES', 32)` 로 만든 키를 이 함수들이 쓸 수 있고, 그 키 바이트는 한
>   번도 문장에 나온 적이 없다. 컴포넌트는 키를 만들거나 저장하거나 지우지 않는다.
> - **권한 경계는 그 네임스페이스다.** MySQL 에는 loadable function 호출에 대한 권한이 없고 keyring
>   reader 서비스도 아무것도 검사하지 않으므로 "누가 호출하는가" 는 경계가 될 수 없다. "어떤 키인가" 가
>   경계다: 계정은 자신의 `priv_user@priv_host` 아래 저장된 키만 쓸 수 있다. 동적 권한은 등록하지
>   않는다. `keyring_udf` 와 다른 점 둘은 의도한 것이며 여기 적어 둔다: 그 함수들은 전역 `EXECUTE` 권한도
>   요구하지만 이 함수들은 요구하지 않는다(자기 키를 읽는 것이 함수의 전부다). 그리고 `user@host`
>   문자열은 계정 이름에 `@` 가 들어 있으면 모호한데, 이는 `keyring_udf` 에서 물려받은 것이고 여기서
>   고치지 않는다 — 고치면 그쪽 키에 닿을 수 없게 된다. `priv_user` 가 빈 계정(익명)은 거부한다: 하나의
>   주체가 아니기 때문이다. 네임스페이스는 *문자열* 이며, 거기서 따라 나오지만 시도해 보지 않은 것들이
>   있다: 지웠다가 같은 이름으로 다시 만든 계정은 옛 계정의 키에 닿고, `RENAME USER` 는 키를 두고
>   떠나며, 프록시에서는 `priv_user` 가 보고하는 이름이 쓰인다. 그리고 다른 계정을 definer 로 루틴을 만들
>   수 있는 쪽(8.0 의 `SET_USER_ID`, 8.2 부터 `SET_ANY_DEFINER`)은 그 계정의 키를 쓸 수 있다. 그 권한은
>   이미 그 계정이 되는 것과 같다.
> - **계정 간 키 공유**는 `SQL SECURITY DEFINER` 저장 루틴으로 한다. 루틴 안에서는 보안 컨텍스트가
>   definer 의 것이므로 definer 의 키가 쓰인다. 뷰는 그렇게 되지 **않는다** — 뷰 안의 함수는 뷰의
>   `SQL SECURITY` 와 무관하게 invoker 로 실행된다. 그런 루틴은 호출자가 고를 수 있게 해 준 것 전부에
>   대한 오라클이 되므로 **키 id 와 AAD 를 하드코딩한다**. 둘 다 매개변수로 받지 않는다. 루틴의 형태도
>   중요하다(아래 관찰): 저장 *함수* 는 호출마다 새 `UDF_INIT` 을 얻으므로 `SELECT f(col) FROM t` 는
>   행마다 keyring 을 읽고, 문장 전체를 담은 저장 *프로시저* 는 한 번 읽는다.
> - **호출이 *쓸 수 있는 키 없음* 으로 실패하면 같은 계정으로 진단한다**: `SELECT CURRENT_USER()` 가
>   네임스페이스를 알려 주고(`app@localhost` 와 `app@%` 는 서로 다르다), `keyring_key_type_fetch('id')` 와
>   `keyring_key_length_fetch('id')` 가 저장된 것을 알려 준다 — 둘 다 전역 `EXECUTE` 권한이 필요하다.
>   컴포넌트의 메시지는 어느 쪽이었는지 말하지 않는다.
> - **키는 keyring 타입 `AES`(대소문자까지 정확히 비교) 이고 16, 24 또는 32바이트여야 한다.** 길이가 수트를 고르며 다른 것은
>   고르지 않는다(A10). `gcm.min_key_bytes` 는 두 암호화 함수에 적용되고 `gcm_decrypt_kr` 에는 적용되지
>   않는다. 기존 함수와 똑같다.
> - **키 id** 는 서버가 인자를 `utf8mb4` 로 변환한 뒤 기준으로 NUL 바이트가 없는 1–255바이트다.
>   `keyring_udf` 가 자신의 문자열 인자에 요청하는 것과 같으므로(세 트리 모두의
>   `plugin/keyring_udf/keyring_udf.cc` 에서 읽음) ASCII 가 아닌 id 도 양쪽에서 같은 항목을 가리킨다. 이
>   상한은 id 를 고정 버퍼에 두기 위해 이 컴포넌트가 정한 것이다.
> - **`UDF_INIT` 당 keyring 읽기는 많아야 한 번, 모든 인자가 NULL 이 아닌 첫 행에서.** `init` 에서가
>   아니다: 아래 관찰 참조. 그 `UDF_INIT` 의 이후 모든 행은 같은 id 바이트를 가져와야 하며, 다른 id 는
>   에러다. 따라서 행마다 달라지는 id(컬럼)는 두 번째로 다른 값에서 거부된다. id 는 비밀이 아니므로
>   `memcmp` 로 비교한다. 키를 읽을 때의 계정도 함께 기록해 매 행 비교한다 — 보안 컨텍스트를 읽는 것은
>   keyring 을 건드리지 않는다 — 그래서 "`UDF_INIT` 안에서 계정은 바뀌지 않는다" 는 가정이 아니라
>   강제된다. 바뀌면 에러다. 한 행에서의 순서는: NULL 검사, id 와 계정 검사, 그런 첫 행이면 keyring
>   읽기, 그다음 코어. 읽기는 항목의 길이를 먼저 묻고, 그것이 수트 길이의 `AES` 항목일 때만 바이트를
>   요청한다. 그래서 이 컴포넌트는 쓰지 않을 항목의 바이트를 요청하지 않는다. 한 문장에 `UDF_INIT` 이 몇 개인지는 컴포넌트가 아니라 서버가 정한다 — 위의 저장
>   함수 참조. id 는 리터럴, 사용자 변수 또는 바인딩 인자로 넘길 것: *계산된* id 는 다른 인자와 마찬가지로
>   A7 의 8.0/8.4 인자 결함을 받는다.
> - **NULL 인자는 SQL NULL** 이며 keyring 에 접근하지 않고 id 도 검사하지 않는다
>   (`spec/envelope.md` §4 규칙 3).
> - **키 출처의 모든 실패는 `gcm.strict` 와 무관하게 에러이고,** `gcm.strict` 의 의미는 하나로 유지된다 —
>   tag 불일치. 실패는 넷이며 그 이상 구분하지 않는다: *keyring 사용 불가*(reader 의 `init` 이나 fetch
>   실패); *쓸 수 있는 키 없음*(이 계정의 이 id 아래 항목이 없거나, 타입이 `AES` 가 아니거나, 길이가
>   16·24·32 가 아님 — **셋 모두 하나의 메시지**. 다른 타입이나 어긋난 길이의 항목이 드러나지 않도록); *잘못된 id*(빈 값 — 서버의 keyring 도 디버그 빌드에서 assert 한다 —
>   255바이트 초과, NUL 바이트, 또는 첫 행과 다름); *호출자 계정 없음*(행 사이에 계정이 바뀐 경우 포함).
>   어떤 메시지에도 키 id, 계정, keyring 항목의 길이나 타입을 넣지 않는다. **이것은 오라클을 좁힐 뿐 닫지
>   않는다**: id 를 매개변수로 받는 definer 루틴은 여전히 호출자에게 어떤 id 가 쓸 수 있는 AES 키를
>   가리키고 그 길이가 얼마인지 알려 준다 — `gcm.min_key_bytes` 거부를 통해, 다른 수트로 꾸민 봉투가
>   끌어내는 키 길이 에러를 통해, *keyring 사용 불가* 와 *쓸 수 있는 키 없음* 의 차이를 통해, 그리고 여기서 아무것도 균등하게 만들지 않는 타이밍을 통해.
>   그런 루틴이 id 를 하드코딩해야 하는 이유다.
> - **에러는 그 `UDF_INIT` 에서 최종이다.** 서버는 함수가 에러를 보고한 뒤에는 그 함수의 행 콜백을 다시
>   부르지 않는다 — `udf_handler::get_arguments` 가 핸들러의 에러 플래그를 보고 돌아간다. 8.0.43,
>   8.4.11, 9.4.0 소스에서 읽음 — 그래서 같은 `UDF_INIT` 에서 키 출처 실패나 다른 어떤 에러 뒤에도 행이
>   이어지지 않는다. 구현은 실패를 기록도 해 두어, 그래도 들어온 호출은 처리하지 않고 거부한다.
> - **`gcm_encrypt_det_kr` 은 `gcm_encrypt_det` 처럼 `const_item` 을 선언한다** — UNIQUE 인덱스의 상수
>   조회가 이 변형의 용도다. 그 결과 keyring 읽기가 문장 최적화 중에, 호출자의 세션에서 호출자의
>   계정으로 일어날 수 있다. 상수 `gcm_encrypt_det_kr` 호출이 든 문장의 `EXPLAIN` 이 keyring 을 읽는지는
>   관찰하지 않았다.
> - **함수는 항상 등록된다.** "선택" 이란 쓰는 것이 선택이라는 뜻이다: keyring 이 없는 서버에서도
>   컴포넌트는 설치되고 기존 함수는 동작하며, `_kr` 호출은 *keyring 사용 불가* 를 낸다. 지금까지 8.4
>   에서만 관찰했다. 8.0 과 9.4 에서도 성립하는지는 구현 PR 의 관문이지 이 개정이 확립한 것이 아니다.
>
> ### 키 복사본: A11 을 어디까지 넓히는가
>
> A11 은 `UDF_INIT` 이 키 복사본을 `gcm_decrypt` 의 스케줄된 컨텍스트 옆이나 `gcm_encrypt_det` 의 nonce
> 키 옆에만 두도록 허용한다. `_kr` 함수에는 하나가 더 필요하다: **keyring 에서 읽은 키(최대 32바이트)와
> 그 키를 읽을 때 쓴 id 와 계정을, 첫 행부터 `deinit` 까지 인스턴스별 상태에 보관한다.** A11 의 복사본과 두 가지가
> 다르고, 둘 다 의도한 것이다.
>
> - 서버가 문장을 위해 이미 들고 있는 인자의 두 번째 복사본이 아니다: 어떤 인자 버퍼에도 *이* 문장의
>   텍스트에도 키는 없다. 컴포넌트의 복사본들 — 이것과, 여기서 나온 A11 의 스케줄된 컨텍스트와 nonce 키
>   — 이 이 문장이 keyring 자체 메모리에 더하는 것이며, 문장 실행 중에 뜬 코어 덤프에 들어 있다.
> - **`gcm.strict=OFF` 가 NULL 로 바꾸는 `bad_tag` 뒤에도 남는다.** A11 은 cipher 연산이 실패할 때마다
>   복사본을 cleanse 하며, 그것은 그대로 일어난다: 스케줄된 컨텍스트와 그 복사본, 캐시된 nonce 키는
>   바뀌지 않은 코어가 A11 대로 폐기한다. 읽어 온 키는 유지한다. 다음 행을 복호화해야 하기 때문이다.
>   **이 함수들 중 하나가 에러를 내는 행 — `gcm.strict=ON` 에서의 `bad_tag` 포함 — 은 그 `UDF_INIT` 이 가진
>   모든 비밀을 즉시 버린다**: 읽어 온 키, 그리고 A11 의 두 상태와 결과 버퍼까지. 코어가 사전 검사에서
>   내는 에러(잘못된 봉투, 수트 불일치)는 스케줄된 컨텍스트와 nonce 키를 그대로 두기 때문이다. `deinit` 을
>   기다리지 않는다: 에러 뒤에는 행이 이어지지 않으므로(위) 잃는 것이 없고, 서버가 에러 뒤에 항상
>   `deinit` 을 호출하는 것도 아니다. NULL 경로에서도
>   키를 버리면, 손상된 행을 심어 둔 쪽이 문장을 멈출 에러도 없이 행마다 keyring 읽기를 유발하게 되고,
>   외부 백엔드에서는 그것이 행마다의 네트워크 호출일 수 있다.
>
> **이것이 무엇과 충돌하는지, 검토자가 찾게 두지 않고 적는다.** A11 은 "전체 키 바이트 외의 것을 키로 하는
> 캐시" 를 기각했고, `crypto-safety.md` 는 그것을 차단 패턴으로 두며, `architecture.md` §5 는 행에서
> 행으로 넘기는 것이 그 밖에 없고 행 콜백이 파일이나 네트워크를 반복해서 건드리지 않는다고 한다. `crypto-safety.md` 는 키 취급을 "키는 UDF
> 인자 `key` 로만 들어온다" 로 시작하고, `AGENTS.md` §9 는 keyring 연동을 범위 밖으로 둔다. 읽어 온
> 키는 *(호출 계정, 키 id)* 를 키로 하는 행 간 값이고, 그 한 번의 읽기는 행 콜백에서 일어난다. 예외의
> 근거: A11 의 규칙은 호출자가 준 키가 행 사이에 바뀔 수 있는데 더 싸게 비교되는 대용물은 그대로일 수
> 있기 때문에 있다. 여기서는 id *가* 호출자의 입력 전부이고, keyring 을 읽기 전에는 비교할 키 바이트가
> 없으며, 다시 읽어서 비교하는 것이 바로 이 설계가 피하는 행 단위 백엔드 호출이다. 캐시 키의 두 부분,
> id 와 계정은 모두 매 행 비교한다. 읽기는 `UDF_INIT` 당 한 번이다. **definer 저장 함수를 통하면 행마다
> 한 번이다.** 서버가 호출마다 별도의 `UDF_INIT` 을 주기 때문이다: 그 한 가지 형태에 대해 §5 를 어기는
> 것을 받아들이며, 아래 운영 제약에 적는다. 이 규칙 문구들은 구현 PR 에서 이 예외만을 명시하도록
> 개정한다.
>
> 조건: 복사본은 한 `UDF_INIT` 에 속하고 스레드나 인스턴스 사이에 공유되지 않는다. `deinit` 에서, 그리고
> 할당 뒤 `init` 이 실패할 때 cleanse 한다. reader 객체는 fetch 직후 해제하고 행 사이에 들고 있지
> 않는다(reader 는 자신의 `init` 부터 `deinit` 까지 서버 전역 keyring 락의 읽기 락을 잡는다). 그 해제가
> 실패하면 결과는 무시한다 — 할 수 있는 것이 없다 — 그리고 이미 읽어 온 키는 그대로 쓴다. fetch
> 버퍼는 모든 경로에서 cleanse 한다. `UDF_INIT` 사이에는 아무것도 캐시하지 않으므로, keyring 에서 지우거나 바꾼
> 키는 그 키를 읽는 다음 `UDF_INIT` 부터 반영된다. **한 문장이 하나의 키만 본다는 보장이 아니다.** 보통은
> 문장의 다음 실행이지만, definer 저장 함수는 행마다 `UDF_INIT` 을 얻는다 — 그래서 그런 문장이 실행되는
> 도중에 바뀐 키는 다음 행부터 적용될 수 있고, 그런 스캔으로 채운 결정적 컬럼은 두 키로 봉인돼 나올 수
> 있다. 캐시하는 백엔드에서
> 답이 얼마나 최신인지는 그 백엔드의 성질이지 이 컴포넌트의 것이 아니다.
>
> 코어(`gcm`, `envelope`, `nonce`)는 바뀌지 않는다. keyring 과 호출자 계정을 읽는 것은 서버 어댑터이고
> (`architecture.md` §1), `_kr` 함수는 기존 세 함수와 같은 코어 진입점을 호출한다.
>
> ### 2026-10-12 일회용 프로브 컴포넌트로 관찰한 것
>
> 서버는 8.0.46, 8.4.11, 9.4.0(고정된 이미지), 프로브는 8.0.43, 8.4.11, 9.4.0 트리로 빌드했다. **한 번
> 관찰했고, 아래 표들은 여전히 관찰일 뿐이다**: 그 일회용 프로브는 커밋하지 않았고, 이 행들을 재현하는
> 커밋된 테스트는 없다. 대신 더 작은 프로브를 `tests/probe` 로 커밋했고, 그것이 고정하는 것은 첫 번째
> 표의 *귀결* — 매개변수에 값이 들어오기 전에 서버가 평가하는 호출과, 그때 de-initialise 되지 않는
> 인스턴스 — 이며 `tests/integration/nested/20`–`22` 에 있다("구현 기록" 참조). 세 표의 모든 행에서 세
> 버전의 출력이 같았다.
>
> | 함수에 넘긴 것 | `init` 이 보는 것 | 행 함수가 보는 것 |
> |---|---|---|
> | 리터럴, 사용자 변수, 저장 프로시저 변수, 리터럴의 `CONCAT`, `(SELECT 'k')` | 값 | 값 |
> | prepared statement 의 `?` (`EXECUTE … USING @v`) | **널 포인터, 길이 0** | 값 |
> | 컬럼 | 널 포인터, 길이 = 컬럼 폭 | 값 |
> | NULL 리터럴 | 널 포인터, 길이 0 | NULL |
>
> 즉 `init` 은 바인딩 인자와 NULL 리터럴을 구분할 수 없고, "id 는 `init` 에서 확정돼야 한다" 고 하면
> 애플리케이션이 보통 보내는 방식을 거부하게 된다. 그래서 위의 첫 행 읽기다.
>
> | 호출자와 문맥 | 컴포넌트가 읽는 `auth_id` | definer `root@%` 소유의 키 |
> |---|---|---|
> | `app@%` 가 직접 호출 | `app@%` | 없음 |
> | `app@%` 가 `root@%` 정의의 `SQL SECURITY DEFINER` 함수를 통해 | `root@%` | 찾음 |
> | `app@%` 가 `SQL SECURITY INVOKER` 함수를 통해 | `app@%` | 없음 |
> | `app@%` 가 `root@%` 정의의 `SQL SECURITY DEFINER` 뷰를 통해 | `app@%` | 없음 |
>
> | 다섯 행을 스캔하며 함수를 호출하는 방식 | 만들어진 `UDF_INIT` |
> |---|---|
> | select list 에서 직접 | 1 |
> | select list 에서 호출한 저장 *함수* 안에서 | 5 — 행마다 하나 |
> | 직접, `SELECT` 전체를 저장 *프로시저* 안에 두고 | 1 |
> | `EXPLAIN` 아래(`WHERE` 비교 안의 함수) | 1, 행 호출 없음 |
>
> `keyring_key_generate`(`AES`, 16·32바이트)와 `keyring_key_store`(`SECRET`, 8바이트)로 만든 키는 길이와
> 타입 그대로 읽혔다. 없는 id 는 reader 의 `init` 이 성공을 반환하고 reader 객체가 널이며, 기본값인
> `log_error_verbosity` 2 에서는 에러 로그에 줄을 남기지 않았다. 3 에서는 keyring 컴포넌트가 data id 와
> auth id 를 담은 note 를 남긴다(`ER_NOTE_KEYRING_COMPONENT_READ_DATA_NOT_FOUND`. 8.4.11 소스에서 읽었고
> 실행하지는 않음) — 즉 상세 에러 로깅에서는 키 id 와 그것을 요청한 계정이 에러 로그에 남는다. 이
> 컴포넌트가 아니라 서버의 keyring 이 남기는 것이다. 전역 `EXECUTE` 권한이 없는 계정은 `keyring_key_generate` 에서 거부됐고 reader 에는
> 여전히 닿았다. keyring 이 로드되지 않은 서버 — **8.4 만** — 에서는 reader 의 `init` 이 실패를 반환했고
> `INSTALL COMPONENT` 는 성공해 있었다. 트리거와 이벤트는 시도하지 않았다.
>
> 8.0.43, 8.4.11, 9.4.0 소스에서 읽은 것(실행하지 않음): 서비스 헤더는 셋이 동일하고 8.0.24 에
> 도입됐다 — 그보다 오래된 8.0 에서는 이 서비스에 대한 `REQUIRES_SERVICE` 가 충족될 수 없어
> `INSTALL COMPONENT` 가 실패할 것이다. 시도하지 않았다: 컴포넌트는 8.0.43 을 상대로 빌드·테스트하며 그
> 이전은 지원하지 않는다. `mysql_thd_security_context`, `mysql_security_context_options`,
> `mysql_current_thread_reader` 의 시그니처도 셋이 같다. 서버는 셋 모두에서 reader 서비스의 기본 구현을
> 등록하며, 그래서 8.0 과 9.4 에서도 요구 서비스 선언이 설치를 막지 않을 것으로 본다. 서버의 reader
> 래퍼는 `init` 에서 전역 keyring 락의 읽기 락을 잡고 `deinit` 까지 유지한다. 백엔드 읽기 실패는 에러 코드
> 없이 `fetch_length` 나 `fetch` 의 실패로 나타나므로, 컴포넌트는 "백엔드 불통" 을 다른 fetch 실패와
> 구분할 수 없고 구분한다고 주장하지도 않는다.
>
> ### 어떤 keyring 인가, 그리고 §3 의 전제
>
> 원래 §3 은 keyring 백엔드를 전제 조건이라 하고 `component_keyring_file` 을 "성립하지 않는다" 고
> 판정했다. 그 판정은 한 가지 목표에 대한 것이었고, 목표는 둘이다.
>
> - **키를 암호화·복호화 문장에서 빼는 것** — keyring 이 데이터를 어디에 저장하는지와 무관하므로 file
>   keyring 으로 충분하다. 이 개정이 주장하는 것은 이것이며, 시도해 본 keyring 은 file keyring 뿐이다.
> - **데이터 디렉터리나 백업 유출을 견디는 것** — 키가 DB 호스트 밖에 있어야 하므로 외부 백엔드가
>   필요하다. 이 목표에 대해서는 §3 이 유효하다: `component_keyring_file` 에서는 키가 데이터 옆에 있고,
>   이 개정은 달리 주장하지 않는다.
>
> Oracle 의 MySQL Community 배포에는 외부 백엔드가 없다: 8.4 매뉴얼은 `component_keyring_file` 을 유일한
> keyring 으로 들고(8.0 이미지에는 legacy `keyring_file` 플러그인도 있다), 외부 백엔드는 MySQL Enterprise
> Edition 에 있다([매뉴얼](https://dev.mysql.com/doc/refman/8.4/en/keyring.html)). 따라서 프로젝트의 CI 는
> file keyring 만 검증할 수 있다. Enterprise 백엔드, 그리고 Percona Server 의 keyring 컴포넌트에서의
> 동작은 **검증되지 않았고** 지원한다고 주장하지 않는다. 캐시하지 않는 백엔드에서는 `UDF_INIT` 당 한 번의
> 읽기가 문장마다의 백엔드 호출이 된다.
>
> ### 추가되는 운영 제약
>
> - keyring 내용은 복제되지 않는다. 컴포넌트가 복제되지 않는 것과 같다(제약 14). `_kr` 함수를 실행하는
>   모든 서버에 같은 id **와 같은 계정** 아래 키가 있어야 한다.
> - `gcm_encrypt_kr` 과 `gcm_encrypt_det_kr` 은 둘 다 ROW binlog 가 필요하다. 기존 `gcm_encrypt_det` 는
>   어디서 재실행되든 같은 바이트를 내지만, replica 에서 재실행되는 `_kr` 함수는 applier 가 실행되는
>   계정으로 replica 의 keyring 에서 id 를 찾게 된다. 검증하지 않았다. 의존하지 말 것.
> - **definer 저장 *함수* 를 통한 공유는 행마다 keyring 읽기 한 번이 든다.** 매번 서버 전역 keyring 읽기
>   락을 잡고, 캐시하지 않는 백엔드에서는 행마다 백엔드 호출이다. 공유 키에 대한
>   `WHERE f(col) LIKE '%길%'` 이 바로 그 형태다. 애플리케이션마다 자기 키를 가진 계정 하나를 쓰는 쪽을
>   택하고, 키를 공유해야 하면 문장 전체를 definer 프로시저에 넣으며, 큰 스캔에 함수 형태를 쓰기 전에
>   측정할 것.
> - 키 사용량 계산(A8, 제약 11–13)은 이 개정으로 바뀌지 않는다: 여기서 컴포넌트는 아무것도 세지 않는다.
>   (이후 개정 A14 가 키 이름별 호출 수를 더한다.) 여러 계정이나
>   서버에서 id 로 닿는 키는 사용 예산에서 하나의 키다.
> - **결정적 키에 대한 모든 조건은 그대로 적용되며, keyring 은 그중 둘을 더 깨기 쉽게 만든다.** A12 는
>   수트와 보안 도메인마다 독립적인 전체 길이 CSPRNG 키를 요구한다: `keyring_key_generate` 는 그런 키를
>   주지만 `keyring_key_store` 는 채워 넣은 키나 엔트로피가 낮은 키를 포함해 받은 것을 그대로 받고,
>   컴포넌트는 구분할 수 없다. 그리고 "키 하나에 AAD 규약 하나"(제약 7)와 "랜덤 모드와 결정적 모드에
>   독립된 키"(A12)는 키 *바이트* 에 대한 것이다: 여러 계정이 루틴으로 닿는 키, 또는
>   `keyring_key_fetch` 가 애플리케이션에 내주고 애플리케이션이 `gcm_encrypt_det` 에 넘기는 키는 그 모두에
>   걸쳐 여전히 AAD 규약 하나를 가진 하나의 키다.
> - keyring 에서 생성한 키는 다른 어디에도 없다. keyring 백업과 옛 데이터를 위한 옛 키 보관은 전과 같이
>   운영자의 책임이고 — 이제 유일한 복사본이 운영자의 것이다.
>

>   keyring 읽기 한 번과 `init` 에서의 읽기 없음, 어떤 경로에서도 reader 가 열린 채 남지 않음, 각 keyring
>   호출의 실패, 길이 호출과 어긋나는 fetch, 실패 종류별 고정(latch), 행 사이의 계정 변경,
>   `gcm.strict=OFF` 가 NULL 로 바꾸는 `bad_tag` 뒤에도 남는 읽어 온 키, 그리고 에러를 내는 행이 그 항목의
>   모든 비밀 — 읽어 온 키, 스케줄된 컨텍스트, 캐시된 nonce 키, 결과 버퍼 — 을 지우는 것(각각 항목의
>   상태에 대해 단언).
> - `mysql-test/suite/gcm/t/gcm_kr`, 8.4 에서 기록: 왕복, `LIKE`, 상호 운용, 그리고 한 문장의 여러 행에
>   걸친 `gcm.strict` ON·OFF. 에러 로그에 예상 밖의 줄이 없다는 MTR 의 검사 아래에서.
>
> **관찰했고 고정하지 않은 것.** 세 번째 표의 `UDF_INIT` 개수와 첫 번째 표의 인자 가시성 행들은 일회용
> 프로브의 카운터에서 나온 것이며 커밋된 테스트로 재현하지 않는다. 대신 커밋된 프로브(`tests/probe`,
> `scripts/build-probe.sh` 로 빌드)가 자신의 `init`·`deinit` 호출을 세어, 첫 번째 표의 귀결 — 중첩
> 호출의 새어 나간 인스턴스 — 을 `tests/integration/nested/20`–`22` 에서 고정한다. 에러 경로의 삭제는
> 고정돼 있다. `deinit` 에서의 삭제는 `free_state` 를 읽어서 확인한 것이다: `deinit` 뒤에는 메모리가
> 해제돼 테스트가 볼 것이 남지 않는다.
>
> **도중에 발견한 서버 결함. 이 함수들에 한정되지 않으며, major 별로 고정했다.** loadable function 이
> **prepared statement 의 재-prepare 가 `EXECUTE` 에서** fix 된 **뒤에** 실패하면 그 함수의 `UDF_INIT` 이 버려진다: deinit 함수가
> 호출되지 않으며 — 문장이 끝날 때도, `DEALLOCATE PREPARE` 때도, 세션이 끝날 때도 — 컴포넌트는 서버를
> 재시작할 때까지 언인스톨되지 않는다. 문장이 이미 fix 한 **모든** 함수가 버려지고, 어느 컴포넌트의
> 함수인지도 가리지 않는다.
>
> 원인은 8.0.43·8.4.11·9.4.0 소스에서 읽었고, 자기완결적 재현과 함께
> `docs/upstream-udf-handler-leak.md` 에 기록했다: `udf_handler::fix_fields` 는 핸들러를
> 유지할 가치가 생기는 순간 자신의 RAII 해제를 미루고, 그러면 `udf_handler::cleanup()` 만이 되돌릴
> 길이 된다 — 그 함수는 문장이 (재)준비되는 동안 일찍 돌아가는데, 실패한 prepare 가 결코 도달하지 않는
> 실행까지 핸들러를 살려 두는 것이 그 이유다.
>
> 방아쇠는 실패한 *재-prepare* 이지 문장의 일반적인 실패가 아니다: 케이스 `25` 의 대조군은 실패
> 컬럼이 앞선 같은 prepared 형태라 재-prepare 가 함수가 fix 되기 전에 실패한다 — `init` 하나와 그
> `deinit` 을 더할 뿐이고 아무것도 남지 않는다. 핸들러를, `udf_handler::cleanup()` 이 일찍 돌아가는
> (재)준비 상태에 두는 것은 prepared statement 다; 일반 문장의 fix 실패는 누수되지 않는 것으로
> 관측됐다. #55 의 원인을 읽기 전까지, 이슈 #43 이 제기된 형태(아래 표)는 중첩과 바인딩 인자가
> 필요하다고 서술돼 있었다.
>
> 가장 먼저 찾은 형태이자 이슈 #43 이 제기된 형태는 다른 함수의 인자이면서 prepared statement 의
> 매개변수를 받는 함수다: 바깥 함수의 `init` 이 매개변수에 값이 들어오기 전에 안쪽 호출을 평가하고,
> 안쪽은 빈 문자열을 보며, `PREPARE … 'SELECT gcm_decrypt(gcm_encrypt(?, ?), ?)'` 는 `EXECUTE` 에서
> 0바이트 키로 실패한다(`_kr` 형태는 *잘못된 id* 로). 중첩도, 바인딩 인자도, 에러를 내는 것도 모두
> **부수적**이다 — 누수에 필요한 것은 실패한 재-prepare 다 — 그리고 첫 검토 뒤에 추가한 세 케이스가 그것을
> 보인다: 같은 select list 의 *형제* 함수, 아무것도 올리지 않은 키 id 인스턴스, 중첩도 매개변수도 없는
> 평범한 `ALTER TABLE` 재-prepare.
>

> #### 서버 원인, 소스에서 읽은 것 (2026-10-13)
>
> 위 결함은 8.0.43·8.4.11·9.4.0 소스에서 진단하고 프로브의 카운트와 대조해 확인했다. 전체 기록 —
> 코드, major 간 차이, 그리고 자기완결적 재현 — 은 `docs/upstream-udf-handler-leak.md` 에
> 있으며, 어디에도 제출하지 않은 초안이다. 한 문단으로: 새어 나간 핸들러는 문장이 이미 fix 한
> 것이고, 해제 경로인 `udf_handler::cleanup()` 이 문장이 (재)준비되는 동안 일찍 돌아간다 — 실패한
> (재)prepare 가 결코 도달하지 않는 실행까지 핸들러를 살려 두는 것이 그 설계 이유다. 가장 먼저 찾은
> 형태이자 이슈 #43 이 제기된 형태는 *바깥* 함수의 `init` 이 실행되는 동안 실패한다:
> `udf_handler::call_init_func` 는 상수 인자를 `args[i]->val_str(...)` 로 평가하는데,
> 그 인자가 그 자체로 loadable function 이면 그것이 안쪽 함수의 행 콜백이다 — 바인딩된 매개변수가
> 아직 값이 없고, 그것이 안쪽이 보는 빈 문자열이다. 안쪽의 `udf_handler` 는 이미 fix 되어 있고
> RAII 해제는 **미뤄져** 있으므로(`udf_fun_guard.defer()` — 핸들러가 실행까지 살아남는 것이
> 의도다), 그 뒤로는 `udf_handler::cleanup()` 만이 그것을 해제할 수 있다. 그 함수는 문장이
> (재)준비되는 동안 의도적으로 일찍 돌아가므로, 핸들러를 위해 살려 둔 실행은 오지 않고 아무것도
> 그것을 해제하지 않는다. 따라서 `find_udf()` 가 잡은 `usage_count` 가 그대로 남고,
> `mysql_udf_registration::udf_unregister` 는 `usage_count == 1`(컴포넌트가 등록한 함수의 유휴
> 상태)에서만 성공하므로 컴포넌트의 deinit 이 실패한다 — 위 표의 ER 3538 `UNINSTALL` 오류가
> 그것이다. 새어 나간 핸들러의 deinit 은 결코 호출되지 않는다. 8.0.43 은 안쪽뿐 아니라 *바깥*
> 함수의 핸들러도 잃는데, 그 버전의 `call_init_func` 는 상수 인자를 평가한 뒤 `thd->is_error()` 를
> 확인하지 않기 때문이다(8.4.11 과 9.4.0 은 확인한다). 프로브의 바깥 init 카운트가 8.0 에서 2,
> 나머지 둘에서 0 인 이유가 그것이다.
>
> 이것은 소스 읽기와 프로브 카운트이지 커밋된 테스트로 고정한 것이 아니다. 어느 쪽에도 수정을
> 시도하지 않았다: 서버는 중단 경로에서 핸들러를 돌려줘야 하고, 그 결과의 컴포넌트 쪽 몫이 개정 A16
> (오지 않는 `deinit` 을 기다리는 대신 에러를 내는 행이 모든 비밀을 버린다)이다.

> ## 개정 A12 (2026-10-07) — 수트 간 nonce 키 연결, 그리고 결정적 AES-128: 검토용 분석
>
> **상태: Codex(AI 설계 검토자)가 2026-10-07 에 결정을 기록함.** 아래 분석과 권고는 제안 작성자의
> 입력이고, 별도의 결정 블록이 이슈 #22 의 검토를 기록한다. 범위가 한정된 AI 평가이며, 사람의 암호
> 감사, 구성의 안전성 증명, 운영 배포 승인이 아니다. 실행 동작은 바뀌지 않는다.
>
> ### 질문 1 — 수트들이 nonce 키 유도를 하나로 공유한다
>
> **정확히 무엇이 드러나는가.** 모든 수트에서 `nonce_key = HMAC-SHA256(key, "mysql-gcm/v1/det-nonce")`
> 이다. HMAC 은 64바이트 블록보다 짧은 키를 0으로 채우므로([RFC 2104 §2](https://www.rfc-editor.org/rfc/rfc2104.html#section-2))
> 키 `K` 와 `K ‖ 0ᵐ` 은 같은 HMAC 키다. 둘 다 수트 길이인 경우 — 16과 24, 16과 32, 24와 32 — 같은
> `nonce_key` 를, 따라서 같은 평문에 대해 같은 결정적 nonce 를 만든다. `tests/unit/nonce_test.cc`
> (`CrossSuiteZeroExtension`)가 세 쌍 모두에 대해 이를 고정한다: 저장된 nonce 는 같고 ciphertext 와
> tag 는 다르다.
>
> 결과: `K` 로 봉인한 컬럼과 `K ‖ 0ᵐ` 으로 봉인한 컬럼을 모두 읽을 수 있는 사람은 *두 컬럼 사이에서*
> 어느 행이 같은 평문을 담는지 볼 수 있다. 결정적 변형이 이미 한 키 안에서 받아들이는 동등성 누출이
> 두 번째 키로 넓어진 것이다. GCM 의 치명적 경우는 **아니다** — AES 키가 다르므로 한 AES 키에서의 nonce 재사용이 아니다 — 직접 드러나는 것은 동등성이며 키 바이트가 아니다. 한 도메인의 알려진 값이나
> 암호화 오라클로 다른 도메인의 일치하는 평문을 식별할 수 있다. 연결 수용에는 이 추론도 포함된다.
>
> **언제 생기는가.** 이 구조적 HMAC 키 동등성은 한 키가 다른 키의 0 확장일 때 생긴다. 우연한 HMAC 또는
> 잘린 nonce 충돌도 가능하다. 독립적이고 균일한 키 한 쌍에서 관계의 확률은 16/24바이트일 때 2⁻¹⁹²,
> 16/32 또는 24/32일 때 2⁻²⁵⁶ 이다. 접두부와 0 꼬리가 모두 일치해야 한다. 2⁻⁶⁴ 는 8바이트 꼬리가
> 0일 확률일 뿐 독립 키 쌍이 일치할 확률이 아니다. A10 의 하한이 막는 실패인 잘림은 이것을
> 만들지 않는다: 32바이트 키를 자르면 *앞부분*이 남고, 그 앞부분의 0 확장은 버린 바이트가 0이 아닌 한
> 다른 키다. 이것을 만드는 것은 짧은 키를 0으로 채워 더 긴 수트에 맞추는 애플리케이션이다 —
> `crypto-safety.md` 가 component 안에서 금지하는 바로 그 folding·padding 이지만, 호출자가 호출 전에
> 하는 것은 component 가 막을 수 없다.
>
> **선택지.**
>
> - **(a) 키 생성 가정을 명시하고 수용.** 수트마다 키를 독립적으로 생성하고, 어떤 키도 다른 키를
>   패딩해서 만들지 않는다. 운영 제약으로 문서화한다. 비용: 코드 없음, 모든 배포가 지키는 것에 기댐.
> - **(b) 유도에서 수트를 분리.** 수트를 입력으로 넣는다 — 수트별 레이블이나 HMAC 메시지의 version
>   바이트. 비용: `spec/envelope.md` 버전 올림과 새 결정적 version 바이트. 복호화 때문이 아니다 — 기존
>   봉투는 nonce 를 저장하므로 레이블이 무엇이 되든 복호화된다 — `spec/envelope.md` §7 이 유도 레이블과
>   version 바이트를 동결하므로 새 유도는 `0x05`·`0x07` 의 재정의가 아니라 새 버전이어야 하고, version
>   바이트가 어떤 유도가 값을 재현하는지 알려 주는 수단이기 때문이다. 그리고 결정적 연속성이 깨진다 — 변경 전후에 봉인한 값이 더는 같게
>   비교되지 않으므로 AES-128·AES-192 아래의 모든 조인·`UNIQUE` 컬럼을 양쪽 함께 재암호화해야 한다.
>   `0x03` 은 지금 레이블을 유지해 잃는 것이 없다.
> - **(c) 암호화에서 꼬리가 0인 키를 거부.** 수트 길이이면서 끝 바이트 때문에 더 짧은 수트 키의 0
>   확장이 되는 키 — 8바이트 0으로 끝나는 24바이트 키, 8바이트나 16바이트 0으로 끝나는 32바이트
>   키 — 를 두 암호화 함수가 전용 오류로 거부한다. `gcm.min_key_bytes` 미만의 키를 거부하는 것과 같은
>   방식이다. 복호화는 영향받지 않으므로 하한과 마찬가지로 이미 쓴 데이터는 계속 읽힌다.
>
>   *보장하는 것.* 정책 **적용 이후에 받아들이는** 키들 사이에는 0 확장 관계가 없으므로, 이후 쓰기 간
>   수트 연결의 이 구조적 원인을 제거한다. 저장된 데이터에 이미 있는 관계는 되돌리지 못한다: 정책 전에
>   `K32 = K16 ‖ 0¹⁶` 로 쓴 행이 있고 그 뒤에도 `K16` 이 받아들여진다면, `K16` 으로 새로 쓴 값은 그 옛 행과
>   같은 nonce 를 만든다 — 이 동등성은 행을 언제 썼는지가 아니라 HMAC 의 키 정규화(RFC 2104 §2)에서
>   나온다. 따라서 기존의 긴 키 데이터는 다른 기존 데이터뿐 아니라 짧은 키로 새로 쓰는 값과도 연결된
>   채로 남는다.
>
>   *이미 그런 키를 쓰는 배포가 치르는 비용.* 봉투 바이트도 유도도 바뀌지 않지만, 그 키 아래의 결정적
>   *작업*이 멈춘다: `WHERE col = gcm_encrypt_det(?, key)`, 그 키로 만드는 모든 새 조인 값과 새 `UNIQUE`
>   삽입이 오류가 된다. 복호화할 수 있다는 것과 결정적 작업을 계속할 수 있다는 것은 다르다. 거부된 키에서
>   옮겨 가는 것은 키 변경이며, 같게 비교되어야 하는 모든 컬럼의 이행이 따른다(A8). 구현 비용: UDF 계층의
>   몇 줄과 행당 최대 16바이트의 상수 시간 검사이며, CSPRNG 가 약 2⁻⁶⁴ 확률로 만드는 키를 거부한다. 새
>   거부 조건과 전용 오류는 동작 계약이므로 구현 PR 에서 `spec/envelope.md` 에 넣는다 — 바이트 배치를
>   건드리지 않고 실패 조건을 더하는 문서 변경으로서 §7 의 규칙을 따른다.
>
> **권고: (c), 그리고 (a) 의 가정도 `docs/ops-constraints.md` 에 적는다.** 모든 배포를 믿지도, 유도를
> 바꾸지도 않고 새 0 확장 쌍이 생기는 것을 막는 유일한 선택지다. 이미 꼬리가 0인 키를 쓰는 배포에는
> 공짜가 아니며(위), 그런 키로 이미 쓴 데이터의 연결을 풀지도 않는다. 검토자에게 남는 것: 기존 긴 키
> 데이터와 그 짧은 형태로 새로 쓰는 값 사이에 남는 연결을 수용할지, 아니면 0 확장 형태가 쓰인 적이 있다고
> 알려진 경우 짧은 형태도 거부해야 할지 — component 는 그것을 알 수 없으므로 운영 규칙이 된다; 그리고
> 검사가 UDF 계층(하한 같은 SQL 정책)에 속하는지 코어(키 유효성 규칙)에 속하는지.
>
> ### 질문 2 — `gcm_encrypt_det` 가 128비트 키를 받아야 하는가
>
> **키 크기와 무관한 것.** 결정적 nonce 는 96비트로 자른 HMAC-SHA256 이므로, 한 키 아래 *서로 다른*
> 두 평문이 같은 nonce 를 받을 확률 — GHASH 인증 키 노출과 그 키 아래 위조를 가능하게 할 수 있는 치명적
> 경우 — 은 수트와 무관하게 서로 다른 평문 n 개에 대해 약 n²/2⁹⁷ 이다. §5.2 의 계산은 그대로다. 이
> 구성은 [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)
> §8.2 의 두 IV 구성 어느 쪽에도 정확히 들어맞지 않는다: 결정적(고정 필드 + 호출 카운터) 구성도 RBG
> 기반 구성도 아니므로, §8 의 유일성 요구는 확률적으로만 성립하고 §8.3 의 호출 한도는 그대로 옮겨지지
> 않는다. 이는 AES-128 만큼 AES-256 에도 해당하며, 어느 쪽이든 키당 사용량 예산이 필요하다(A8).
>
> **키 크기에 달린 것.** 키 자체의 여유다. AES-128 은 고전적으로 128비트 강도를 가지며, 많은 키에 걸친
> 다중 대상 공격과 장기 위협에 대해 AES-256 보다 여유가 적다. AES-128 에 대한 실용적 공격은 알려져 있지
> 않고 주장하지도 않는다. *결정적 변형에서* 이 질문을 날카롭게 만드는 것은 수명이다: 결정적 키는 조인과
> `UNIQUE` 컬럼을 떠받치므로 회전하려면 같게 비교되어야 하는 모든 컬럼을 한꺼번에 재암호화해야 한다.
> 그래서 결정적 키는 랜덤 nonce 키보다 오래 살고 더 많이 봉인하는 경향이 있고, 바로 그 자리에서 작은
> 여유가 가장 문제가 된다.
>
> **선택지.** (i) 지금처럼 `gcm.min_key_bytes` 뒤에서 제공, (ii) 조건을 명시하고 제공, (iii) 16바이트
> 키의 `gcm_encrypt_det` 를 거부(기존 `0x05` 복호화는 영향 없음).
>
> **권고: (ii).** 계속 제공한다 — AES-128 을 강제하는 상대와의 상호운용은 실제 필요이고, 제거해야 할
> 근거는 찾지 못했다 — 다만 다음 조건을 README 와 `docs/ops-constraints.md` 에 적는다: 키당 고정된
> AAD 규칙 하나(A8); 모든 writer 를 합친 키당 사용량 예산과 보존 기간, 둘 다 배포의 보안 검토가
> 정한다 — A8 이 보편적 수치로 제시하는 것을 금하므로 여기서 숫자를 제안하지 않는다; 모든 조인의 양쪽
> 재암호화를 포함하는 회전 계획; 보존 기간이 길거나 정해지지 않은 결정적 컬럼에는 AES-256 을 권장
> 수트로. `gcm.min_key_bytes = 32` 는 기본값으로 유지한다. 그것은 진입 정책이지 사용량 한도가 아니며,
> 위 조건은 그것에 의존하지 않는다.
>

> **Q1 근거와 조건.** 수트 및 별도 보안 도메인마다 CSPRNG 로 전체 길이의 키를 독립 생성한다.
> 다른 키를 패딩·잘라내기 등으로 크기 변경하지 않는다. 쓰기 전에 이 생성 경로를 확인한다. 관련된
> 두 형태를 이미 사용했다면 **양쪽 모두** 새 암호화를 중단하고 모든 JOIN/UNIQUE 의존 컬럼을 독립
> 키로 이관한다. 이전 키는 필요한 읽기에만 보존한다. 백업과 공격자가 가진 사본을 포함해 이미 노출된
> 연결은 되돌릴 수 없다. (c)는 생성 경로나 과거 긴 키/신규 짧은 키 연결을 통제하지 못하면서 결정적
> 조회와 랜덤 쓰기까지 중단시킨다. 이 위협 모델에서는 그 비용을 정당화하지 못한다. 호출자가 선택한
> 관련 키에도 분리가 보장되어야 한다면 (a)는 부족하다. 새 개정에서 새 버전과 이관을 갖춘 (b)를 택한다.
>
> **Q2 근거와 조건.** 128비트 키라는 사실만으로 구성이 무효가 되지는 않으며, 96비트 충돌 추정만으로
> 안전성이 성립하지도 않는다. AES-128 활성화 전에 운영 보안 검토가 동등성·빈도·길이 누출과 선택 평문
> 조회 노출을 승인하고 키마다 다음을 기록해야 한다. Nonce 조건은 모든 수트에 적용된다.
>
> - 모든 쓰기 주체에서 고정된 AAD 바이트열 하나. 랜덤 암호화 및 다른 프로토콜에는 독립 키를 쓴다.
>   그렇지 않다면 모드 간 nonce 충돌을 포함한 별도 분석이 필요하다.
> - 서버·컬럼·조회·애플리케이션 전체를 합친 **수치로 정한 사용 예산과 허용 위험**. 조회/오라클 호출,
>   메시지·AAD 길이와 위조 시도를 포함한다. HMAC 을 PRF 로 가정한 이상적 모델에서 서로 다른 평문
>   바이트열 `d` 개의 충돌 확률 상한은 `d(d-1)/2^97` 이다. 총 암호화 호출 수는 `d` 의 보수적 상한이다.
>   동일 재시도는 새 값을 추가하지 않지만 행 삭제나 DB 복원은 과거 사용을 지우지 않는다. 이 항은
>   위험의 일부이며 보편적 안전 한도나 전체 조합의 증명이 아니다.
> - 유한한 암호화 사용 기간과 별도로 명시한 기밀성/보존 기간(백업 포함). 길거나 종료가 정해지지 않은
>   보존에는 AES-256 을 우선한다. 이것도 nonce 한도를 없애지는 않는다. 이번 검토는 배포별 호출 수나
>   연수를 승인하지 않는다.
> - 예산 또는 암호화 사용 기간이 끝나기 전에 교체한다. 키 노출 의심, AAD 정책 위반, nonce 충돌,
>   사용량/RNG 이력 불확실성이 있으면 즉시 쓰기를 중단한다. 안전한 RNG 상태를 복구하고 독립 교체
>   키를 생성한다. 전환 시 동등성에 의존하는 모든 컬럼과 조회를 함께 이관하고, 이전 키는 필요한
>   이력 읽기에만 둔다. 교체로 이미 안전하지 않은 키 아래 노출된 사본의 기밀성·무결성을 회복할 수 없다.
>
> **근거와 한계.** RFC 2104 §2 가 Q1 을 설명하며 `CrossSuiteZeroExtension` 6개 사례가 재현한다.
> [SP 800-38D §8 및 부록 B](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)는
> nonce·인증 위험의 근거다. 이 합성 IV 는 §8.2 의 두 구성 어느 쪽도 아니며 NIST 적합성을 주장하지 않는다.
> [SP 800-57 Part 1 Rev. 5 §5.3 및 §5.6](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf)는
> 키 사용 기간과 강도 평가의 근거다. 단위 테스트 6,493개와 기존 8.4 통합 smoke 가 통과했다. 이는 동작
> 확인이지 암호 안전성 증명이 아니다. 전체 구성, A11 메모리 보존/타이밍, 운영 설정은 이번 범위 밖이다.
> 이 결정은 함께 갱신하는 운영 문서만 필요하며 새 봉투·SQL 오류·구현 PR 은 필요하지 않다.

> ## 개정 A11 (2026-10-07) — 복호화 컨텍스트와 결정적 nonce 키의 문장 단위 재사용
>
> **상태: 구현되어 머지됨 (PR #23, 2026-10-07, 해당 PR 에 기록된 검토 뒤 저장소 owner 가 머지).**
> 보유되는 두 상태는 `UdfState`(`src/udf_glue.h`)에 있고 `src/gcm.cc` 와 `src/nonce.{h,cc}` 에
> 구현돼 있으며 `src/udf_*.cc` 의 행 콜백이 구동한다. 고정한 것: `tests/unit`(`gcm_test.cc`,
> `det_session_test.cc`)과 `tests/adapter`(`init` 당 상태 하나, 그리고 키 검사); 아래 인용한
> 프로토타입 수치를 대체하는 CI 측정값은 `docs/perf.md` 에 있다(프로토타입은 절감의 모양을 보이려고
> 남긴다). 개정 A16 이 이후에 "사전 검사가 스케줄을 그대로 둔다"는 문장을 대체하고 이 개정 끝의 노출
> 문단을 다시 썼다; 두 곳 모두 이제 A16 을 가리킨다.
>
> §8 은 한 항목을 일부러 미해결로 남겨 두었다: `derive_nonce_key` 는 키에만 의존하는데
> `encrypt_det` 가 행마다 다시 계산하고, 이를 `UDF_INIT` 당 캐시하려면 **키 복사본을 행 사이에
> 보관**해야 하는데, `crypto-safety.md` 는 개정과 보안 검토 없이는 이를 허용하지 않는다. 이 문서가
> 그 개정이며, 같은 키를 행마다 새로 스케줄하는 나머지 한 곳 — `gcm_decrypt` 뒤의 EVP 컨텍스트 —
> 까지 넓힌다.
>
> **결정.** `UDF_INIT` — 한 UDF 항목의 `init` 부터 `deinit` 까지의 수명으로, **한 문장의 한 번의
> 실행**이고 항상 한 스레드가 구동한다 — 는 인스턴스별 상태에 다음을 보관할 수 있다:
>
> (추정이 아니라 8.0.43, 8.4.11, 9.4.0 소스에서 확인한 것이다. `func_init` 은 `udf_handler::fix_fields`
> 에서, `func_deinit` 은 그 실행이 끝날 때 `Item_udf_func::cleanup()` 에서 불린다. UDF 를 참조하는
> prepared statement 는 `EXECUTE` 마다 다시 prepare 되므로(`Prepared_statement::execute_loop`,
> `has_udf()`) 이 쌍은 두 실행에 걸치지 않는다. 스칼라 UDF 의 handler 는 복사 생성되지 않는다 — 그
> 경로는 이 component 가 등록하지 않는 집계 UDF 전용이다 — 그리고 `Item` 은 한 `THD` 의 한 문장
> arena 에 속한다.)
>
> - (a) `gcm_decrypt`: 키 스케줄이 설정된 `EVP_CIPHER_CTX` 하나와, 그 스케줄에 쓰인 키 바이트의
>   복사본(최대 32바이트), 그리고 그것이 속한 수트;
> - (b) `gcm_encrypt_det`: 키 바이트의 복사본(최대 32바이트)과 유도된 32바이트
>   `nonce_key = HMAC-SHA256(key, label)`.
>
> `gcm_encrypt`(랜덤 nonce)에는 캐시를 두지 않는다. 그 EVP 컨텍스트 재사용은 나중에 측정해 볼 수
> 있는 후보이고, 여기서 결정하지 않는다.
>
> **불변 조건.** 구현이 전부 강제하고 단위 테스트가 고정한다:
>
> - 보관한 키 복사본은 들어온 키와 `CRYPTO_memcmp`(상수 시간)로 비교한다. 길이와 수트는 공개
>   정보이므로 비교를 조기 종료해도 되지만, 바이트는 안 된다.
> - 복사본은 바이트나 수트가 다를 때만 교체하고, 교체 전에 이전 복사본을 `OPENSSL_cleanse` 한다.
> - 암호 연산의 **모든** 실패에서 — 어느 단계의 OpenSSL 오류든, 그리고 `bad_tag` — 복사본을 소거하고
>   컨텍스트를 잊는다. 다음 행은 처음부터 시작하며, 방금 오류를 보고한 컨텍스트를 절대 신뢰하지 않는다.
>   컨텍스트를 건드리기 *전에* 돌아가는 사전 검사 — 어느 수트에도 없는 키 길이, 잘못된 봉투 — 는
>   호출이 도는 동안에는 컨텍스트를 건드리지 않는다 (한 행의 잘못된 키 길이는 그 행의 SQL 오류이지,
>   호출 *도중에* 유효한 키 스케줄을 버릴 이유가 아니다). 그리고 그 호출은 에러를 내며, 에러를 내는 행은
>   사본·컨텍스트·nonce 키·결과 버퍼를 한꺼번에 버린다(개정 A16, 위). nonce 키 캐시도 같은 규칙을
>   따른다: HMAC 실패에서는 잊고, 에러를 내는 행이 버린다.
> - `deinit` 은 둘 다 소거한다.
> - 키를 잊을 때 컨텍스트도 함께 reset 한다. `EVP_CIPHER_CTX` 안의 키 스케줄은 키와 동등한 자료이므로,
>   그것을 만든 복사본보다 오래 남지 않는다.
> - 상태는 스레드 사이에서 공유하지 않으며, `UDF_INIT` 하나는 스레드 하나가 구동한다.
> - 기록하거나 받아들이는 바이트는 아무것도 바뀌지 않는다. `spec/envelope.md` 의 바이트 배치는 그대로이고,
>   `nonce_key` 를 "호출마다" 유도한다고 적은 문장 하나만 "한 `UDF_INIT` 안에서 키가 바뀔 때"로 바로잡는다.
>   §7 이 버전 올림 없이 허용하는 수정이다. 기존 벡터 테스트를 재사용 경로로 돌려 출력이 바이트 단위로
>   동일함을 증명한다.
> - 컨텍스트를 다시 만드는 행은 재사용하는 행보다 오래 걸린다. 그 차이가 무엇을 누구에게 드러낼 수
>   있는지는 키가 어디서 오는지에 달려 있다 — 아래 위협 모델을 보라.
>
> **이유.** 시간은 암호 자체가 아니라 행마다 하는 준비에 있다:
>
> - 코어: 16바이트 `open` 이 353 → 170 ns. 그 크기에서는 호출마다 하는 `EVP_CIPHER_CTX_new`,
>   `Init` 두 번(둘째가 키 스케줄), free 가 비용의 전부다.
> - SQL: MySQL 9.4 에서 100,000행에 대한 `gcm_decrypt(col) LIKE`. p95 가 세션 1에서
>   49.6 → 23.2 ms, 세션 8에서 126.4 → 27.2 ms; `AES_DECRYPT` 대비 비율은 1.06 → 0.48, 1.27 → 0.26.
>   세션 8의 이득(행당 약 1 µs)은 직렬 벤치가 예측하는 값(행당 약 180 ns)보다 훨씬 크다. 한 가지
>   가설은 OpenSSL 3 의 호출별 컨텍스트 준비에서 스레드 간 경합이 생긴다는 것이지만, 이 측정은 원인을
>   분리하지 않았으며, 이 개정이 기대는 것은 설명이 아니라 관측된 이득이다.
> - 결정적 변형: 행당 HMAC 한 번이 사라진다. MySQL 8.0 에서 `BENCHMARK()` 로 서버 쪽에서 잰
>   호출당 약 0.75 µs (2.29 → 1.52 µs). 함수 항목 하나가 여러 행에 걸쳐 평가되는 문장 —
>   `INSERT … SELECT`, `UPDATE`, 조인 — 에서만 효과가 있다. 다중 행 `INSERT … VALUES` 는 식마다
>   자기 `UDF_INIT` 을 가지므로 얻는 것이 없다.
> - 부하 러너에 추가한, 같은 행을 세도록 술어를 맞춘 대조 질의 두 개는 스캔과 `gcm_decrypt` 를 함께
>   부르는 스캔 사이의 p95 차이를 노트북에서 `gcm_decrypt(col) LIKE` 질의 p95 의 73~85% 로 보였다
>   (행당 384~391 ns, bare open 약 280 ns 와 나란히). 이는 질의 간 차이이지 구성 요소 시간이 아니며,
>   복호화 호출이 질의의 대부분이라는 것을 말할 뿐 호출 안의 어디에 시간이 드는지는 말하지 않는다.
>
> **노출, 솔직하게.** 바뀌는 것은 키 재료의 *보유 기간*이다. A11 이전에는 키 사본과 유도된 재료가
> 연산 하나, 행 하나 동안만 살았다. 이후에는 UDF 항목이 **마지막으로 쓴 키** — 그 사본, 컨텍스트 안의
> 키 스케줄, 결정적 변형이라면 `nonce_key` — 가 다른 키나 수트로 암호 연산에 도달한 행이 오거나, 암호
> 연산이 실패하거나, 실행이 끝나 항목의 `deinit` 이 불릴 때까지 산다. 암호를 실제로 쓰지 않으면서 이전
> 키를 그대로 두는 행은 두 가지다: NULL 인자, 그리고 열리는 레거시 `0x01` 봉투(실패하는 `0x01` 행은
> 에러를 내고, 에러를 내는 행은 상태 전체를 버린다 — 개정 A16, 위). 그 밖에 암호에 도달하지 않는 행
> — 너무 긴 인자, 잘못된 봉투, 어느 수트에도 없는 키 길이 — 은 에러를 낸다. 실행 *안에서는* 한도가
> 같다 — 다음 행, 또는 에러를 내는 행이 보유를 끝낸다 — 다만 *서버* 가 `deinit` 없이 **그리고 에러 없이**
> 버린 인스턴스는 아예 끝나지 않는다: 들고 있던 것, 이 사본까지 서버가 살아 있는 동안 그대로 남는다. 그것이 이슈 #43 의
> 결함이고 `tests/integration/nested/24_nonraising_kr_inner` 가 고정하며, A11 도 A16 도 행 콜백 안에서는
> 그것을 막을 수 없다. 보유가 얼마나 더하는지는 키가
> 어디서 오느냐에 달려 있고, 두 경우는 같지 않다:
>
> - **호출자가 문장에 상수로 주는 키** — 리터럴, 사용자 변수, 바인딩된 파라미터. README 가 문서화한
>   사용법이다. 서버는 그 키를 실행 내내 인자 버퍼와, §6 이 general/slow 로그에 닿는다고 적어 둔 문장
>   텍스트에 이미 들고 있고, 호출자는 이미 그 키를 안다. A11 은 같은 기간 동안 메모리상 위치를 하나
>   더할 뿐이며, 문장 중간의 코어 덤프에는 어느 쪽이든 키가 들어 있다.
> - **행마다 계산되는 키** — 컬럼에서 읽거나, 식으로 유도하거나, definer 권한으로 도는 view 나 저장
>   루틴이 넘기는 키로, 호출자가 알아서는 안 될 수 있다. 이 경우 서버는 각 행의 키를 그 행을 평가하는
>   동안만 들고 있고, A11 은 가장 최근 키를 그 행을 넘어 실행이 끝날 때까지 보관한다. 즉 UDF 항목당
>   실행당 최대 키 하나의 보유가 늘어나며, 이 개정은 그것을 받아들인다 — 문장으로 한정되고, 모든 출구에서
>   소거되며, 공유되지 않는다 — 그리고 숨기지 않고 이름 붙인다.
>
> **타이밍.** 직전 행과 같은 키를 쓰는 행은 컨텍스트를 다시 만드는 행보다 빠르다(측정한 하드웨어의 코어
> 기준 약 120 ns 대 약 300 ns). 위 첫 번째 경우에는 호출자가 모든 키를 골랐으므로 그 차이는 아무것도
> 알려 주지 않는다. 두 번째 경우에는 원리상, 행 평가 시간을 잴 수 있는 사람에게 *연속한 행이 같은 키를
> 썼는지* 를 — 키 바이트는 결코 아니다 — 알려 주는 신호가 된다. 클라이언트가 보는 것은 문장 전체의
> 소요 시간만이 아니다. 스트리밍 결과(`mysql_use_result`)는 행이 만들어지는 대로
> 전달되므로 각 행의 도착 시점을 관찰할 수 있고, 원리상 행 단위 차이도 관찰할 수 있다. 그 정밀도는
> 실행 계획, 서버와 네트워크의 버퍼링, 드라이버에 따라 달라지며, 적은 행만 돌려주는 필터나 정렬·집계는
> 대부분을 가린다. hit 와 miss 시간을 구별하는 공격은 입증된 바 없고 주장하지도 않는다. 따라서 A11 이
> 받아들이는 위협 모델은 이렇다: **이미 문장을 제출하고 결과가 도착하는 대로 관찰할 수 있는 공격자는
> 평가된 연속 행이 같은 키를 썼는지 알 수 있을지 모르나, 어떤 키인지는 알 수 없다.** 여기에는 공격자가
> 나란히 놓기로 고른 행도 포함된다. 행마다 키가 다른 view 위에서 `WHERE` 와 `ORDER BY` 로 호출자는 어떤
> 두 행이 연속해서 평가될지 정할 수 있고, select 목록의 `SYSDATE(6)` 같은 행 단위 시계나 행 도착 시점은
> 반복 질의로 평균 낼 수 있는 행 단위 소요 시간을 준다. 따라서 신호는 "키가 얼마나 자주 바뀌는가"만이
> 아니라 원리상 **공격자가 고른 두 행이 같은 키를 쓰는가** 이다. 이것은 측정할 수 있을지에 대한
> 가설이지 측정된 결과가 아니다. 그것조차 문제가 되는 배포 — 그룹 구성을 알아서는 안 되는 호출자를 위해 행마다
> 키를 고르는 definer 권한 루틴 — 는 이 개정의 수용에 기대지 말고 그런 키를 행 단위 식 밖에 두어야
> 한다. 이 개정이 함께 이름 붙이는 위험:
>
> - 복사본은 연산이 진행 중일 때만이 아니라, 함수가 평가되는 행과 행 사이의 유휴 시간을 포함해 실행
>   전체 동안 살아 있다.
> - 서버 크래시는 `deinit` 을 건너뛰므로 복사본은 소거되지 않는다. 서버 자신의 인자 버퍼도
>   마찬가지다.
> - 상태를 스레드 사이에서 재사용하는 버그는 정확성 버그이자 동시에 비밀성 버그다. 이 개정이 기대는
>   가정은 단일 스레드 `UDF_INIT` 모델이고, 이 PR 의 어댑터 테스트가 `init` 당 상태 하나가 만들어짐을
>   고정한다.
>
> 선례: `UDF_INIT` 상태는 이미 `gcm.strict` 와 `gcm.min_key_bytes` 스냅샷을 정확히 이 수명 동안
> 들고 있다 (A5, A10). 새로운 점은 보유하는 상태가 비밀이라는 것이다.
>
> **기각한 것.** `UDF_INIT` 보다 오래 사는 캐시나 전역 캐시 — 수명이 무한하고 행 경로에 잠금이
> 필요해진다. 그리고 전체 키 바이트 외의 것으로 색인하는 캐시 — 키의 해시도, 길이도, 인자 버퍼의
> 주소도 안 된다.
>
> **영향:**
>
> | 영역 | 변경 |
> |---|---|
> | `.agents/rules/architecture.md` §3, §5 | `UDF_INIT` 행에 보유 상태 둘이 추가된다; 연산 행은 EVP *연산*과 일시적 비밀을 유지한다; 행 간 재사용은 이 개정이 허용한 것으로 한정된다 |
> | `.agents/rules/crypto-safety.md` | 키 복사 규칙에 이 하나의 예외와 그 불변 조건이 들어간다; `UDF_INIT` 보다 오래 사는 복사본, 전체 키 바이트 외의 것으로 색인하는 캐시는 차단 패턴이다 |
> | `src/gcm.{h,cc}`, `src/nonce.{h,cc}`, `src/udf_*.cc` | `UDF_INIT` 상태에 매달린 재사용 복호화 경로와 nonce 키 캐시 경로 |
> | `tests/unit`, `tests/adapter` | 위 불변 조건; 재사용 경로를 통과하는 벡터; `init` 당 상태 하나 |
> | `docs/perf.md` | 여기 인용한 프로토타입 수치를 대체하는 CI 측정값 |

> ## 개정 A10 (2026-10-06) — AES-128-GCM 과 AES-192-GCM
>
> **상태: 전부 구현됨.** 세 수트가 모두 출시됐다 — `0x02`/`0x03`(AES-256), `0x06`/`0x07`(AES-192),
> `0x04`/`0x05`(AES-128). `gcm.min_key_bytes` 기본값이 32 이므로 AES-256 아래는 전부 옵트인이다.
> `spec/envelope.md` 는 v3 다. NIST CAVP KAT 를 모든 수트에 대해 넣었다 — 2,250개, 수트당 750개,
> 그중 인증 실패가 각각 191 / 190 / 196 개다.
>
> AES-192 추가는 이 개정이 스스로 주장한 "수트 하나는 표 한 줄 + `EVP_CIPHER_fetch` 하나" 를 시험했다.
> 성립했다 — 파일 4개, 17줄. 나머지는 전부 표에서 유도된다: 파싱, version 과 키 길이의 일치 검사, nonce
> 유도, 에러 메시지, 바닥. 공짜가 **아니었던** 것은 테스트와 문서 표면이다. 열 몇 군데가 AES-192 를
> 미구현이라고 단언하고 있었고, 하나씩 의도적으로 뒤집어야 했다.
>
> **여기서 확정한 것과 그 근거** (`0x05` 를 출시한다는 것은 이들을 확정한다는 뜻이므로):
>
> - **AES-128 에도 `gcm_encrypt_det` 를 제공한다.** 결정적 nonce 는 수트와 무관하게 HMAC-SHA256 을
>   96비트로 자른 것이므로 §5.2 의 충돌 경계가 키 길이로 움직이지 않고, 구성이 노출하는 것(동등성·빈도·
>   길이)도 AES-256 이 이미 갖는 것과 같다. 128비트 키가 바꾸는 것은 암호 자체의 여유이고, 그건 운영자가
>   키 길이를 고름으로써 내리는 키 강도 결정이지 변형을 빼는 방식으로 component 가 대신 내릴 결정이
>   아니다. 빼는 것은 일관성도 없다 — 128비트 `gcm_encrypt` 는 여전히 쓸 수 있으므로, 결정성이 필요한
>   배포는 해시 컬럼 같은 *더 나쁜* 답으로 밀려난다.
> - **세 수트가 유도 레이블 하나를 공유하며, 이는 바꾸지 않고 받아들인다.** 초안은 "수트별 레이블이
>   `0x03` 과 `0x05` 를 비교 불가능하게 만든다"고 적었는데 그건 틀렸고 철회한다. 둘은 이미 version
>   바이트부터 달라 같게 비교되지 않으며(`tests/adapter` 와 MTR 케이스가 모두 단언한다), **새** `0x05`
>   에만 별도 레이블을 줘도 기존 `0x03` 봉투의 재현성은 그대로다.
>
>   실제 이유는 더 좁다. 레이블은 암호 키와 HMAC 키를 분리하기 위해 존재하고 그 역할은 모든 수트에서
>   수행되며, `crypto-safety.md` 는 그것이 **한 곳의 상수 하나**여야 한다고 요구한다. 레이블이 둘이면
>   바로 그 파일에 수트별 매핑이 생기는데, 그 대가로 사는 분리는 아직 필요가 입증되지 않았다 — 수트는
>   이미 서로 다른 키로 분리돼 있고, 유일하게 문서화된 예외가 짧은 키와 그 제로 확장이 같은 nonce 키를
>   유도한다는 것(RFC 2104 §2)이다. 그 예외 자체는 공격이 아니며(두 AES 키가 다르고 GCM 의 치명적 경우는
>   한 키 아래의 한 nonce 다), `spec/envelope.md` §2.5 에 "구현이 의존해서는 안 되는 것"으로 적혀 있다.
>
>   보안 검토가 필요하다고 판단하면, 수트별 레이블은 **기존 `0x03` 데이터에 비용이 들지 않는다** — 주장의
>   범위는 거기까지이고, `0x05` 가 출시되는 순간 그 범위가 좁아진다. 그 뒤로는 레이블 변경이 `0x03` 에서와
>   똑같이 `0x05` 데이터의 결정적 재현성을 깨뜨린다: 같은 평문이 저장된 봉투를 재현하지 못하게 되므로 그
>   컬럼의 조인·UNIQUE·정확일치가 맞지 않게 된다. 자체 version 바이트와 이관이 필요하며, 이는
>   `spec/envelope.md` §7 의 일반 규칙이지 예외가 아니다. 이 변경이 싼 구간은 `0x05` 가 아직 누구의
>   데이터에도 없을 때, 즉 지금이다.
>
> **보안 검토에 남기는 것:** 공유 레이블을 장래 스펙 버전에서 수트별로 바꿀 것인지, 그리고
> `gcm.min_key_bytes` 계약 4항 — 그중 셋은 구현이 답했고(암호화 전용, GLOBAL 전용, 32 로 fail closed),
> 넷째인 위반 에러는 `bad_key_len` 과 구분되는 메시지다. 검토는 이 선택들을 확인하는 것이지 발견하는
> 것이 아니다.
>
> §2 와 개정 A1 은 수트를 AES-256-GCM 으로 고정한다. 봉인에 쓰는 cipher 는
> `EVP_CIPHER_fetch("AES-256-GCM")` 하나뿐이고, 키는 정확히 32 바이트를 호출마다 검사한다.
> 이 개정은 **AES-128-GCM 과 AES-192-GCM 을 나란히 추가한다**. AES-256-GCM 은 그대로 기본값이자
> 권장값이고, 작은 키 길이는 상호운용성과 규정 준수를 위한 것이지 속도를 위한 것이 아니다.
>
> **성능 이득은 아직 측정하지 않았다.** AES-128 은 AES-256 보다 라운드 수가 적으므로 암호 연산 자체는
> 싸지만, 그것이 SQL 수준에서 얼마나 남는지에 대한 수치가 이 프로젝트에는 없고 인용해서도 안 된다.
> `docs/perf.md` 의 부하 결과는 GCM 과 CBC 빌트인의 비교이지 AES-128 과 AES-256 의 비교가 아니다.
> 그리고 두 암호 사이의 0.9 근처 비율만으로는 쿼리에서 암호가 차지하는 몫을 알 수 없다 — 비용이 비슷한
> 두 암호는 그 비용이 크든 작든 같은 비율을 내므로, 행 스캔이 지배하는지 여부를 이 수치들은 말해주지 않는다.
>
> 측정은 둘로 나뉘고 어느 쪽도 상대의 질문에 답하지 않는다. **`tests/bench` 는 수트 사이의 코어 차이를
> 측정한다** — 서버 없이 돌므로 SQL 에 대해서는 아무 말도 할 수 없다. **종단 SQL 차이는 부하 시나리오가
> 측정한다.** 작은 수트에 대한 성능 주장은 둘 다 있고 난 뒤에 한다.
>
> **수트는 키 길이로만 선택한다.** 16 바이트 → AES-128-GCM, 24 → AES-192, 32 → AES-256. 새 함수 인자도,
> 새 sysvar 도, 호출 형태의 변경도 없다.
>
> 이것이 핵심 결정이고, 그 트레이드오프는 정확하게 적어야 한다.
>
> 명시적 선택자(`gcm_encrypt(plaintext, key, suite)`)가 개정 A8 이 AAD 에 대해 부과하는 종류의 호출 간
> 일관성 의무를 **만들지는 않는다**. AES 수트별 키 길이는 [FIPS 197](https://csrc.nist.gov/pubs/fips/197/final)
> 로 고정돼 있으므로, component 가 어긋나는 (수트, 키 길이) 조합을 즉시 거부하면 된다 — AES-128 에
> 32바이트 키는 바로 에러이고, 접기도 자르기도 하지 않는다. 수트마다 유효한 키 길이가 정확히 하나이므로
> 한 키를 두 강도로 쓸 수 없고, 운영자에게 새 규칙이 생기지도 않는다.
>
> 길이 추론이 실제로 얻는 것은 **API 단순성**이다. 호출 형태가 바뀌지 않고, 애플리케이션이 틀릴 네 번째
> 인자가 없다. 포기하는 것은 **교차 검증**이다 — 호출자가 의도한 수트와 실제로 전달된 키를 맞춰볼 기회.
> "AES-256 을 의도했는데 키가 16바이트로 잘렸다"는 의도와 키의 불일치이고, 선택자는 그것을 에러로 만든다.
> 길이 추론에는 비교할 의도가 없다. 이는 아래 "대가" 절의 같은 문제를 반대편에서 본 것이고, 두 절은 함께
> 읽어야 한다.
>
> 그럼에도 여기서는 길이 추론을 택한다. 단, 절단 방지를 **버리지 않고 유지한다**는 조건에서다 —
> 기본값 32 의 `gcm.min_key_bytes` 가 기본값을 그대로 둔 배포에 대해 그 방지를 유지한다. 이것이 선택자와
> **동등하지는 않다**. 최소 길이 정책은 서버 전역의 하한선이지 호출마다 호출자의 의도를 검증하는 것이
> 아니고, 한 애플리케이션 때문에 하한선을 낮춰야 하는 혼합 배포에서는 모두가 그 방지를 잃는다 — 아래 계약
> 항목 참조. 완화책을 아예 채택하지 않는다면, 둘 다 없이 출시할 것이 아니라 이 결정을 선택자 쪽으로
> 재검토해야 한다.
>
> **봉투: 새 version 바이트 네 개.** `spec/envelope.md` §7 이 기존 바이트를 동결한다 — 새 형식은 새
> version 바이트이지 기존 것의 재정의가 아니다. 따라서 `0x02`·`0x03` 은 정확히 AES-256-GCM 을 계속 뜻한다.
>
> ```
> 0x02  AES-256-GCM 무작위      (변경 없음)
> 0x03  AES-256-GCM 결정적      (변경 없음)
> 0x04  AES-128-GCM 무작위
> 0x05  AES-128-GCM 결정적
> 0x06  AES-192-GCM 무작위
> 0x07  AES-192-GCM 결정적
> ```
>
> 각각의 배치는 `0x02`·`0x03` 과 동일하다 — `version(1) || nonce(12) || ciphertext || tag(16)`, 즉
> 평문 + 29 바이트. version 바이트와 키 길이만 다르다. `0x02`·`0x03` 에서 시작된 짝수=무작위·홀수=결정적
> 패턴이 이어지지만, 이것은 가독성 속성이지 구현이 의존해도 되는 규칙이 아니다. 대응은 산술이 아니라 표다.
>
> 수트를 봉투에 기록하는 것이 꼭 필요하지는 않다 — 복호화 시 호출자가 주는 키가 이미 수트를 결정한다 —
> 그러나 봉투를 **자기 서술적으로** 유지한다. 개정 A2 가 결정적 nonce 를 재계산하지 않고 저장하기로 한 것과
> 같은 선택이다. 이관·감사·키 교체 도구가 키를 쥐지 않고도 그 행을 무엇이 만들었는지 알 수 있다.
>
> **version 바이트가 기대 키 길이를 정하고, 불일치는 `bad_key_len` 이다.** `0x02` 봉투를 16 바이트 키로
> 복호화하면 태그 실패가 아니라 불일치를 지목하는 에러가 난다. 이것이 얻는 것은 정확히 한 가지 구분이다 —
> **봉투가 요구하는 키 길이와 전달된 키 길이가 어긋난다**는 것을 태그 실패와 구분한다. 이 구분이 없으면
> 같은 상황이 `bad_tag` 로 보고되어 운영자를 데이터 손상 쪽으로 이끈다. 절단 탐지기가 아니다 — 잘린 키가
> 드러나지 않는 경우는 아래 "대가" 절에 있고, version 바이트가 손상돼도 같은 에러가 난다.
>
> **바뀌지 않는 것:**
>
> - 결정적 nonce 유도와 그 레이블. `nonce_key = HMAC-SHA256(key, "mysql-gcm/v1/det-nonce")` 는 모든 키
>   길이에 대해 바이트 그대로 유지되고, 레이블은 `spec/envelope.md` §7 이 동결했다.
>
>   레이블을 바꿔도 기존 데이터의 **복호화는 깨지지 않는다**. 개정 A2 가 봉투에 nonce 를 저장한 이유가
>   바로 복호화가 nonce 를 재계산하지 않게 하려는 것이다. 깨지는 것은 같은 입력을 다시 암호화했을 때
>   기존 암호문이 재현되지 않는다는 것이고, 그것이 결정적 변형의 존재 이유 전부이므로 걸린 것은
>   JOIN·UNIQUE·정확일치의 연속성이다. 레이블은 유지한다 — 이유는 복호화 가능성이 아니라 연속성이다.
>
>   HMAC-SHA256 은 임의 길이 키를 받으므로 새 유도식이 기계적으로 필요하지는 않다. 그렇다고 **키 길이가
>   다르면 도메인이 분리된다는 결론이 따라 나오지는 않는다.**
>   [RFC 2104 §2](https://www.rfc-editor.org/rfc/rfc2104.html#section-2) 는 블록(64바이트)보다 짧은 키를
>   0 으로 패딩하므로, 16바이트 키 `K` 와 32바이트 키 `K ‖ 0¹⁶` 는 **동일한** nonce 키를 유도하고 따라서
>   같은 평문에 같은 nonce 를 만든다. 가정이 아니라 실제로 확인했다. 이 쌍 자체가 GCM nonce 재사용은
>   아니다 — 두 AES 키가 다르고, GCM 의 치명적 경우는 한 키 아래의 한 nonce 다 — 그러나 "길이가 다르면
>   도메인이 분리된다" 는 근거로 쓸 수 없고, 새 수트에 명시적 도메인 분리가 필요한지는 이 개정이 아니라
>   아래 보안 검토가 답할 문제다.
> - 태그 길이 16, nonce 길이 12 — 세 수트 모두.
> - strict 의미론, 실패 코드, AAD 규칙.
> - legacy `0x01` CBC 경로. AES-256-CBC 복호화 전용으로 유지된다 (아래 미해결 항목 참조).
> - 결정적 JOIN·UNIQUE 동작. 암호문은 같은 키에서만 비교 가능하고 키는 길이가 하나뿐이므로, 기존의
>   "같은 키·같은 AAD" 요건이 이미 이를 포함한다. 이 개정으로 새로 생기는 운영 규칙은 없다.
>
> **대가를 그대로 적는다.** 지금은 `key.size != 32` 가 에러이므로, 전송 중에 잘린 키 — 클라이언트 버그,
> 잘못된 환경변수, 잘못 자른 버퍼 — 가 요란하게 실패한다. 이 개정 이후에는 32 바이트 키가 16 바이트로
> 잘린 것이 **유효한 AES-128 키**이고, `gcm_encrypt` 가 그것으로 봉인하고 성공을 보고한다. 의도보다 낮은
> 강도로 암호화되는데 아무도 그렇다고 말해주지 않는다.
>
> **나중에 반드시 발견되는 것도 아니다.** 복호화가 이를 드러내는 것은 누군가 *의도했던* 키로 읽을 때뿐이다.
> 쓰기와 읽기가 모두 같은 16바이트 잘린 키를 쓰면 `0x04` 봉투와 일치하므로 둘 다 무한히 성공한다.
> 불일치는 원래 32바이트 키로 그 행을 처음 읽는 순간에 드러나고, 그 순간은 백업 복구일 수도, 이관일 수도,
> 영영 오지 않을 수도 있다.
>
> 위의 `bad_key_len` 구분은 여전히 둘 가치가 있지만, 그것이 말해주는 바를 정확히 읽어야 한다 — 봉투와
> 전달된 키가 길이에 대해 어긋난다는 진단이다. 키가 잘렸다는 증거는 아니다. version 바이트 손상도 같은
> 신호를 낸다.
>
> 이것이 이 기능의 실제 가격이고, 키 길이가 선택자인 한 설계로 없앨 수 없다. 완화책이 둘 있고 그 선택은
> **여기서 확정하지 않는다**:
>
> 1. sysvar — `gcm.min_key_bytes` (기본 32, 24 나 16 으로 설정 가능) — 작은 수트를 쓸 의도가 없는 배포가
>    서버에서 거부하게 한다. 현재 동작이 기본값으로 유지된다: 아무것도 하지 않은 설치는 변화가 없고,
>    잘린 키는 여전히 요란하게 실패한다. 비용은 sysvar 하나와 개정 A5 의 8.0·8.4 GLOBAL 전용 스코프 문제다.
>
>    채택한다면 그 계약을 먼저 확정해야 하고, 아래는 구현 세부가 아니다:
>
>    - **새 암호화에 적용하고 기존 데이터의 복호화에는 적용하지 않는다.** 그러지 않으면 정책을 16 에서
>      32 로 올린 순간, 재암호화를 위해 읽어야 할 바로 그 행들이 잠긴다.
>    - **관리자 강제 정책인가, 실수 방지 설정인가.** 세션이 마음대로 낮출 수 있다면 후자이고, 전자라고
>      설명해서는 안 된다. 8.0·8.4 에서 GLOBAL 전용이므로 개정 A5 가 이미 답을 제약한다.
>    - **GLOBAL 전용 서버에서 한 애플리케이션 때문에 낮추면 그 서버의 모든 애플리케이션이 절단 보호를
>      잃는다.** 기본값은 기존 배포를 보호하지만, 혼합 배포의 의도를 표현하지는 못한다.
>    - **정책 위반 시의 에러와 설정 조회 실패 시의 동작**을 둘 다 정해야 한다. 후자는 fail closed 가
>      확립된 패턴이다 (개정 A5).
> 2. component 에는 아무것도 두지 않고, 그 기대를 운영 제약으로 문서화한다.
>
> 1번을 권고한다. 이 개정을 기존 배포의 보장을 조용히 약화시키는 것이 아니라 **옵트인**으로 만들기
> 때문이다. 키 정책에 닿는 모든 것에 대해 개정 A8 이 요구하는 대로, 확정 전에 보안 검토가 필요하다.
>
> **의도적으로 범위 밖:** legacy `0x01` 봉투는 AES-256-CBC 로 유지한다. 따라서 지금
> `block_encryption_mode = 'aes-128-cbc'` 로 운영 중인 배포는 여전히 자기 데이터를 dual-read 할 수 없다.
> 이는 실재하는 공백이고 별개의 문제다 — GCM 생성이 아니라 기존 `AES_ENCRYPT` 출력을 읽는 문제다.
> 필요하다면 자체 개정과 자체 version 바이트를 가져야 하고, 여기 묶을 것이 아니라 이관 근거를 보고 결정한다.
>
> **순서.** 0.1.0 태깅 이후 0.2.0 으로 들어갈 계획이었다. *2026-10-10 수정:* 이 개정과 A11, A12 가 구현될
> 때까지 0.1.0 은 태깅되지 않았고, 0.1.0 용으로 준비한 커밋에는 그 뒤 고친 component 결함 두 개가 있다 —
> 8.0 과 8.4 에서 `gcm.strict` 를 동기화 없이 읽던 것, 그리고 init 롤백이 소유하지 않았을 수 있는 cipher
> 핸들을 해제하던 것. 그 커밋을 태깅하면 알려진 결함을 공개하게 되므로, 0.1.0 은 이후 상태에서 자르고
> `0x04`~`0x07` 을 포함한다. 그 전에 공개된 것이 없으므로 이 version 바이트를 거부하는 릴리스된 component
> 는 없다. 추가는 여전히 하위 호환이다 — 모든 `0x02`/`0x03` 봉투가 그대로 복호화되고, 이전 빌드는
> `spec/envelope.md` §2.4 가 요구하는 대로 `0x04`~`0x07` 을 `bad_envelope` 로 거부한다.
>

> ## 개정 A9 (2026-10-02, 확정) — 설치 실패 후 남는 등록과 등록 순서
>
> `INSTALL COMPONENT` 중 `gcm_component_init()` 이 1 을 반환하면, 로더는 롤백하면서
> scope guard 로 scheme 의 `unload` 를 호출하고 그것이 **`dlclose()`** 를 수행한다.
> `dlopen` 에 `RTLD_NODELETE` 가 붙는 것은 **ASan/LSan 빌드뿐**이다
> (`components/libminchassis/dynamic_loader_scheme_file.cc`, 8.4.11 트리에서 확인).
>
> 따라서 롤백에서 해제가 거부된 등록은 **언매핑된 세그먼트**를 가리킨다.
>
> - 해제가 거부된 UDF: `udf_unregister` 는 사용 중인 함수를 **원래 이름 그대로** `udf_hash` 에
>   남긴다 (`sql_udf.cc`). 따라서 이미 resolve 한 세션뿐 아니라 **새 세션이 그 이름을 호출해도**
>   언매핑된 코드로 뛴다. 다만 이름을 알고 호출해야 한다.
> - 해제가 거부된 sysvar: 딕셔너리가 `&g_strict` 를 언매핑 메모리에 두고 있고, **열거만으로**
>   닿는다 — `SHOW VARIABLES`, `performance_schema.global_variables`. 이름을 지목할 필요가 없다.
>
> 즉 차이는 "이미 resolve 했는가" 가 아니라 **지목 대 열거**다. 변수 쪽이 훨씬 도달하기 쉽다.
>
> 결정:
>
> - **component API 로는 고칠 수 없다.** 로더에게 "라이브러리를 매핑된 채 두라" 고 요청하는
>   서비스가 없고, `init` 에서 언로드를 거부할 방법도 없다. 코드로 해결했다고 쓰지 않는다.
> - **등록 순서로 노출을 줄인다.** `gcm.strict` 는 UDF 세 개가 모두 등록된 **뒤에** 등록한다.
>   그러면 실제로 일어날 수 있는 실패(= `udf_register` 가 중간에 실패)의 롤백 시점에는 변수가
>   아직 존재하지 않으므로, 위의 두 번째 경우가 **구조적으로 불가능**해진다. 남는 노출은
>   `sysvar_register()` 자체가 실패하는 경우이고 그때는 UDF 만 되돌린다.
> - 그 대가는 함수가 존재하고 변수가 아직 없는 **짧은 창**이다. 그 창에 들어온 호출은
>   등록되지 않은 변수를 읽어 서비스가 실패하고 `strict_enabled()` 가 `true` 를 돌려준다 —
>   strict **ON**, 즉 fail-closed 방향이다. 창은 `INSTALL COMPONENT` 내부에 있다.
> - 해제가 거부되었을 때 **암호 핸들을 해제하지 않는다.** 이것이 위의 크래시를 막지는 못한다.
>   망가진 설치에 두 번째 결함을 더하지 않는 것, 그리고 `gcm_component_deinit` 과 같은 입장을
>   취하는 것이 목적이다. deinit 에서는 거부된 `UNINSTALL` 이 component 를 로드된 채 두므로
>   같은 추론이 **실제로** 성립한다.
> - **ASan 빌드는 이 결론을 반대로 보이게 한다.** `RTLD_NODELETE` 가 정확히 그때만 붙기
>   때문이다. 이 사안을 샌타이저로 "확인" 하면 틀린 답을 얻는다. `tests/adapter` 의
>   샌타이저가 기본 OFF 인 이유다.
> - **deinit 은 init 의 거울이 아니다.** init 은 변수를 마지막에 등록하지만 deinit 도 변수를
>   마지막에 해제한다 (LIFO 가 아니다). 의도적이다: deinit 은 함수가 사용 중이면 **거부하고
>   되돌려야** 하는데, 변수를 먼저 해제해 두면 거부 시점에 변수가 없는 상태로 component 가 남는다.
>   함수부터 처리하면 거부가 변수에 손대기 전에 일어난다. "대칭이 아니니 맞추자" 는 수정을 하지 않는다.
>   이 순서는 `GivenAFunctionStillInUse_WhenDeinit_ThenTheVariableIsStillRegistered` 와
>   `GivenEverythingUnregisters_WhenDeinit_ThenTheVariableGoesLast` 가 고정한다. 후자는 호출
>   **순서 전체**를 단언한다 — 어떤 호출이 있었는지만 보는 단언은 두 개가 뒤바뀐 것을 보지 못하고,
>   실제로 그 변이가 이 파일의 이전 판을 통과했다.
> - 등록 순서와 롤백 분기는 `tests/adapter/lifecycle_test.cc` 가 스텁 서비스로 고정한다.
>   변이 테스트로 확인한 것: 순서 되돌리기, 조건 없는 자원 해제, `strict_enabled()` 를 fail-open
>   으로 바꾸기, 잠금 없는 `g_strict` 직접 읽기로 되돌리기, `mac_deinit()`·CBC 해제 제거,
>   deinit 의 `was_present` 가드 제거 — 일곱 가지 모두 스위트가 실패한다.

> ## 개정 A8 — 키·nonce 운영 책임과 보안 보장의 범위
>
> component 는 키를 SQL 인자로 받고 nonce 생성·인증 검증을 수행하지만,
> 키별 사용량 집계·자동 키 교체·nonce 중복 탐지·AAD 정책 강제는 구현하지 않는다.
> 배포 전 운영자가 동일 키를 사용하는 모든 서버·컬럼·애플리케이션의 암호화 사용량을
> 합산할 방법과 사용 한도·교체 기준을 정하고 보안 검토를 받아야 한다.
> 무작위/결정적 모드의 충돌 분석과 메시지 길이·위조 시도 등을 함께 고려한다.
> 이 프로젝트는 모든 배포에 적용할 수 있는 안전한 키당 사용량을 확정하지 않았다.
> 근거: [NIST SP 800-38D §8 및 부록 A/B](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
>
> 결정적 암호화의 AAD 는 컬럼별이 아니라 **동일 키를 사용하는 모든 결정적 호출**에서
> 같은 바이트열(또는 항상 빈 값)이어야 한다. 서로 다른 AAD 영역은 키를 분리한다.
> 암호문 동등성으로 JOIN 하는 컬럼들은 같은 키·AAD 를 사용해야 하며, 키 교체 시
> 이전/신규 암호문의 동등성이 유지되지 않으므로 이관 절차를 함께 설계한다.
>
> 이미 생성한 봉투를 복사·복제·복원하는 것은 새 암호화 호출이 아니다.
> `gcm_encrypt` 재호출은 새 nonce 로 암호화하고, 결정적 재호출은 키·평문·AAD 가
> 모두 같을 때 기존 결과를 재현한다. 재시도 중 AAD 만 바꾸지 않는다.
> 백업 복구로 키 사용량 장부를 되돌리지 않는다. 복구·프로세스 복제 후 난수 상태의
> 안전성이나 누적 사용량을 확신할 수 없으면 해당 키로 새 쓰기를 중단한다. 모든 쓰기 주체의
> 난수 상태를 복구·확인한 뒤 독립적으로 안전하게 생성한 새 키로 쓰기를 재개한다.
> 키 교체만으로 중복된 난수 상태가 해결되는 것은 아니다.
> 과거 데이터/백업 복호화에 필요한 키는 외부 키 관리 절차로 보존한다.
>
> 테스트 벡터 통과와 샘플 nonce 충돌 테스트는 운영 한도 준수나 결정적 구성의 안전성
> 증명이 아니다. 보안 가드 훅도 개발 명령을 제한할 뿐 운영 중 암호 사용을 감시하지 않는다.
> 이 개정은 운영 전제를 명시하며 SQL API·봉투·nonce 유도식·벡터를 변경하지 않는다.

> ## 개정 A8 (2026-09-28) — 배치 토폴로지: ROW 복제와 샤딩
>
> 함수 표면·봉투는 그대로 두고, 이 component 가 **복제·샤딩 구성에서 어떻게 배치되는지**를 명문화한다.
> 결론부터: 샤드마다 primary + ROW replica 를 두는 구성은 이 설계와 자연히 맞는다. 다만 지켜야 할
> 조건이 있고, 그 조건은 코드가 아니라 운영이 지킨다.
>
> **복제 — 암호화 결과를 그대로 전달한다**
>
> - `binlog_format=ROW` 에서는 primary 가 저장한 암호문·nonce·태그가 그대로 복제된다. replica 는
>   암호화를 다시 실행하지 않는다. STATEMENT 방식은 무작위 nonce 때문에 양쪽 값이 달라지므로
>   ROW 를 필수로 둔다 (§6 1항). 근거:
>   <https://dev.mysql.com/doc/refman/8.4/en/replication-formats.html>
>   실측: `tests/e2e/scenarios/replica_consistency.py` 와 `mysql-test/suite/gcm/t/gcm_replication.test`
>   가 양쪽 바이트 일치·replica 복호화·replica 에서의 한글 LIKE 를 확인한다 (8.4 · 9.4 통과).
> - **component 설치는 복제되지 않는다.** `INSTALL COMPONENT` 는 그 서버의 `mysql.component` 에만
>   기록된다. 복호화 조회를 받는 서버, 장애 시 primary 로 승격될 서버에는 **각각 설치**해야 하고,
>   애플리케이션이 그 서버에도 키를 전달할 수 있어야 한다. 근거:
>   <https://dev.mysql.com/doc/refman/8.4/en/component-loading.html>
>   MTR 복제 테스트가 primary·replica 양쪽에서 `gcm_install.inc` 를 소스하는 이유가 이것이다.
>
> **샤딩 — 라우팅과 키 정책이 핵심이다**
>
> | 항목 | 적용할 원칙 |
> |---|---|
> | 샤드 선택 | `tenant_id` 처럼 안정적인 식별자로 라우팅한다. 무작위 nonce 암호문(`0x02`)은 같은 평문도 매번 달라지므로 라우팅 키로 쓸 수 없다. 결정적 암호문(`0x03`)은 안정적이지만 그 자체를 샤드 키로 쓰면 키 로테이션이 리샤딩이 된다 |
> | 샤드 간 데이터 이동 | 기존 암호문을 **그대로** 옮길 수 있다 (재암호화 불필요). 목적지에서도 원래 키와 AAD 로 복호화해야 한다 |
> | 결정적 암호문 비교 | 샤드 간 같은 암호문을 얻으려면 키·평문·AAD 가 모두 같아야 한다. §6 의 "키마다 AAD 하나" 규칙이 샤드 경계를 넘어 적용된다 — 샤드별로 AAD 를 다르게 두면 같은 평문이 다른 봉투가 되어 교차 비교가 깨진다 |
> | 키 사용량 | 같은 키를 여러 샤드에서 쓰면 **새 암호화 호출량을 전체 샤드에 걸쳐 합산**해서 봐야 한다. 기존 암호문을 옮기는 것은 새 암호화가 아니다. 결정적 변형의 nonce 충돌 경계(§5.2)도 이 합산치로 따진다 |
> | 부분일치 검색 | `gcm_decrypt(...) LIKE '%길%'` 만으로는 샤드를 고를 수 없다. 라우팅 조건이 없으면 여러 샤드를 조회하고 각 샤드가 후보 행을 복호화한다 — 비용이 샤드 수에 비례한다 |
>
> **범위 밖**: 특정 샤딩 미들웨어(프록시·라우터)가 사용자 정의 함수 호출을 그대로 전달하는지,
> 결과 charset 을 보존하는지는 **그 조합으로 따로 검증해야 한다.** 이 저장소는 자체 운영 MySQL 서버에
> 대해서만 검증한다 (§0 범위). 프록시 방식은 §0 에서 이미 범위 밖이다.

> ## 개정 A7 (2026-09-28, 확정) — 계산된 SQL 식을 인자로 넘기지 않는다 (8.0·8.4 서버 결함)
>
> MySQL 8.0·8.4 는 **계산된 문자열 식**을 loadable function 인자로 넘길 때, 한 statement 의
> **두 번째 행부터** 낡은 인자 뷰를 건네준다. 같은 식을 빌트인 함수에 넘기면 항상 올바른 값이
> 나오고, component 를 "인자를 그대로 되돌려주는" 빌드로 바꿔도 같은 손상이 관측된다 —
> 즉 component 안에서는 탐지도 복구도 불가능하다. 9.4.0 에서는 재현되지 않는다.
>
> 실측 (`tests/integration/91_server_udf_arg_defect.sql` 이 버전별로 고정한다):
>
> | 인자 식 | 8.0.43 | 8.4.11 | 9.4.0 |
> |---|---|---|---|
> | `CONCAT(col, int_col)` · `CONCAT_WS(...)` · 이를 감싼 `LOWER(...)` | 정상 | **byte 0 손상** | 정상 |
> | `REPEAT('a', int_col)` | **길이 부풀림** | 정상 | 정상 |
> | `CAST(계산식 AS CHAR)` | 정상 | **16바이트에서 손상** | 정상 |
> | 컬럼 · 리터럴 · 사용자 변수 · 바인드 파라미터 | 정상 | 정상 | 정상 |
>
> 원인 지점은 `sql/item_func.cc` 의 `udf_handler::get_and_convert_string` 이다. 인자 Item 이 돌려준
> `String` 을 **얕게 복사**한 뒤(`buffers[index] = *res`) `c_ptr_safe()` 를 호출하는데, 그 Item 이
> 중첩 Item 의 버퍼를 가리키고 있으면 포인터·길이가 낡는다. 8.4 의 손상이 16바이트 경계에서
> 나타나는 것이 `String` 재할당 경계와 일치한다.
>
> 결정:
>
> - **회피를 코드로 시도하지 않는다.** 서버가 변환을 수행하도록 다른 collation 을 요구하면
>   (`argument_set(args, "collation", 0, "utf8mb4_bin")`) 8.4 의 `CONCAT` 손상은 사라지지만
>   `REPEAT` 의 **길이**가 부풀어 더 나쁜 결과(더 많은 바이트를 봉인)가 된다. 실측으로 확인했다.
>   따라서 `udf_encrypt.cc` 는 계약이 요구하는 charset(`utf8mb4`)만 요청한다.
> - **운영 제약으로 문서화한다** (§6, `docs/ops-constraints.md` 10항, README). 모든 버전에서 안전한
>   호출 형태는 컬럼·리터럴·사용자 변수·바인드 파라미터, 즉 **구체화된 값**이다. 애플리케이션이
>   드라이버로 바인드 파라미터를 보내는 정상 경로는 영향이 없다.
> - SQL 안에서 값을 계산해야 하면 **실제 테이블**에 먼저 쓴다 (`CREATE TEMPORARY TABLE ... AS SELECT`
>   또는 별도 statement) 뒤 저장된 컬럼으로 호출한다. **파생 테이블은 안 된다**: 기본
>   `derived_merge=on` 에서 옵티마이저가 파생 테이블의 식을 바깥 쿼리로 병합하므로 결국 행마다 계산된다.
>   8.4.11 실측 — `FROM (SELECT CONCAT(nm,id) AS v FROM t) d` 는 2·3행이 손상되고, 같은 쿼리에
>   `/*+ NO_MERGE(d) */` 또는 `derived_merge=off` 를 주면 정상이다. 그 둘은 구체화를 강제하므로 동작하지만
>   옵티마이저 힌트라 장래 버전이 무시할 수 있다. 실제 테이블은 그렇지 않다.
>   `CAST` 만으로도 충분하지 않다 (8.4, 16바이트).
> - `gcm_decrypt` 의 봉투 인자도 같은 부류이지만 실패가 `bad_tag`/`bad_envelope` 에러로 드러나므로
>   조용한 데이터 손상이 아니다. `gcm_encrypt*` 가 위험한 쪽이다.
> - 서버가 수정되면 91 케이스의 기대값이 0→1 로 바뀌어 CI 에서 드러난다. 그때 이 개정과 제약을 해제한다.

> ## 개정 A6 — 모듈 경계와 자원 수명
>
> 배포 범위(A4)와 SQL·봉투 계약은 유지하고, 구현의 경계를
> `.agents/rules/architecture.md` 에 명문화한다. 서버 어댑터는 코어를 호출하지만
> 코어(`gcm`, `envelope`, `nonce`)는 MySQL 서비스·설정·SQL 오류에 의존하지 않는다.
> SQL NULL·charset·strict 오류 변환은 UDF 계층, 바이트 형식은 envelope,
> 인증 결과는 gcm, 서버 버전 차이는 component/sysvar 계층이 담당한다.
>
> 자원은 component·UDF_INIT·연산 수명으로 구분한다. UDF_INIT 은 세션 전체와
> 동일하지 않다. (개정 A11 은 비밀을 담는 자원 둘 — `gcm_decrypt` 의 스케줄된 EVP 컨텍스트와
> `gcm_encrypt_det` 의 유도된 nonce 키, 각각 키 복사본과 함께 — 를 거기 적은 불변 조건 아래
> UDF_INIT 수명에 추가한다.) 등록 실패 시 롤백하고, 해제 실패 시 사용 중인 자원을 유지하며
> 이미 해제한 자원을 다시 해제하지 않도록 상태를 추적한다.
> 행 처리 경로에서 설정 조회·알고리즘 fetch·파일/네트워크 접근을 반복하지 않는다.
> 테스트용 고정 nonce 진입점은 SQL 에 노출하지 않고, 암호화를 우회하는 실험 코드는
> 배포 대상에서 제외한다. 기존 파일 배치를 유지하며 범용 backend 계층은 추가하지 않는다.
>
> 참고한 구현: [Percona Encryption UDF](https://github.com/percona/percona-server/blob/8.4/components/encryption_udf/encryption_udf_component.cc)의
> 서버/암호 래퍼 분리와 등록 상태 추적,
> [MySQL keyring operations](https://dev.mysql.com/doc/dev/mysql-server/8.4.9/operations_8h_source.html)의
> 연산/backend 경계,
> [pgcrypto SQL 진입점](https://github.com/postgres/postgres/blob/REL_17_STABLE/contrib/pgcrypto/pgcrypto.c)의
> SQL 인자·결과·오류 변환. 이들은 설계 참고이며 외부 프로젝트의 API·예외 정책·기능을 도입하는 근거는 아니다.

> ## 개정 A5 (2026-09-28, 확정) — `gcm.strict` 의 SESSION 스코프는 MySQL 9.0+ 에서만
>
> A1 개정은 `gcm.strict` 를 GLOBAL + SESSION 으로 두었다. 서버 소스 실측 결과
> **component sysvar 의 세션 스코프는 9.0.0 이상에만 구현되어 있다.** 8.0/8.4 에서
> `PLUGIN_VAR_THDLOCAL` 을 넘기면 등록은 성공하고 값 읽기는 범위 밖 읽기가 된다.
>
> 근거 (태그 `mysql-8.0.43` · `mysql-8.4.11` · `mysql-9.4.0` 실측):
>
> - `sql/server_component/component_sys_var_service.cc` 의 `PLUGIN_VAR_THDLOCAL` 등장 횟수는
>   8.0.43 · 8.4.11 이 0, 9.4.0 이 11 이다. 8.x 의 `register_variable` 은
>   `flags & PLUGIN_VAR_WITH_SIGN_TYPEMASK`(`0x00ff`) 로만 타입을 분기하므로 THDLOCAL(`0x0100`)이 탈락하고,
>   전역 bool 포인터를 쓰는 GLOBAL 경로가 실행된다.
> - 그런데 `sys_var_pluginvar` 는 **그 플래그로 스코프를 정하고**(`sql/sql_plugin_var.h`),
>   값 접근은 `real_value_ptr()` 에서 `*(int *)(plugin_var + 1)` 을 세션 저장소의 **바이트 offset** 으로
>   해석한다(`sql/sql_plugin_var.cc`). 8.x component 경로에서 그 자리는 전역 변수의 주소다 → OOB read.
>   **8.0/8.4 에 THDLOCAL 을 넘기지 않는다.**
> - 세션 값을 읽는 유일한 서비스 `mysql_system_variable_reader` 도 9.0.0 신설이다
>   (`include/mysql/components/services/mysql_system_variable.h`: 8.4.11 부재, 9.4.0 존재).
>   `component_sys_variable_register::get_variable` 은 헤더 주석과 구현(`OPT_GLOBAL` 하드코딩) 모두
>   **GLOBAL 전용**이라 세션 값 읽기에 쓸 수 없다.
> - 9.x 선례: `components/test/test_session_var_service.cc`,
>   `mysql-test/suite/service_sys_var_registration/{t,r}/session_var_service.*`.
>
> 결정:
>
> ```
> MySQL 9.0+     gcm.strict : GLOBAL + SESSION   (PLUGIN_VAR_BOOL | PLUGIN_VAR_THDLOCAL)
> MySQL 8.0/8.4  gcm.strict : GLOBAL only        (PLUGIN_VAR_BOOL)
> ```
>
> - 분기는 **컴파일 타임** (`MYSQL_VERSION_ID`). `mysql_system_variable_reader` 의 `SERVICE_TYPE` 선언
>   자체가 8.x 헤더에 없어 런타임 probe 로는 빌드되지 않고, `REQUIRES_SERVICE` 는 하드 로드 의존이므로
>   8.x 빌드에서는 그 두 서비스를 REQUIRES 목록에서 빼야 한다.
> - 8.0/8.4 에서 `SET SESSION gcm.strict` 는 서버가 `ER_INCORRECT_GLOBAL_LOCAL_VAR` 로 거부한다.
>   §6 운영 제약과 README 에 명시한다.
> - **태그 실패 의미론은 바뀌지 않는다** (ON=에러, OFF=NULL). 바뀌는 것은 그 값을 어느 스코프에서
>   바꿀 수 있는지 뿐이다. 서비스 호출 실패 시에는 strict ON 으로 간주한다 (fail closed).
> - 값은 statement 당 한 번(`Udf_func_init`)만 읽고 행마다 읽지 않는다. reader 는
>   `LOCK_system_variables_hash` read lock + 해시 룩업 + 숫자→문자열 변환을 거치므로 행 단위 호출은
>   부하 게이트에서 바로 드러난다. `SET SESSION` 은 statement 경계에서만 바뀌므로 의미론도 정확하다.

> ## 개정 A4 — 배포 범위는 MySQL component 와 SQL 인터페이스
>
> Python·Java 암호화 클라이언트를 별도 제품으로 제공하지 않는다. 애플리케이션은
> 기존 MySQL 드라이버로 `gcm_encrypt` / `gcm_encrypt_det` / `gcm_decrypt` 를 SQL 호출한다.
> 드라이버에 이 프로젝트의 암호 구현을 통합할 필요는 없다.
>
> Python 은 벡터 생성·검증과 SQL 기반 E2E/부하 실행을 위한 개발 도구로만 사용한다.
> `scripts/gen-vectors.py` 는 `cryptography` 로 고정 입력의 벡터를 생성하고 검증하며,
> 재사용 가능한 암복호화 클라이언트 API 나 패키지를 제공하지 않는다.
> 봉투·SQL API·기존 벡터의 바이트 값은 이 범위 개정으로 변경하지 않는다.
> C++ 단위 테스트와 SQL 통합 테스트가 서버 동작을 검증하며, 언어별 클라이언트의
> 동등성 검증·배포·호환성 유지 의무는 제거한다.

> ## 개정 A2 (2026-09-28, 확정) — 결정적 봉투도 nonce 를 저장한다
>
> 미해결 이슈 A2 를 다음으로 확정한다. §2.2 는 결정적 봉투를 `version || ct || tag` 로 두고
> "nonce 는 재계산" 이라 했지만, nonce 가 평문의 HMAC 이므로 **복호화 시점에는 평문을 몰라
> 재계산할 수 없다.** 따라서 결정적 봉투도 nonce 12 바이트를 저장한다.
>
> ```
> 0x02  GCM 무작위 : 0x02 || nonce(12) || ciphertext || tag(16)
> 0x03  GCM 결정적 : 0x03 || nonce(12) || ciphertext || tag(16)   # nonce 는 유도하되 저장한다
> ```
>
> - 결정성·동등성은 그대로다 (같은 키·평문·AAD → 같은 봉투 전체 바이트). 조인·UNIQUE 는 영향 없음.
> - 비용: 결정적 값당 +12 바이트. §2.2 의 "실제 증가 0~16 바이트" 는 **"평문 + 29 바이트"** 로 정정한다.
> - 복호화는 저장된 nonce 를 그대로 쓴다. 재계산 후 비교는 요구하지 않는다 (GCM 태그가 이미 인증한다).
> - 대안 AES-GCM-SIV 는 OpenSSL 3.2+ 에 묶여 서버 OpenSSL 을 제약하므로 채택하지 않는다.
>   선례는 HashiCorp Vault Transit 의 convergent encryption v2 (nonce 를 함께 저장한다).
> - 확정본은 `spec/envelope.md` (FINAL). 서버 구현·벡터 생성 도구·테스트는 그 문서를 따른다.

> ## 개정 A3 (2026-09-28) — v1 legacy CBC 봉투의 정의
>
> §2.2 는 version 바이트로 CBC→GCM dual-read 를 지원한다고만 했고 v1 의 바이트 배치는 비어 있었다.
> 구현·테스트를 위해 다음으로 정의한다. **복호화 전용이며 component 는 v1 을 절대 생성하지 않는다.**
>
> ```
> 0x01  legacy CBC : 0x01 || iv(16) || AES-256-CBC(PKCS#7) ciphertext
> ```
>
> - 마이그레이션은 기존 `AES_ENCRYPT` 값 앞에 version 바이트와 IV 를 덧붙이기만 한다 — 재암호화가 없다.
>   MySQL 은 32 바이트 키를 그대로 AES-256 키로 쓴다 (`my_aes_create_key` 의 XOR 접기는 입력 길이가
>   키 길이와 같으면 항등이다). 따라서 같은 키로 `gcm_decrypt` 와 `AES_DECRYPT` 결과가 같다.
> - v1 은 **인증되지 않는다.** 틀린 키로도 패딩이 우연히 맞으면 쓰레기 평문이 나올 수 있다. legacy
>   데이터의 성질이며 v2/v3 로 이관하면 사라진다. 이 한계를 `spec/envelope.md` 와 README 에 명시한다.
> - v1 은 AAD 를 받지 않는다. 비어 있지 않은 AAD 로 v1 을 복호화하면 `bad_envelope` 에러.
> - `gcm.strict` 는 v1 경로에 영향을 주지 않는다 (태그가 없다). 길이·패딩 오류는 항상 에러.

> ## 개정 A1 (2026-09-28) — 키 전달 방식: keyring → SQL 인자
>
> 초기안(§2.1 · §2.3 · §3 · §5.4 · Phase S 의 keyring 항목)과 달리, **키는 기존 MySQL
> `AES_ENCRYPT(str, key_str)` 과 동일하게 SQL 인자로 받는다.** 아래가 §2 를 대체한다.
>
> ```
> gcm_encrypt(plaintext, key [, aad])       -> BLOB     무작위 nonce
> gcm_encrypt_det(plaintext, key [, aad])   -> BLOB     결정적
> gcm_decrypt(ciphertext, key [, aad])      -> VARCHAR  charset 태깅 (utf8mb4)
> ```
>
> - `key` 는 **정확히 32 바이트**(AES-256) 바이너리. 길이가 다르면 에러. `AES_ENCRYPT` 의
>   키 접기(XOR folding)는 재현하지 않는다 — 약한 키를 조용히 받아들이는 원인이다.
> - 결정적 변형의 nonce 키는 별도 인자 없이 도메인 분리로 유도한다 (Phase 1 에서 확정):
>   `nonce_key = HMAC-SHA256(key, "mysql-gcm/v1/det-nonce")`,
>   `nonce = HMAC-SHA256(nonce_key, plaintext)[:12]`.
> - sysvar 는 `gcm.strict` (GLOBAL + SESSION, 기본 ON) 만 남는다. my.cnf 에는 `loose_gcm.strict`.
>   `gcm.key_id` · `gcm.nonce_key_id` · `gcm_key_id()` 는 폐기.
> - `keyring_reader_with_status` 의존과 §3 keyring 백엔드 선결 결정은 **범위 밖**이 된다.
>   §5.4 의 "키를 my.cnf 에 두지 않는다" 는 여전히 유효하다 (키는 앱이 보관하고 쿼리마다 전달).
> - 대가: 키 바이트가 SQL 문에 등장하므로 general log · slow log · `performance_schema.events_statements_*`
>   · SBR binlog 에 남을 수 있다. 이는 **현재 `AES_ENCRYPT` 운영과 동일한 노출면**이며 §6 운영 제약에
>   추가한다. keyring 방식은 향후 선택 기능(`gcm_encrypt_kr` 류)으로 재검토할 수 있다. *개정 A13 에서 재검토.*
> - Phase S 체크리스트에서 "keyring 에서 키를 읽음" 항목은 제거되고, "32 바이트 키 인자 검증 +
>   `SET SESSION gcm.strict` 동작" 으로 대체된다.

MySQL 에 AES-256-GCM 암복호화 함수를 추가하는 서버 component 를 만들기 위한
설계 문서. 별도 오픈소스로 분리할 것을 전제로 쓴다.

암호화 로드맵 2단계(CBC→GCM)의 선택 가능한 구성요소다. 이것 없이도 GCM 전환은
가능하지만, 그 경우 서버측 검색(LIKE)을 잃는다 — §1 참조.

> 원 프로젝트의 관련 문서: `.agents/docs/value-column-encryption.md`(로드맵),
> `.agents/docs/ope-removal.md`(0단계). 이 저장소에는 포함되지 않는다.

## 1. 왜 필요한가

### 1.1 MySQL 은 GCM 을 지원하지 않는다 (확정)

`block_encryption_mode` 허용값은 `aes-{128,192,256}-{ECB,CBC,CFB1,CFB8,CFB128,OFB}`
뿐이고, AEAD 모드가 없다. 인증 태그·AAD 를 받을 인자 자리도 없다.

실측 — 컨테이너에서 `SET SESSION block_encryption_mode` 직접 시험:

| 모드 | MySQL 8.4.11 | MySQL 9.4.0 |
|---|---|---|
| aes-256-cbc / -ecb / -cfb128 / -ofb | 수용 | 수용 |
| aes-256-gcm | 거부 | 거부 |
| aes-256-gcm-siv / -siv / -ctr / -xts | 거부 | 거부 |

```
ERROR 1231 (42000): Variable 'block_encryption_mode' can't be set to the value of 'aes-256-gcm'
```

문서도 8.0 → 8.4 → 9.7 까지 같은 목록이다. MySQL 버전을 올려 해결하는 경로는 없다.
MariaDB 도 ECB/CBC/CTR 뿐이라 계열 전체의 한계다.

### 1.2 서버측 복호화를 잃으면 부분일치 검색이 성립하지 않는다

환자명·EMR ID 부분일치 검색은 현재 서버측 `AES_DECRYPT + LIKE` 로 동작한다.
이를 앱으로 옮기면 요청마다 후보 전량을 복호화해야 한다.

| 후보 환자 수 | 앱측 읽기 + 복호화 (실측 기준 10.6µs/행) |
|---|---|
| 10,000 | 117ms |
| 100,000 | ~1.1초 |
| 300,000 | ~3.2초 |

검색 요청마다 3초는 성립하지 않는다. 서버측은 행 전송·파이썬 객체 생성이 없고
암복호가 C 속도라 비용 구조가 근본적으로 다르며, 현재 운영이 이미 그렇게 돌고
있으므로 성립이 증명된 경로다.

> 부분일치를 포기할 수 있다면(전방일치·정확일치로 축소) 이 component 는 필요 없다.
> 제품 결정이 선행 조건이다.

### 1.3 기존 오픈소스로는 안 된다

| 프로젝트 | 상태 |
|---|---|
| crypsi-mysql-udf | AES-GCM UDF 를 제공하지만 스타 0 · 커밋 36 · OpenSSL 1.1.1(EOL) 요구 · 키를 SQL 인자로 받음 · 결정적 모드 없음 · 라이선스 불명확 |
| lib_mysqludf_aes256 | AES-256 확장이고 GCM 아님 |
| Acra (Apache 2.0) | 프록시로 AES-256-GCM. 검색은 정확일치만(CE), 전방일치는 Enterprise, 부분일치·범위 없음. SQL 파싱 프록시라 CTE 많은 쿼리에 리스크 |

Acra 의 기능 경계가 우리 진단을 독립적으로 확인해준다 — 이 분야 제품도 부분일치는
제공하지 않는다.

## 2. 무엇을 만드는가

> 키 취급은 개정 A1 이, 봉투는 A2·A3 이 대체했다. 아래 원문을 그대로 두는 이유는 그 개정들이 바로 이
> 텍스트에 대한 델타로 쓰여 있어 원문 없이는 읽히지 않기 때문이다. **현행 설계가 아니다** — `gcm_key_id()`,
> 키 인자 없는 함수 표면, nonce 를 저장하지 않는 결정적 봉투는 모두 폐기됐다.

### 2.1 함수 표면

빌트인을 덮어쓸 수 없으므로 새 이름이어야 한다. `block_encryption_mode` 에
모드를 추가하는 것도 불가능하다.

```
gcm_encrypt(plaintext [, aad])       -> BLOB      무작위 nonce
gcm_encrypt_det(plaintext [, aad])   -> BLOB      결정적 (조인·UNIQUE·정확일치용)
gcm_decrypt(ciphertext [, aad])      -> VARCHAR   charset 태깅 (§5.3)
gcm_key_id()                         -> VARCHAR   현재 key id (관측용)
```

`gcm_encrypt_det` 는 선택이 아니다. 이것이 없으면 암호 컬럼을 조인 키로 쓰는
지점 전체가 깨진다 (vc-backend 94 / vc-report 37 / vc-sync 88곳, 패턴 재산정치).
결정적 변형이 있으면 그 지점들은 무변경이다.

```
nonce = HMAC-SHA256(nonce_key, plaintext)[:12]     # 합성 nonce, 저장 불필요
ct    = AES-256-GCM(key, nonce, plaintext, aad)
```

### 2.2 암호문 봉투

```
무작위 nonce : version(1) || nonce(12) || ciphertext || tag(16)
결정적       : version(1) || ciphertext || tag(16)        # nonce 는 재계산
```

- BLOB 반환. VARCHAR 아님 — MySQL 은 바이너리를 텍스트 형식으로 필터할 때
  동작이 애매하다 (Acra 도 같은 이유로 명시적 캐스팅을 넣었다)
- version 바이트로 CBC(v1) → GCM(v2) 과도기 dual-read 를 지원한다
- PKCS7 패딩이 사라지므로 실제 증가는 0~16바이트 (결정적 변형 기준)

### 2.3 my.cnf 통합

`component_sys_variable_register` 로 sysvar 를 등록하면 my.cnf·커맨드라인에서 설정된다.

```ini
[mysqld]
# key id 만. 키 바이트는 절대 두지 않는다 (§5.4)
loose_gcm.key_id       = vc_phi_v1
loose_gcm.nonce_key_id = vc_phi_nonce_v1
loose_gcm.strict       = ON
```

| sysvar | 스코프 | 설명 |
|---|---|---|
| gcm.key_id | GLOBAL + SESSION | keyring data id. 세션 스코프가 있어야 로테이션·dual-read 과도기가 된다 |
| gcm.nonce_key_id | GLOBAL + SESSION | 합성 nonce 용 HMAC 키 id (암호 키와 분리) |
| gcm.strict | GLOBAL + SESSION | 태그 불일치 시 ON=에러 / OFF=NULL |

키는 `keyring_reader_with_status` 로 Data ID 조회한다 → 키 바이트가 SQL 에
등장하지 않는다. crypsi 의 결함을 이걸로 피한다.

## 3. 선결 결정 — keyring 백엔드 (스파이크보다 먼저)

> 개정 A1 으로 **범위 밖**이 됐다. A1 이 이 절을 근거로 쓰여 있어 남겨둔다. 개정 A13 이 재검토했고,
> 이 절의 판정은 그것이 다루던 목표에 대해 그대로 유지한다.

이 결정이 프로젝트 정당성 자체를 좌우한다.

지금은 앱이 키를 갖고 SQL 로 넘긴다. keyring 방식은 DB 호스트에 키가 상주한다.

로드맵이 밝힌 암호화의 실질 효익은 "DB 파일·백업 유출 시 값 노출 차단" 이다.
그런데 `component_keyring_file` 로 같은 호스트에 키를 두면 데이터 파일을 가져간
사람이 키도 가져간다 — 그 효익이 사라진다.

| 백엔드 | 판정 |
|---|---|
| component_keyring_file | 불가. 위 효익이 무너진다. 개발·테스트에만 |
| component_keyring_vault / KMS keyring | 필요 조건 |

외부 keyring 을 운영에 둘 수 없다면 이 방향 전체를 재검토해야 한다.
"keyring_file 로 시작해서 나중에 바꾼다"는 계획은 위험하다.

## 4. 절차

### Phase S — 스파이크 (1~2일, 스펙보다 먼저)

위험한 미지값을 한 번에 답하는 최소 component 를 먼저 만든다. 이 결과에 따라
스펙이 달라지므로 순서를 바꾸지 않는다.

- [ ] component 골격이 UDF 하나를 `mysql_service_udf_registration` 으로 등록
- [ ] my.cnf 의 `loose_gcm.key_id` 를 sysvar 로 읽음
- [ ] keyring 에서 그 id 로 키를 읽음 (`keyring_reader_with_status`)
- [ ] `gcm_decrypt` 반환값에 charset 태깅 → 한글 `LIKE '%김%'` 이 native collation 으로 동작
      ← decrypt_like 필요 여부가 여기서 결정된다 (§5.3)
- [ ] `Created_tmp_disk_tables` 관측 — 평문이 디스크 temp 로 내려가는지 (§5.3)
- [ ] `EVP_CIPHER_fetch(NULL, "AES-256-GCM", NULL)` 이 빌드·런타임 OpenSSL 조합에서 성공

로컬 검증:

```sh
# 빌드한 .so 를 plugin_dir 로 넣고
docker cp component_gcm.so mysql-dev:/usr/lib/mysql/plugin/
docker exec -i mysql-dev mysql -uroot <<'SQL'
INSTALL COMPONENT 'file://component_gcm';
SELECT gcm_key_id();
SELECT HEX(gcm_encrypt_det('홍길동'));
SELECT gcm_decrypt(gcm_encrypt_det('홍길동'));
SELECT gcm_decrypt(gcm_encrypt_det('홍길동')) LIKE '%길%';   -- 1 이어야 한다
SHOW STATUS LIKE 'Created_tmp_disk_tables';
SQL
```

### Phase 1 — 스펙 (스파이크 결과 반영 후)

- 봉투 포맷 · 함수 표면 · sysvar · 실패 의미론 확정
- 테스트 벡터 — NIST CAVP GCM KAT + 자체 벡터. C++ 서버 코어와 SQL 테스트의 공통 기준이다
- 문서화할 운영 제약 목록 (§6)

### Phase 2 — 구현 + 테스트

- OpenSSL EVP, 이름으로 fetch (`EVP_aes_256_gcm()` 심볼 직접 사용 금지 — 빌드 OpenSSL 에 묶인다)
- `OPENSSL_cleanse` 로 키 버퍼 소거. 에러 메시지에 키·평문 금지
- MTR (mysql-test) .test/.result 스위트
- 결정적 변형의 nonce 충돌 경계 테스트

### Phase 3 — SQL 사용 흐름과 E2E 검증

기존 MySQL 드라이버로 SQL 함수를 호출하는 사용 흐름을 검증한다. 암호화 저장 →
서버 복호화와 한글 LIKE, ROW 복제, legacy CBC dual-read, AAD 불일치 및 세션 strict
격리를 다룬다. Python runner 는 SQL 실행·결과 확인만 담당하며 암복호화하지 않는다.

### Phase 4 — 빌드·배포·문서

- 빌드 매트릭스: MySQL 메이저 버전 × 플랫폼(amd64/arm64, glibc/musl) × OpenSSL
  — component ABI 가 서버 버전에 결합된다
- §6 의 운영 제약을 README 첫 화면에 배치

### Phase 5 — 업스트림 (선택, 기대치 낮게)

선례: WL#6781 "Support multiple AES Encryption modes" 가 지금의 모드 목록을 추가했다.
채널은 존재한다.

다만 `AES_ENCRYPT(str, key, iv, kdf, salt, info)` 에 태그·AAD 자리가 없어 기존 함수
확장이 아니라 새 함수군이 필요하므로 수용 가능성은 낮다. feature request 제출은
비용이 거의 없다.

## 5. 설계 결정과 근거

### 5.1 왜 component 인가 (legacy UDF plugin 아님)

component 인프라는 서비스 경계가 명확하고 신규 확장의 권장 경로다. 결정적으로
keyring 서비스와 sysvar 등록 서비스를 쓸 수 있다 — legacy UDF 로는 키를 함수
인자로 받는 수밖에 없다 (crypsi 가 그렇다).

### 5.2 왜 결정적 변형이 필수인가

암호 컬럼이 스키마의 조인 백본이다.

```
Patient.encrypted_emr_id      == Encounter.encrypted_patient_id
Encounter.encrypted_emr_id    == Score.encrypted_encounter_id
Encounter.encrypted_emr_id    == UserPin.encrypted_encounter_id
```

또 `uq_emr_location_natural_key (site, ward, room, bed)` 는 room/bed 가 결정적
AES 라서 성립하는 UNIQUE 다. 무작위 nonce 만 제공하면 이 전부가 깨진다.

합성 nonce 의 안전성: 서로 다른 평문이 같은 nonce 를 얻으면 GCM 은 치명적이지만,
HMAC-SHA256 을 96비트로 자른 충돌은 값 1,000만 개 기준 약 10⁻¹⁵ 수준이다. 같은
평문이 같은 nonce 를 얻는 것은 의도한 결정성이다. 다만 동일 키의 모든 결정적 호출에서
AAD 가 같아야 한다(개정 A8). 동등성·빈도·길이 정보가 노출되며, 이 충돌 확률 계산만으로
구성 전체의 안전성이나 키당 운영 한도가 증명되지는 않는다. 별도 보안 검토가 필요하다.

선례: HashiCorp Vault Transit 의 convergent encryption 이 같은 구성이다.

### 5.3 왜 decrypt_like 를 먼저 만들지 않는가

MySQL 8.0.19 부터 `mysql_udf_metadata` 서비스로 반환값의 charset/collation 을
지정할 수 있다. 그러면 MySQL 의 native LIKE 를 그대로 쓸 수 있다.

```sql
WHERE gcm_decrypt(encrypted_name) LIKE '%김%'   -- 컬럼의 콜레이션 아래에서
```

decrypt_like 를 직접 만들면 C 로 컬럼 콜레이션의 대소문자 무시·악센트/전각 처리를 CJK 까지
재현해야 한다. OPE 제거에서 파이썬 코드포인트 순서와 MySQL collation 이 달라 한 번 데인 지점이다.
재현하지 말고 MySQL 것을 쓴다. 콜레이션은 컬럼의 것이고, 8.0+ 의 기본 utf8mb4 콜레이션은
`utf8mb4_0900_ai_ci` 이며(측정 — `tests/integration/20_korean_like.expected`), 이 절이 예시로
들던 옛 `utf8mb4_general_ci` 가 아니다. 개정 A17 은 그 비교 위에 인덱스를 얹으면 어떻게 되는지
측정했다: 바이너리 정규화는 콜레이션이 맞추는 행을 놓친다(`docs/leakage-ngram.md`).

> 단, decrypt_like 를 원할 정당한 이유가 하나 있다 — 성능이 아니라 보안이다.
> `gcm_decrypt(col)` 이 임시 테이블·filesort 를 타면 평문이 디스크 기반 temp 로
> 내려간다. boolean 만 돌려주는 융합 함수는 평문을 메모리 밖으로 내보내지 않는다.
> Phase S 에서 `Created_tmp_disk_tables` 로 실제 발생을 관측한 뒤 판단한다.

### 5.4 왜 키를 my.cnf 에 두지 않는가

파일 읽기 권한자 전원에게 노출되고, 설정관리·백업·이미지에 남고, SHOW VARIABLES
로도 보일 수 있다. MySQL 자신의 InnoDB TDE 가 쓰는 방식이 정답이다 — my.cnf 는
key id 만, 키 바이트는 keyring.

### 5.5 태그 불일치를 NULL 로 내리지 않는다

기존 `AES_DECRYPT` 는 실패 시 NULL 을 돌려줘 "키 틀림"과 "데이터 없음"이 구분되지
않는다. AEAD 에서 이건 인증의 의미를 없앤다. `gcm.strict=ON` 을 기본으로 두고
에러를 올린다.

## 6. 운영 제약 — README 에 반드시 명시

- 무작위 nonce 함수는 비결정적 → statement-based replication 에서 위험하다.
  `INSERT ... VALUES(gcm_encrypt(...))` 가 마스터와 레플리카에서 다른 값을 만든다.
  ROW binlog 필수
- 비결정 함수는 생성 컬럼·인덱스에 사용 불가
- 평문이 서버 로그에 남는다. 암호화 호출은 평문을 SQL 인자로 받으므로 general
  log · slow log · performance_schema.events_statements_* · SBR binlog 에 남는다.
  검색 패턴('%김%')도 평문 PHI 조각이다. UDF 방식의 근본 한계이며 회피할 수 없다
- 관리형 MySQL 에는 설치할 수 없다 (plugin_dir 접근 불가)
- component sysvar 는 component 설치 전까지 값이 적용되지 않는다. my.cnf 에
  `loose_` 접두 없이 적으면 최초 기동이 실패할 수 있다
- UDF 는 옵티마이저에 불투명하다. 선택도는 다른 술어(scope·status 필터)에 의존한다
- (개정 A17) `LIKE` 에 인덱스를 주려는 키드 n-gram 토큰 사이드 테이블은 **연구 후 기각**했다:
  결정적 토큰이 n-gram 빈도와 동시출현을 누출하고, 한국어에서 실험이 S1 공격으로 n-gram 의 20.7%를
  복구했으며(두 번째 S1 공격 17.3%, 더 강한 S3 공격 3 은 31.7%), 상한을 크게 넘었다. [`leakage-ngram.md`](leakage-ngram.md)
  참고. 동기 쿼리 `LIKE '%김%'` 는 인덱스의 최악 사례(~21% 선택도)이고, 바이너리 토큰 키는
  콜레이션을 존중하지 않는다.
- (개정 A2) `gcm_encrypt_det` 의 nonce 는 평문만의 함수다. **한 키에 대해 같은 평문을 서로 다른 AAD 로
  암호화하면 (키, nonce) 쌍이 재사용**되고, 두 값을 모두 본 공격자는 GHASH 서브키를 복원해 그 nonce 에
  대한 태그 위조가 가능해진다. 기밀성은 영향받지 않는다(같은 평문이므로 키스트림이 두 평문을 덮지 않는다).
  운영 규칙: 동일 키를 사용하는 모든 결정적 호출에서 AAD 를 하나로 고정한다.
  서버·컬럼·애플리케이션이 달라도 예외가 없으며, 다른 AAD 영역에는 다른 키를 쓴다.
  무작위 변형에는 이 AAD 고정 제약이 적용되지 않는다.
  근거·표현은 `spec/envelope.md` §3.
- (개정 A3) `gcm_decrypt` 는 legacy `0x01`(CBC) 봉투를 받아들이며 이 경로는 **인증되지 않는다**.
  dual-read 이관이 끝나면 애플리케이션에서 `0x01` 을 거부한다.
- (개정 A1) 키가 SQL 인자로 전달되므로 general log · slow log · performance_schema · SBR binlog 에
  키 바이트가 남을 수 있다. `AES_ENCRYPT` 와 동일한 노출면. general log 비활성, slow log 의
  `log_raw=OFF` 는 도움이 되지 않으므로(UDF 인자는 리터럴) 로그 접근 통제로 대응한다
- (개정 A5) `gcm.strict` 는 MySQL 9.0 미만에서 **GLOBAL 전용**이다. 8.0·8.4 에서 `SET SESSION gcm.strict`
  는 `ER_INCORRECT_GLOBAL_LOCAL_VAR` 로 거부된다. 태그 실패 의미론(ON=에러, OFF=NULL)은 모든 버전에서 같다
- (개정 A7) **계산된 SQL 식을 `gcm_encrypt*` 인자로 직접 넘기지 않는다.** 8.0·8.4 서버가 두 번째 행부터
  낡은 인자를 건네 조용히 잘못된 평문을 봉인할 수 있다. 컬럼·리터럴·사용자 변수·바인드 파라미터를 쓰고,
  SQL 안에서 계산해야 하면 먼저 구체화한다 (`CAST` 만으로는 불충분)
- (개정 A8) **component 설치는 복제되지 않는다.** 복호화 조회를 받는 서버와 승격 대상 replica 에 각각
  `INSTALL COMPONENT` 하고, 애플리케이션이 그 서버에도 키를 전달할 수 있어야 한다. ROW binlog 는
  암호문·nonce·태그를 그대로 옮기므로 replica 가 재암호화하지 않는다
- (개정 A8) **샤딩에서는 무작위 암호문을 라우팅 키로 쓸 수 없고**, `gcm_decrypt(...) LIKE` 만으로는
  샤드를 고를 수 없다. 안정적 식별자로 라우팅한다. "키마다 AAD 하나" 규칙은 샤드 경계를 넘어 적용되며,
  결정적 암호문을 샤드 간 비교하려면 키·평문·AAD 가 모두 같아야 한다. 샤딩 미들웨어의 UDF 전달·charset
  보존 여부는 그 조합으로 별도 검증한다

- (개정 A8) 동일 키를 쓰는 모든 서버·컬럼·애플리케이션의 사용량을 합산하고,
  배포 전 키당 사용 예산·교체 기준을 보안 검토한다. component 는 예산을 갖지 않고 자동 교체도 하지
  않는다. 키 id 함수에 대해서는 키 이름별 카운트를 공개한다(`gcm_key_usage`, 개정 A14). 이 합산의 입력
  하나이지 합계가 아니다.
- (개정 A8) 봉투 복사/복원은 새 암호화가 아니다. 재암호화·결정적 재시도의 조건을 구분하고,
  DB 복원으로 누적 사용량을 되돌리지 않는다. 사용 이력·난수 상태 안전성이 불확실하면 쓰기를 중단하고,
  모든 쓰기 주체의 난수 상태를 복구·확인한 뒤 안전하게 생성한 새 키로 재개한다.
- (개정 A8) 키 교체는 결정적 암호문의 JOIN/UNIQUE 이관과 과거 데이터·백업용 키 보존을 동반한다.
  가드 훅·벡터·샘플 충돌 테스트는 운영 중 nonce 재사용 탐지나 안전성 증명을 제공하지 않는다.

## 7. 라이선스 — GPLv2 (확정)

**결론: GPLv2 로 확정한다** (2026-09-28). `LICENSE` 에 GPLv2 전문을 두고, 소스에는
`SPDX-License-Identifier: GPL-2.0-only` 를 표기한다.

근거: MySQL 서버는 GPLv2(FOSS exception)이고 component 는 서버 헤더에 링크한다. 파생물
판단 시 GPLv2 배포가 안전한 선택이다. Apache/MIT 로 내리는 길은 검토 대상이었으나
채택하지 않았다. OpenSSL 3 는 Apache-2.0 이고 GPLv2 와의 조합은 MySQL 자신의 FOSS
exception 이 다루는 구성과 같다 — 우리는 서버가 이미 로드한 libcrypto 를 쓰고 별도
번들·정적 링크를 하지 않으므로(crypto-safety) MySQL 배포와 같은 형태다.
`GPL-2.0-only` 이며 "or later" 가 아니다: MySQL 이 GPLv2-only 이므로 상향 호환을
주장하지 않는다.
