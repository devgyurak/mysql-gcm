# Operational constraints (must appear on the README first screen)

Source: `docs/design.md` §6 and amendments A1, A3, A5, A7, A8, A10, A12, A13, A14. Keep the two in sync.

1. **`gcm_encrypt` is non-deterministic.** Under statement-based replication the primary and replica produce different bytes. ROW binlog is required. Non-deterministic functions cannot be used in generated columns or indexes.
2. **Keys and plaintext appear in server logs.** Keys and plaintext are SQL arguments (same surface as `AES_ENCRYPT`), so they can land in the general log, slow log, `performance_schema.events_statements_*` and SBR binlog. `LIKE '%kim%'` patterns are plaintext fragments too. Control log access; this cannot be avoided by the component. The key-id functions (item 17) take the *key* out of the encryption and decryption statements; the plaintext and the `LIKE` pattern stay.
3. **Self-managed MySQL only.** Managed services (RDS, Aurora, Cloud SQL) do not expose `plugin_dir`.
4. **Component sysvars need `loose_` in my.cnf** (`loose_gcm.strict=ON`); without it the server refuses to start before the component is installed.
5. **The functions are opaque to the optimizer.** `WHERE gcm_decrypt(col, @k) LIKE ...` always scans the candidate set; selectivity must come from other predicates.
6. **`gcm_encrypt_det` reveals equality, and costs several times more than the random variant.** Use it only for join keys, UNIQUE constraints and exact-match lookups, never for free text. Its nonce comes from two HMAC-SHA256 passes over the key and the plaintext (`spec/envelope.md` §3), which measures **3.5–5x a plain AES-GCM seal** — the cost is the HMAC, not the cipher, and whether it grows or shrinks with plaintext size depends on whether that CPU accelerates SHA-256 as well as AES. Decryption is unaffected: `gcm_decrypt` costs the same for either variant. Measure on your own hardware before putting it on a write-heavy column (`docs/perf.md`).
7. **One AAD convention per key for deterministic encryption** (`spec/envelope.md` §3). `gcm_encrypt_det` derives its nonce from the plaintext only, so encrypting the same plaintext under one key with two different AADs reuses the (key, nonce) pair and can enable tag forgery. All deterministic calls with that key must use identical AAD bytes (or always empty AAD) across servers, columns and applications. Different AAD domains require different keys. Columns joined by ciphertext equality need the same key and AAD. The random variant has no fixed-AAD requirement.
8. **`gcm_decrypt` accepts legacy `0x01` (CBC) envelopes, which are unauthenticated.** Dual-read exists to migrate; a wrong key can return garbage instead of an error. Finish the migration to `0x02`/`0x03` and then reject `0x01` at the application layer. **A v1 plaintext must already be UTF-8**: the result is tagged `utf8mb4` for every version, and unlike a *character* argument to `0x02`/`0x03` a v1 envelope never went through the encryption path that converts it. (A `binary` argument is not converted either, so `gcm_encrypt(UNHEX('ff'), key)` has the same ill-formed result — encrypt text, not bytes, if you want `LIKE` to work on it.) A latin1 `Müller` comes back as the ill-formed `4D FC 6C 6C 65 72`, and `LIKE '%ller%'` then returns 0 with no error — the search this project exists for fails silently. Convert the legacy column to `utf8mb4` before prefixing `0x01 || iv` (`spec/envelope.md` §2.3). The component cannot fix this for you: it does not know the legacy charset, and guessing would corrupt genuinely binary values.
9. **`gcm.strict` has no SESSION scope before MySQL 9.0** (`docs/design.md` amendment A5). Component system variables only gained session scope in 9.0.0, so on 8.0 and 8.4 `gcm.strict` is GLOBAL-only and `SET SESSION gcm.strict` fails with `ER_INCORRECT_GLOBAL_LOCAL_VAR`. Relaxing strictness for one connection is a 9.0+ capability; before that it is a server-wide decision. The tag-failure semantics themselves (ON = error, OFF = NULL) are identical on every version.
10. **Pass a stored value, not a freshly computed expression** (`docs/design.md` amendment A7). MySQL 8.0 and 8.4 hand a loadable function a stale view of some *computed* string arguments from the second row of a statement onward, so `gcm_encrypt_det(CONCAT(name, id), @k)` can silently seal the wrong bytes. Built-in functions over the same expression are unaffected and the component cannot detect it. Safe on every version: a column, a literal, a user variable or a bound parameter — which is what an application sends anyway. If a value must be computed in SQL, write it into a **real table** first — a `CREATE TEMPORARY TABLE ... AS SELECT`, or a separate statement — and call the function on the stored column. **A derived table is not enough**: with the default `derived_merge=on` the optimizer merges its expression back into the outer query, so the argument is computed per row after all. Measured on 8.4.11: `FROM (SELECT CONCAT(nm, id) AS v FROM t) d` corrupts rows 2 and 3, while the same query with `/*+ NO_MERGE(d) */` or `optimizer_switch='derived_merge=off'` is correct. Those two force materialisation and do work, but they are optimizer hints — a future version is free to ignore them, and a real table is not. `CAST` alone is **not** a workaround either. MySQL 9.4 does not reproduce it. `tests/integration/91_server_udf_arg_defect.sql` pins the behaviour per version.
11. **Define a per-key usage budget and rotation plan before deployment.** Aggregate encryption use across all servers, columns and applications sharing the key. Review limits for the random/deterministic nonce construction, message sizes and acceptable risk; this project has not established a universal safe usage limit. The component does not hold a budget or rotate keys. For the key-id functions it publishes a count per key name (`gcm_key_usage`, item 19), which is one input to this sum and not the sum. Rotation changes deterministic ciphertext equality, so plan JOIN/UNIQUE migrations and externally managed retention of keys needed for old data and backups. A12 requires independent full-length CSPRNG keys per suite/security domain, never resizing another key. If related forms were used, stop encryption under both and migrate dependent columns together; old copies remain linkable. Before enabling deterministic AES-128, approve a numerical budget, finite encryption-use period and confidentiality/retention horizon including backups. Keep AAD fixed per key and use independent keys for random mode unless cross-mode risk is separately reviewed. Rotate before budget/period expiry; stop on suspected key compromise, nonce collision, AAD violation or uncertain usage/RNG history. Prefer AES-256 for long/open-ended retention. The default floor remains 32 and does not enforce these conditions. See A12 for full conditions.
12. **Preserve nonce safety and usage accounting through retries and recovery.** Copying, replicating or restoring an existing envelope is not a new encryption call. A new `gcm_encrypt` call uses a fresh random nonce. A deterministic retry reproduces bytes only for the same key, plaintext and AAD; do not change only AAD. Do not reset cumulative key-usage accounting when restoring a database. If usage history or RNG-state safety is uncertain after recovery/process cloning, stop encrypting with the affected key. Restore and verify safe RNG state across all writers before resuming with a freshly and independently generated key; key replacement alone does not repair duplicated RNG state. Retain old keys for required reads.
13. **Distinguish implemented checks from operational assurances.** Input validation, authentication and failure handling are implemented. Nonce-reuse detection, cross-call AAD-policy enforcement, usage quotas and rotation are not; `gcm_key_usage` (item 19) counts and enforces nothing. Development guard hooks constrain agent commands, not production calls. Deterministic encryption leaks equality, frequency and length; test-vector conformance and sampled collision tests do not prove the construction or deployment safe. Obtain an independent review before production use. On 2026-10-07 Codex recorded a scoped AI design review of #22/A12: Q1 accepts shared derivation under independent key generation; Q2 retains deterministic AES-128 conditionally. The full construction, implementation, A11 retention/timing and deployment configuration were not reviewed; this is not a human cryptographic audit. Reference: [NIST SP 800-38D, §8 and Appendices A/B](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
14. **Installing the component is not replicated** (`docs/design.md` amendment A8). `INSTALL COMPONENT` writes to that server's `mysql.component` and nothing else. Install it on every server that answers decryption queries and on every replica that could be promoted, and make sure the application can supply the key there too. Keyring contents are not replicated either: a server that runs a key-id function (item 17) needs the key in its own keyring, under the same id and the same account. ROW binlog carries the ciphertext, nonce and tag as bytes, so a replica never re-encrypts — that is what makes replication safe here, and it is also why the replica still needs the component to *read* those values. MySQL reference: [replication formats](https://dev.mysql.com/doc/refman/8.4/en/replication-formats.html), [component loading](https://dev.mysql.com/doc/refman/8.4/en/component-loading.html).
15. **Sharding: route on a stable identifier, not on ciphertext** (`docs/design.md` amendment A8). A random-nonce value differs on every call, so it cannot be a routing key; a deterministic value is stable but using it as the shard key turns key rotation into a resharding job. Moving rows between shards needs no re-encryption — the destination decrypts with the original key and AAD. Comparing deterministic ciphertext across shards requires the same key, plaintext *and* AAD, so the "one AAD convention per key" rule (item 7) applies across shard boundaries. Count new encryption calls across all shards that share a key when reasoning about the deterministic collision bound; copying existing ciphertext is not a new encryption. And `gcm_decrypt(...) LIKE '%김%'` alone cannot select a shard: without a routing predicate every shard is queried and each decrypts its own candidates. Whether a particular sharding proxy or router forwards loadable-function calls and preserves the result charset must be verified with that combination — this project only validates self-managed MySQL servers.
16. **A truncated key silently selects a weaker cipher unless `gcm.min_key_bytes` stops it** (`docs/design.md` amendment A10). The key length picks the suite — 32 bytes is AES-256-GCM, 24 is AES-192-GCM, 16 is AES-128-GCM — so a 32-byte key that was truncated by a client bug, a mis-set environment variable or a mis-sliced buffer is a *valid* key for a weaker suite. `gcm_encrypt` seals with it and reports success, at a strength nobody asked for. `gcm.min_key_bytes` is GLOBAL and defaults to `32`, which refuses exactly that; leave it alone unless you intend to use a smaller suite; `24` permits AES-192 and AES-256 while refusing AES-128. It is an administrator policy, not a session setting: a session cannot lower it. Lowering it on a server that hosts several applications removes the guard for all of them. Decryption never consults it, so raising it again cannot lock out data written while it was lower — which is what makes migrating off AES-128 possible. Reading the setting fails closed: if the server cannot return it, the floor is 32. Note also that a wrong key length on decryption is reported as a key-length error, which says the envelope and the key disagree — it is *not* evidence of truncation, since a corrupted version byte produces the same error.
17. **The key-id functions move the key into the keyring; they do not make it safe there** (`docs/design.md` amendment A13). `gcm_encrypt_kr`, `gcm_encrypt_det_kr` and `gcm_decrypt_kr` take a key id and read the key stored under it for the calling account, so the key is not an argument of those statements. What follows from that: **(a)** the boundary is the account — `priv_user@priv_host`, the namespace of the server's `keyring_key_generate` — not a privilege. Every session of an account can use every key of that account, and `keyring_key_fetch` hands the bytes to any of them that holds the global `EXECUTE` privilege. **(b)** A key created with `keyring_key_generate` never appears in a statement; importing an existing one with `keyring_key_store` does, once. **(c)** With `component_keyring_file`, the only keyring in Oracle's MySQL Community distribution, the key file sits beside the data, so a stolen data directory or backup includes the key. Surviving that needs an external keyring backend, which is in MySQL Enterprise Edition and has **not** been tested with this component; nor has Percona Server's. **(d)** To share a key between accounts, use a `SQL SECURITY DEFINER` stored routine with the key id and the AAD hard-coded — never as parameters, which would make the routine an oracle over the definer's keyring. A view does not work: a function in a view runs as the invoker. A stored *function* reads the keyring once per row; put the whole statement in a stored *procedure* to read it once. **(e)** One key id per function call per statement: an id taken from a column is refused as soon as a row names a different one. **(f)** Both `_kr` encryption functions need ROW binlog. **(g)** A key generated in the keyring exists nowhere else — back the keyring up, and keep old keys for old data. **(h)** Every condition on a deterministic key (items 6, 7, 11) applies to a keyring key: `keyring_key_store` accepts a padded or low-entropy key and the component cannot tell. **(i)** When a call fails with "no usable AES key", check as the same account: `SELECT CURRENT_USER()` (`app@localhost` and `app@%` are different namespaces), `keyring_key_type_fetch('id')` and `keyring_key_length_fetch('id')`. The message does not say which it was, on purpose. **(j)** With `log_error_verbosity = 3` the server's keyring component writes a note to the error log for every lookup that finds nothing, carrying the key id and the account that asked. That is the server's logging, not this component's, and is off at the default verbosity of 2; treat a verbose error log as containing key ids.
18. **Do not nest one of these functions inside another with a prepared-statement parameter** (`docs/design.md` amendment A13, "Implementation notes"). When a loadable function is an argument of another loadable function and takes a `?`, the server evaluates the inner call while initialising the outer one, before the parameter has its value, so the inner function sees an empty string: `PREPARE s FROM 'SELECT gcm_decrypt(gcm_encrypt(?, ?), ?)'` fails on `EXECUTE` with a 0-byte key, and the key-id form fails with an invalid key id. After that error `UNINSTALL COMPONENT` is refused until the server is restarted. The inner function's `deinit` is never called either — not at the end of the statement, on `DEALLOCATE PREPARE` or when the session ends — so whatever its instance held is neither wiped nor freed while the server runs; the key-id functions therefore wipe everything their instance holds — the fetched key included — in the row that raises an error, rather than waiting for it. Tracked in issue #43. This is server behaviour, observed on 8.4.11 with the key-argument functions and not tried on 8.0 or 9.4; the component cannot detect or prevent it, and no committed test pins it because triggering it leaves the test server unable to uninstall the component. An application has no reason to write this shape — it seals in one statement and opens in another — and a function nested inside a builtin (`LENGTH(gcm_encrypt(?, ?))`) is unaffected.
19. **`gcm_key_usage` is a count, not your key's usage** (`docs/design.md` amendment A14). `SELECT gcm_key_usage('id')` returns, as JSON text, what the key-id functions have counted under that id **for the calling account on this server since the component started**: `random_seals`, `det_seals`, `bytes_sealed`, `tag_failures`, with `since` and `complete`. Use it as one input to the budget of item 11, and know what it leaves out: **(a)** the key-argument functions are not counted at all — a deployment that also passes the same key as an argument (which `keyring_key_fetch` makes possible) has a count that is not the total. **(b)** Other servers are other counts; a replica counts nothing. **(c)** The name is the account and the id, not the key bytes: the same key under another id or account is counted separately, and an id whose key was removed and generated again keeps counting as if it were the same key. **(d)** It restarts from zero at every server start and reinstall; `since` changes when it does. Nothing is persisted, so the durable ledger has to be your monitoring system reading this function — per account, or through a definer routine with the id hard-coded, which then shows its callers that account's volume. **(e)** `det_seals` counts calls: a lookup `WHERE c = gcm_encrypt_det_kr(?, 'id')` adds one each time though it seals nothing new. **(f)** `tag_failures` is the number that can show a forgery attempt, and it also counts honest mistakes such as opening a value under the wrong key id. **(g)** A count appears when the function call that made it is finished with — normally when its statement ends — not while it runs; and a call the server abandons without finishing (item 18) can lose its count, so read the number as a lower bound on what it counts. **(h)** At most 64 key ids per account are counted (1,024 on the server); past that, `complete` is `false` in that account's answers and some of its use is in no row. If the whole table fills, an account that has counted nothing yet is also told `false`. **(i)** There are no thresholds: nothing warns and nothing is refused. Alerting is a rule in your monitoring.
