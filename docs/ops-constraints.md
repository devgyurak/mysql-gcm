# Operational constraints (must appear on the README first screen)

Source: `docs/design.md` §6 and amendments A1, A3, A5, A7, A8. Keep the two in sync.

1. **`gcm_encrypt` is non-deterministic.** Under statement-based replication the primary and replica produce different bytes. ROW binlog is required. Non-deterministic functions cannot be used in generated columns or indexes.
2. **Keys and plaintext appear in server logs.** Keys and plaintext are SQL arguments (same surface as `AES_ENCRYPT`), so they can land in the general log, slow log, `performance_schema.events_statements_*` and SBR binlog. `LIKE '%kim%'` patterns are plaintext fragments too. Control log access; this cannot be avoided by the component.
3. **Self-managed MySQL only.** Managed services (RDS, Aurora, Cloud SQL) do not expose `plugin_dir`.
4. **Component sysvars need `loose_` in my.cnf** (`loose_gcm.strict=ON`); without it the server refuses to start before the component is installed.
5. **The functions are opaque to the optimizer.** `WHERE gcm_decrypt(col, @k) LIKE ...` always scans the candidate set; selectivity must come from other predicates.
6. **`gcm_encrypt_det` reveals equality, and costs several times more than the random variant.** Use it only for join keys, UNIQUE constraints and exact-match lookups, never for free text. Its nonce comes from two HMAC-SHA256 passes over the key and the plaintext (`spec/envelope.md` §3), which measures **3.5–5x a plain AES-GCM seal** — the cost is the HMAC, not the cipher, and whether it grows or shrinks with plaintext size depends on whether that CPU accelerates SHA-256 as well as AES. Decryption is unaffected: `gcm_decrypt` costs the same for either variant. Measure on your own hardware before putting it on a write-heavy column (`docs/perf.md`).
7. **One AAD convention per key for deterministic encryption** (`spec/envelope.md` §3). `gcm_encrypt_det` derives its nonce from the plaintext only, so encrypting the same plaintext under one key with two different AADs reuses the (key, nonce) pair and can enable tag forgery. All deterministic calls with that key must use identical AAD bytes (or always empty AAD) across servers, columns and applications. Different AAD domains require different keys. Columns joined by ciphertext equality need the same key and AAD. The random variant has no fixed-AAD requirement.
8. **`gcm_decrypt` accepts legacy `0x01` (CBC) envelopes, which are unauthenticated.** Dual-read exists to migrate; a wrong key can return garbage instead of an error. Finish the migration to `0x02`/`0x03` and then reject `0x01` at the application layer. **A v1 plaintext must already be UTF-8**: the result is tagged `utf8mb4` for every version, and unlike a *character* argument to `0x02`/`0x03` a v1 envelope never went through the encryption path that converts it. (A `binary` argument is not converted either, so `gcm_encrypt(UNHEX('ff'), key)` has the same ill-formed result — encrypt text, not bytes, if you want `LIKE` to work on it.) A latin1 `Müller` comes back as the ill-formed `4D FC 6C 6C 65 72`, and `LIKE '%ller%'` then returns 0 with no error — the search this project exists for fails silently. Convert the legacy column to `utf8mb4` before prefixing `0x01 || iv` (`spec/envelope.md` §2.3). The component cannot fix this for you: it does not know the legacy charset, and guessing would corrupt genuinely binary values.
9. **`gcm.strict` has no SESSION scope before MySQL 9.0** (`docs/design.md` amendment A5). Component system variables only gained session scope in 9.0.0, so on 8.0 and 8.4 `gcm.strict` is GLOBAL-only and `SET SESSION gcm.strict` fails with `ER_INCORRECT_GLOBAL_LOCAL_VAR`. Relaxing strictness for one connection is a 9.0+ capability; before that it is a server-wide decision. The tag-failure semantics themselves (ON = error, OFF = NULL) are identical on every version.
10. **Pass a stored value, not a freshly computed expression** (`docs/design.md` amendment A7). MySQL 8.0 and 8.4 hand a loadable function a stale view of some *computed* string arguments from the second row of a statement onward, so `gcm_encrypt_det(CONCAT(name, id), @k)` can silently seal the wrong bytes. Built-in functions over the same expression are unaffected and the component cannot detect it. Safe on every version: a column, a literal, a user variable or a bound parameter — which is what an application sends anyway. If a value must be computed in SQL, materialise it first (a derived table, a temporary table or a separate statement); `CAST` alone is **not** a reliable workaround. MySQL 9.4 does not reproduce it. `tests/integration/91_server_udf_arg_defect.sql` pins the behaviour per version.
11. **Define a per-key usage budget and rotation plan before deployment.** Aggregate encryption use across all servers, columns and applications sharing the key. Review limits for the random/deterministic nonce construction, message sizes and acceptable risk; this project has not established a universal safe usage limit. The component does not count uses or rotate keys. Rotation changes deterministic ciphertext equality, so plan JOIN/UNIQUE migrations and externally managed retention of keys needed for old data and backups.
12. **Preserve nonce safety and usage accounting through retries and recovery.** Copying, replicating or restoring an existing envelope is not a new encryption call. A new `gcm_encrypt` call uses a fresh random nonce. A deterministic retry reproduces bytes only for the same key, plaintext and AAD; do not change only AAD. Do not reset cumulative key-usage accounting when restoring a database. If usage history or RNG-state safety is uncertain after recovery/process cloning, stop encrypting with the affected key. Restore and verify safe RNG state across all writers before resuming with a freshly and independently generated key; key replacement alone does not repair duplicated RNG state. Retain old keys for required reads.
13. **Distinguish implemented checks from operational assurances.** Input validation, authentication and failure handling are implemented. Nonce-reuse detection, cross-call AAD-policy enforcement, usage quotas and rotation are not. Development guard hooks constrain agent commands, not production calls. Deterministic encryption leaks equality, frequency and length; test-vector conformance and sampled collision tests do not prove the construction or deployment safe. Obtain an independent review before production use. Reference: [NIST SP 800-38D, §8 and Appendices A/B](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
14. **Installing the component is not replicated** (`docs/design.md` amendment A8). `INSTALL COMPONENT` writes to that server's `mysql.component` and nothing else. Install it on every server that answers decryption queries and on every replica that could be promoted, and make sure the application can supply the key there too. ROW binlog carries the ciphertext, nonce and tag as bytes, so a replica never re-encrypts — that is what makes replication safe here, and it is also why the replica still needs the component to *read* those values. MySQL reference: [replication formats](https://dev.mysql.com/doc/refman/8.4/en/replication-formats.html), [component loading](https://dev.mysql.com/doc/refman/8.4/en/component-loading.html).
15. **Sharding: route on a stable identifier, not on ciphertext** (`docs/design.md` amendment A8). A random-nonce value differs on every call, so it cannot be a routing key; a deterministic value is stable but using it as the shard key turns key rotation into a resharding job. Moving rows between shards needs no re-encryption — the destination decrypts with the original key and AAD. Comparing deterministic ciphertext across shards requires the same key, plaintext *and* AAD, so the "one AAD convention per key" rule (item 7) applies across shard boundaries. Count new encryption calls across all shards that share a key when reasoning about the deterministic collision bound; copying existing ciphertext is not a new encryption. And `gcm_decrypt(...) LIKE '%김%'` alone cannot select a shard: without a routing predicate every shard is queried and each decrypts its own candidates. Whether a particular sharding proxy or router forwards loadable-function calls and preserves the result charset must be verified with that combination — this project only validates self-managed MySQL servers.
