Nothing is published yet, and the construction has not had a human cryptographic audit. Read the
[operational constraints](ops-constraints/) before you rely on it.
</Aside>

```sql
SET @k = UNHEX('000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f');  -- public fixture key

INSERT INTO patients (name_enc) VALUES (gcm_encrypt('홍길동', @k)), (gcm_encrypt('김철수', @k));

SELECT id, gcm_decrypt(name_enc, @k) AS name FROM patients
 WHERE gcm_decrypt(name_enc, @k) LIKE '%길%';     -- one row, 홍길동, matched inside the server
```

<CardGrid>
  <Card title="Search stays in the server" icon="magnifier">
    `gcm_decrypt` returns `utf8mb4`, so `LIKE '%길%'` uses MySQL's own collation. Plaintext never
    has to leave the database to be filtered.
  </Card>
  <Card title="Authenticated, not just encrypted" icon="approve-check">
    Every value carries a 128-bit GCM tag. A changed byte is an error, never wrong data. The key
    length picks AES-256, 192 or 128, and anything below 256 is off by default.
  </Card>
  <Card title="Deterministic when you need joins" icon="puzzle">
    `gcm_encrypt_det` gives the same value for the same input under one key, for join keys,
    `UNIQUE` and exact match. It reveals equality, so it is never for free text.
  </Card>
  <Card title="Measured, with the limits stated" icon="document">
    Server-side `LIKE` over 300,000 encrypted rows measured 0.75–0.96× `AES_DECRYPT` in nine CI
    runs. [How it was measured, and what that does not show](performance/).
  </Card>
</CardGrid>
